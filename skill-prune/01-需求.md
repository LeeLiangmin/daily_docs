# 需求

## 定位

本工具链专用于裁剪与改进 rustbot 的 `engineer-pack` 和 `expert-pack` 中的 skill，不面向任意来源的 skill 提供通用适配。以能力为优先：新版本的能力不低于原版，并尽量提升；同时，新版本不比原版长，完成任务的成本持平或下降。删减、合并、重写和分层均可作为改进手段，不以牺牲能力换取长度或成本下降。

首批只试点 `rust-test`，不改变两个包共 19 个 skill 的总体范围。试点以维护者能根据评测证据决定采用、退回或补测为完成标准，不要求一定产出可采用的候选。

方法依据见《Agent Skill 精简与重写研究综述》。验收方式将在本轮需求讨论中逐项确定。下文尚未讨论的既有条目保留为草案，不视为本轮已经确认的要求。

## 改动范围

候选版本只修改 `SKILL.md` 及配套文本，包括引用文档、示例和模板。允许在这些文本之间合并、重写和调整组织结构，长度约束见目标 G-2。

配套执行脚本保持原样，在任务运行中仍按需使用。脚本的功能优化和代码修复不属于候选生成范围；发现脚本问题时单独记录，不通过修改脚本改善候选的评测结果。

试点实现、依赖安装和测试运行须在独立于日常开发环境的沙箱中进行。隔离未验证前不启动试点，不回退到宿主机运行。

## 目标

| 编号 | 目标 | 验收方式 |
| --- | --- | --- |
| G-1 | 能力优先，新版本的能力不低于原版，并尽量提升 | 在相同任务、Agent、模型和环境下，按《候选验收》检查关键行为逐项通过、任务质量整体及重要场景不降低 |
| G-2 | 新版本不比原版长 | 按字符数统计 `SKILL.md` 及配套文本（引用文档、示例和模板）的总长度，候选不得大于原版；迁移到附件的内容仍计入总字符数 |
| G-3 | 总体任务运行成本持平或下降 | 按《任务运行成本》比较完整任务的平均运行成本，并透明展示各主要任务类型的成本变化，不以文本缩短替代成本测量 |
| G-4 | 在人工确认的边界内自动迭代，是否采用由人工决定 | 按《自动化与人工确认》检查前置确认、自动迭代、关键变更确认和最终交付；不直接修改 rustbot 的源文件 |
| G-5 | 模型升级后可重复执行 | 更换目标模型后，按同一流程重新评测，旧基线不被复用 |

## 交互行为保持

问询、选项提供和等待确认可能承载信息收集、用户决策权和执行授权，属于能力评测的一部分。以具体行为及其作用为判断单位，不笼统决定保留或优化整条流程。

交互行为默认保留，确认其冗余后才允许调整；作用尚不能确定时先保留。允许调整表达、重复说明和材料组织，但不能通过替用户作决定、跳过确认或缩减可选能力来降低成本。

评测需要检查：应当问询时是否问询、应提供的选项是否保留、需要等待回答或确认时是否停止，以及用户的回答和选择是否实际影响后续执行。最终产物正确不能替代这些过程检查。

## 多轮交互评测

采用预定义用户回复与触发条件、由工具自动驱动对话的方式，不使用大模型在运行时自由模拟用户。用户回复、选择分支和触发条件由大模型随用例生成，经人工审阅、调整、反馈迭代并批准。

- **交互定义**：用例规定各阶段的预期交互状态、对应用户回复和后续检查，包括信息补充、选项选择、配置修改和执行确认等适用情形。
- **自动回复**：工具识别实际交互状态，仅在批准的触发条件满足后发送对应回复。不要求被测 Agent 使用固定措辞，但必须保留所需问询、选项和等待行为。
- **异常处理**：出现跳过必要问询、提前执行、未定义分支或无法可靠识别状态时，保留对话和执行记录，标明行为问题或证据缺口，不自行补答、追加提示或纠正流程使测试通过。
- **对照与隔离**：原版与候选在同一用例中使用相同的用户意图、回复规则和判定条件。开发集与验收集各自的回复、分支和触发条件按《开发集与验收集隔离》管理；被测 Agent 仅按交互进展收到当前回复，不预先获得完整对话脚本或判定条件。

## 自动化与人工确认

采用“大模型生成、人工审阅批准、自动迭代、关键变更人工确认、最终人工采用”的方式。任务用例与候选版本均由大模型承担初稿生成和反馈修订，人工主要负责审阅、调整、修正、提出迭代意见和批准，不要求人工从零编写。

- **评测准备**：大模型根据 skill 及配套材料生成任务用例，提出必要能力和交互行为清单。用例应包含任务输入、预期结果、必要交互和判定依据，多轮用例另按《多轮交互评测》定义回复与触发条件，供人工审阅。人工可以直接修改，也可以反馈给模型继续生成和修订；批准后作为评测依据。用例的生成和批准不等于实测通过，自动迭代不得自行降低已确认的要求。
- **自动迭代**：在已确认的范围和预算内，工具自动生成、评测和修订候选，筛选满足能力、长度和任务运行成本要求的版本。常规文本修改不逐轮审批。
- **关键变更确认**：涉及取消问询、缩减选项、跳过确认或其他关键行为变化时，工具提出理由和影响，等待人工确认。未获确认时保留原行为，不阻塞其他已获授权的修改。
- **最终采用**：工具交付候选差异、任务表现、交互行为检查、总字符数和运行成本，由人工决定是否采用。没有合格候选时，交付评测结果和失败原因，不强行生成可采用版本。

## 开发集与验收集隔离

开发集与独立验收集完全分开，两组均由大模型生成，经人工审阅、调整、反馈迭代并批准。两组依据相同的能力要求，分别覆盖关键行为和重要场景，使用不同的任务情境。

- **内容隔离**：任务用例、用例专属输入材料、预期结果、答案、判定细节和运行记录分别管理。同一任务的改名、改写或轻微变体归入同一组，不跨组充当独立用例。
- **用途隔离**：开发集用于候选生成、筛选和修订，模型可以读取其评分与失败轨迹。验收集的生成和保管与候选生成过程隔离，候选生成环节不得接触验收题目、专属材料、答案、判定细节或运行记录。
- **最终验证**：候选确定并冻结后，在独立验收集上对比原版与候选。实际执行任务的 Agent 只获得完成当前任务所需的输入和交互，不获得答案或判定细节。开发集结果不能代替最终验收。
- **失败后修订**：若将验收结果用于指导修订或继续筛选候选，该批验收集转为开发用途，不再承担独立验收；下一轮须生成并经人工批准新的独立验收集。

固定工具、运行环境和通用依赖可以共用，保持原版与候选的比较条件一致；不得借此向候选生成环节暴露验收内容。

## 任务运行成本

采用“总体不增加，分类透明展示”的约束。只计入可归属到单次任务的直接运行费用，包括模型推理费、按次收费的外部工具费和按用量收费的云沙箱费。已包含在其他收费项目中的费用不重复计入。

固定订阅费和共用机器折旧不摊入单次任务，候选生成和评测投入不计入运行成本。本地脚本耗时和工具调用次数作为效率指标展示，不自行折算成金额。

- **完整任务**：从初始请求到任务结束，覆盖全部问询、选择、确认和后续执行。
- **总体比较**：原版与候选使用相同的任务、运行次数和环境，比较平均任务运行成本。失败运行的消耗同样纳入统计，不只选取成功结果。
- **费用证据**：优先采用可归属到任务的实付费用，并注明账单来源。没有逐任务账单时，可以用记录的计费用量乘以适用单价，按项求和，作为成本验收依据。原版与候选采用相同计价规则；报告区分实付与估算，并列出估算所用的分项用量（如普通输入、缓存输入和输出）、单价及费率来源，供审阅者复算。
- **证据缺失**：已知收费项目缺少可归属的实付金额、且无法按用量和费率复算时，分别列出已知费用与缺失项目，不将缺失金额按零计入。若无法据此比较总体运行成本，则成本证据不足，不推荐采用。包月费用不变或 token 总数减少，均不能单独证明任务运行成本未增加。
- **分类展示**：同时列出主要任务类型的成本及变化，允许部分类型的增加由其他类型的节省抵消，不要求每类任务都不增加。任务分类和各类任务的比例在评测前确定，不能根据候选结果调整。
- **能力前提**：成本达标以能力要求通过为前提，不能用失败、提前停止或跳过必要交互造成的低成本抵消能力缺失。

## 对照方式

每个最终候选都须与原版在同一独立验收集上比较。只有需要判断指令对特定任务的贡献时，才在相关开发用例上增加“无指令与原版”的对照，不要求每个 skill 都做。

无指令组不向模型提供被测 skill 的指导内容，各组仍使用相同的工具、未经修改的原版脚本和运行环境。结果只用于提出或排查裁剪假设：模型在没有指令时也能完成任务，不代表某一段可以删除，更不能代替候选与原版的验收比较。

## 候选验收

最终验收使用《开发集与验收集隔离》规定的独立验收集，采用“关键行为逐项通过，任务质量整体及重要场景不降低”的原则。关键行为和重要场景在评测准备阶段由大模型提出、人工审阅批准，不能在看到候选结果后自行放宽。

- **触发能力**：用例不点名被测 skill，预先标明请求是否应选中它。比较原版与候选时，除被测版本外，其余可选的 rustbot skill 保持一致。触发报告分别列出应触发用例中的漏触发和不应触发用例中的误触发，以及各自的用例数。
- **执行能力**：执行用例可以明确指定被测 skill。执行报告列出选中后的任务结果、必要交互和实际产物，区分“未选中”与“选中后执行失败”。触发与执行分别验收，不用一项的成绩抵消另一项的退化。
- **关键行为**：已确认的必要行为逐项检查，不允许用其他任务的高分、长度减少或成本下降抵消失败。交互行为检查见《交互行为保持》。
- **任务质量**：比较总体表现，并分别检查主要任务类型、边界情况和原版薄弱场景，避免平均分掩盖重要场景的退化。不要求每个普通用例都单独取得不退化的统计证明，但仍保留逐例结果，分析失败和波动。
- **运行波动**：不凭一次普通用例失败直接认定版本退化，通过复测和对照分析判断；不能通过反复重试至通过来掩盖关键行为失败。重复次数、统计方法和证据充分性判据在评测方案中确定，未发现显著差异不等于证明不退化。
- **推荐采用**：能力要求通过、总字符数不增加和任务运行成本持平或下降必须同时满足，不使用加权总分使三者互相补偿。证据不足时不推荐采用，说明缺口和补测需要。

## 反目标

- 不追求删得越多越好。长度只是约束，不是优化目标。
- 不自动采用候选。没有人工确认，不合并到 rustbot。
- 不在 `rustbot/` 和 `SkillEvaluator/` 两个上游克隆中修改文件。

## 非目标

- 不覆盖 `rustbot/skills`、`rustbot/knowledge`、`rustbot/test-pack` 和 `rustbot/tools` 下的 skill。
- 不修改 SkillEvaluator 本身。它不提供内容消融，也不提供重写，这两项由本工具链的候选生成环节承担。
- 不评测 rustbot 的 MCP 执行器、hooks 和 dashboard。

## 设计原则

- 每个候选围绕一个明确的修改目的，可以同时修改正文的多个段落及配套文本。例如，合并重复的配置说明时，可以同时修改正文和模板中的说明。改动仍须遵守《改动范围》和《自动化与人工确认》。
- 每个候选说明改动内容和理由、预计影响的任务与交互行为、可能的运行消耗变化，并附上文本差异、关联的开发集用例及原版与候选的对比结果。
- 合并多个已验证改动后，将组合版本视为新候选，重新运行完整开发集，不沿用各项改动单独通过的结论。
- 评测的实验变量只有 skill 内容。同一数据集、同一 Agent 与模型、同一 judge、同一尝试次数。
- 没有被用例触及的内容，得分不变不能证明可以删除或改写。数据集的覆盖度是前提。
- 判定结论宁窄勿宽。尝试次数少时波动大，结论附带统计区间。

## 待决事项

1. 评测方案：确定重复次数、统计方法、证据充分性判据，以及开发集与验收集的隔离实现。
2. 目标 Agent 与模型，以及各 skill 的交互行为清单和冗余判定依据。
3. 用例生成所需的材料、覆盖要求、人工审阅与迭代的呈现方式，以及原版做不好的用例如何获得。
4. 评测环境：Docker Desktop 还是 WSL 2，模型 API 与费用预算。
5. 试点后其余 18 个 skill 的接入顺序。
6. 候选版本和评测结果的存放位置与格式。
