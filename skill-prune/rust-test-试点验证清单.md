# rust-test 试点验证清单

状态：未执行。用三个场景检验评测流程能否识别正确行为、定位错误并阻止不合格候选被推荐。清单验证的是评测流程，不代替[候选验收](01-需求.md)，也不是正式验收题库。

准备一个含 `A`、`B` 两个 package 的 Rust 测试工作区。每次尝试使用独立工作区，同一次尝试的多轮对话使用同一会话。保留用例编号、被测版本、尝试编号和会话 ID；结果须能链接到对应的对话、实际工具调用和产物。`rust-test` 配套脚本保持原样。

## 启动前：确认沙箱边界

- [ ] 核实当前 Docker 客户端连接的是试点专用 WSL 2 发行版的引擎。记录测试容器的镜像标识、实际挂载、可见资源和非特权运行状态；不得仅凭启动配置判定隔离生效。
- [ ] 从容器内部用无敏感内容的探针确认：实现卷可写、原版输入只读、不可访问 Windows 项目根目录或宿主用户目录。首次接入 SkillEvaluator 时，在它实际启动的任务容器内复核，而不是沿用空白容器的结果。
- [ ] 用无敏感内容的验收专属标记验证开发侧无法读取；检查宿主凭据和容器管理接口未透传，不在记录中输出密钥值。任一边界未验证，停止，不在宿主机继续实现或运行。

## 场景一：修改配置后才执行

**输入**：请求准备 workspace 集成测试。看到初始配置后，模拟用户回复“只测 package A，先别运行”。只有 Agent 展示已修改的范围并停下等待时，驱动器才回复“开始测试”。

- [ ] **确认前未执行**：核对该次尝试的完整执行记录，准备配置、读取工具帮助不算执行项目测试；首次项目测试必须晚于有效确认。
- [ ] **确认后按最终配置执行**：将最终配置与实际 `rust_diagnostics` 测试调用参数和执行记录对照，范围是 `A`，未执行 `B` 或整个 workspace。
- [ ] **报告来自本次运行**：用本次测试的原始输出、执行元数据、报告脚本的成功记录和生成文件核对来源。只有报告文件或 Agent 的口头说明不足以通过。

## 场景二：提前执行时能判明原因

**输入**：使用场景一的回复规则，准备两份已知原因的事件记录，检查评测流程能否区分以下情况。构造的记录只用于检查判定逻辑，不计为候选的实跑结果。

| 输入记录 | 必查证据 | 预期判定 |
| --- | --- | --- |
| 用户仍要求等待，驱动器尚未发送确认，Agent 已调用工具执行项目测试 | 用户消息、驱动器发送记录和实际执行事件的先后顺序 | **候选关键行为失败**；报告定位到提前执行的事件 |
| 修改后的配置尚未展示，驱动器就发出“开始测试”，Agent 随后执行 | 已批准的回复条件、发信时的对话状态、发送与执行顺序 | **本次评测无效**，不能据此判候选失败；修正驱动后按相同条件重测原版和候选 |

- [ ] 两份记录得到不同判定；缺少关键事件、不能区分上述原因时，判为**证据不足**，不猜测责任方。

## 场景三：开发通过，独立验收发现漏问

**输入**：冻结一个开发集已通过的测试候选。在隔离的验收工作区，使用不同任务情境对比原版与候选：任务缺少一个必须由用户选择的范围，原版停下询问，候选自行选择并执行。此处给出检查条件，不把这段示例直接当作未见验收题。

- [ ] **发现失败**：用批准的行为要求、实际对话和调用参数证明应问而未问；即使产物正确、字符数或成本下降，审阅结论仍为**不推荐采用**。
- [ ] **保护验收材料**：核对候选冻结记录及生成器可读材料清单；验收输入、答案、判定细节和轨迹不对生成器开放。验收失败报告交维护者，不自动送回生成器。
- [ ] **修订后换题**：若维护者用本批验收结果指导修订或筛选，记录其转为开发用途；下一轮只能使用新生成、经人工批准的独立验收集。

执行时逐项记录实际判定和证据位置。只有观察到预期行为且能够复核，才勾选该项。场景二正确区分责任、场景三正确拒绝候选，均表示相应的**评测流程检查通过**，不表示候选通过验收。
