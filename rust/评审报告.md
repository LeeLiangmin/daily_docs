# Rust 编码规范（节选）评审报告

## 1. 结论摘要

- **范围**：15 条（13 条规则、2 条原则 P.MAC.DCL.01 / P.MAC.PRO.01），按必要性、准确性、定级、lint 四个维度逐条评审。
- **必要性**：15 条全部保留，未发现应删除或合并的条款。
- **准确性**：13 条正文有修订（另全部 15 条新增【检测】字段），其中有实质错误的 2 条：G.TRA.01 的一组「正例」实际违反 Ord 契约（实测 BTreeSet 丢元素）；G.MAC.01 的【例外】示例自相矛盾、校验不充分。另有 3 处示例无法编译（G.CTF.01 类型错误，G.TRA.01、G.ERR.01 缺少 use 或常量定义），1 处在 2024 版次下告警（G.MAC.01）。G.EXP.02、G.TRA.02 只新增【检测】，正文不改。
- **定级**：调整 1 条：G.EXP.01 建议 → 要求。其余维持。
- **lint**：完全支持 1 条（G.TRA.02），部分支持 11 条，不支持 3 条（G.CTF.02、G.MAC.DCL.01、P.MAC.PRO.01）。原清单中 3 处 lint 名有误：`unsafe_block_in_proc_macro` 不存在，`infinite_loop` 缺 `clippy::` 前缀，`rustc::unused_must_use` 不是合法写法。原清单无 lint 的 5 条中，有 2 条现可部分支持（G.CTF.01、P.MAC.DCL.01）。
- **POC**：分两处。门禁 PoC 放在 bot-gate-lab，按该仓库契约每个 lint 一个 case，共 31 个 lint case、20 个 pass 场景；学习用例放在 playground，按条款组织，共 64 个（64/64 按预期复现），覆盖命中、漏报、误报、语义验证与示例校验。

## 2. 评审基线与方法

- lint 基线：rustc / Clippy **1.89.0**。lint 是否存在、所属分组与默认级别，以 rust-lang/rust@1.89.0 与 rust-clippy@rust-1.89.0 的源码为准。
- 学习用例（playground）的实测结果来自 `rustc 1.89.0 (29483883e 2025-08-04)`、`clippy 0.1.89 (29483883ee 2025-08-04)`；其中 3 处 1.89 与 1.97 行为不同，已标注为「版本差异」，并在 case.toml 中用 `since` 同时声明两个版本的期望。
- 门禁 PoC（bot-gate-lab）：`cases/<rustc|clippy>/<lint>/`，`case.toml` 的 `id` 为 lint ID、`rule` 为条款编号；漏报以 `pass/<场景>/` 表达（目标 lint 0 次命中，`kind` 区分边界与漏报），入口 `scripts/validate-guideline.sh`，与 Fast 集合共用 `assert-diagnostics.py`。已在 rustc 1.97.0 上全部通过（48 项检查），尚需在 1.89.0 上复跑。
- 学习用例（playground）：`cases/guideline/<条款>/<场景>/`，`case.toml` 可声明 0 次命中、编译失败、运行输出等预期，入口 `scripts/validate-guideline.py`，终端回显编译器原始输出。
- 「零告警」类结论在 `clippy::all + pedantic + nursery` 下得出，未开启 restriction 组（该组 lint 互相冲突，不适合整体开启）。
- 检测能力定级：**完全支持**＝条款描述的范围 lint 都能覆盖且无已知误报；**部分支持**＝有 lint 但存在漏报或需额外配置；**不支持**＝无可用 lint。

## 4. 逐条评审

### G.CTF.01 宜优先使用模式匹配而非判断后再取值

**必要性：保留。** 判断后再取值会留下额外的 panic 路径（unwrap / 下标越界），而且判断与取值分离后容易在重构中失配；模式匹配把二者合成一步，是 Rust 惯用写法。

**准确性：示例需修正。** 描述准确。反例中 `let list: &[f32] = vec![1.23];` 无法编译（E0308）；正例中的 `index` 未定义来源。

**定级：建议 → 建议。** 属于惯用法与可读性改进，不构成独立的正确性风险，维持建议。

**lint：部分支持。** 原：（无）；建议：`clippy::unnecessary_unwrap`。原文未配置 lint。clippy::unnecessary_unwrap（complexity，默认 warn）可覆盖 Option/Result 先判断后 unwrap 的反例。漏报：切片判空后下标取值无任何 lint（indexing_slicing 不区分是否已判空，粒度不对）；1.89 只识别局部变量，结构体字段先判断后 unwrap 不报（1.97 已支持）。

#### 修订项

**1. 反例代码：修正类型错误**

```diff
- let list: &[f32] = vec![1.23];
+ let list: &[f32] = &[1.23];
```

理由：原示例无法编译（E0308：`Vec<f32>` 不能赋给 `&[f32]`），读者照抄会先撞上编译错误。

依据：POC G.CTF.01-04

**2. 正例注释：说明 index 来源**

```diff
- // 符合
+ // 符合：index 为任意 usize 下标
```

理由：原示例中 `index` 没有定义也没有说明，读者无法判断示例是否完整。

依据：POC G.CTF.01-05

#### lint 调整

```diff
- （无）
+ clippy::unnecessary_unwrap
```

检测能力：**部分支持**

理由：

- 原文没有配置 lint；`unnecessary_unwrap` 默认开启（complexity，warn），能检出第一个反例（判断后 unwrap）。
- 第二个反例（判空后下标取值）没有 lint 能覆盖，所以是部分支持。

### G.CTF.02 在 Match 分支的 Guard 语句中不宜使用带有副作用的条件表达式

**必要性：保留。** Guard 的执行次数对读者不直观（或模式下会多次执行），带副作用时会产生难以定位的逻辑错误，且没有工具能兜底，需要靠规范约束。

**准确性：描述需精确化。** 「匹配几次就会执行 Guard 几次」没有点明前提。实测去掉 `|` 后 Guard 只执行 1 次，多次执行来自或模式中每个匹配成功的子模式（Rust Reference 对 match guard 的说明一致）。示例行为属实。

**定级：建议 → 建议。** 风险仅在「或模式 + 副作用」组合下出现，且无 lint 可检测，维持建议。

**lint：不支持。** 原：（无）；建议：（无）。rustc / Clippy 均无相应 lint；在 clippy::all + pedantic + nursery 下原文反例零告警。

#### 修订项

**1. 描述：点明多次执行的前提**

```diff
- 在 match 分支中，匹配几次就会执行 Guard 几次。Guard 的条件表达式不应该携带副作用。
+ Guard 的条件表达式不应该携带副作用。当分支使用 `|` 组合多个模式时，Guard 会针对每个
+ 匹配成功的子模式各执行一次，直到某次返回 true 为止，因此同一个 Guard 可能被执行多次。
```

理由：原句没有说明前提，容易理解成「所有 Guard 都会重复执行」。实测去掉 `|` 后 Guard 只执行 1 次，多次执行只来自或模式：

```rust
Some(1) | Some(_) if condition(&i) => {}   // condition 执行 2 次
Some(_) if condition(&i) => {}             // condition 执行 1 次
```

依据：POC G.CTF.02-01 / 02

**2. 反例注释：与新描述对应**

```diff
- // 这个条件表达式带有副作用：打印并修改了变量 i 内部的值，因为匹配两次，所以会执行两次
+ // 这个条件表达式带有副作用：打印并修改了变量 i 内部的值。
+ // Some(1) 与 Some(_) 两个子模式都匹配，Guard 返回 false，因此执行两次
```

理由：让读者从注释直接看出执行两次的原因。

#### lint 调整

无变化。

检测能力：**不支持**

理由：

- rustc / Clippy 都没有相应 lint，全量 lint 下原文反例零告警。

门禁 PoC（bot-gate-lab）：无（无对应 lint）

学习用例（playground）：G.CTF.02-01、G.CTF.02-02

### G.CTF.03 循环或递归必须安全退出

修订后标题：**宜确保循环或递归能够安全退出**

**必要性：保留。** 缺少退出机制的循环会导致无法优雅停机、资源无法释放，递归缺少终止条件会栈溢出。

**准确性：需修订。** ①标题用「必须」，与级别「建议」矛盾；②服务主循环等有意常驻的循环是合理设计，原文没有给出合规写法，导致此类代码无法合规；③标题含「递归」但没有递归示例；④panic! / process::exit 是否算「安全退出」未说明（process::exit 不执行析构，与「将资源正确释放」相悖）；⑤正例重复粘贴。

**定级：建议 → 建议。** 常驻循环在服务、嵌入式场景是正常设计，是否需要退出路径依赖业务判断；对应 lint 属 restriction 组，误报需人工甄别。维持建议，仅把标题措辞调整为与级别一致。

**lint：部分支持。** 原：infinite_loop；建议：`clippy::infinite_loop`、`clippy::while_immutable_condition`、`unconditional_recursion`。原文 lint 名缺少 `clippy::` 前缀。infinite_loop（restriction）能检出无 break/return 的 loop，函数返回 `!` 时不报。漏报：把 panic!/process::exit 视为出口；只检查 `loop`，while 形式需 while_immutable_condition；递归需 rustc unconditional_recursion，且有终止分支但不可达时不报。误报：1.89 中未 await 的 async 块内的常驻循环（如 spawn(async { loop {..} })）会误报，1.97 已修复。

#### 修订项

**1. 标题：去掉「必须」**

```diff
- 循环或递归必须安全退出
+ 宜确保循环或递归能够安全退出
```

理由：本条级别是「建议」，标题用「必须」，两者矛盾。

**2. 描述：给常驻循环合规写法，明确什么不算安全退出**

```diff
- 循环必须安全退出，递归也必须安全结束。
+ 循环应能安全退出，递归也应能安全结束。
+ - 有意常驻、不会返回的循环（如服务主循环），应将所在函数的返回类型声明为 `!`，明确表达意图；
+   需要支持停机时，应提供退出信号（如关闭标志、通道关闭）并在退出前释放资源。
+ - `panic!`、`std::process::exit` 不属于安全退出：后者不会执行栈上对象的析构（Drop）。
```

理由：

- 服务主循环、工作线程是正常设计，原文没给合规写法，这类代码按字面无法合规。`-> !` 正是 `clippy::infinite_loop` 认可的豁免方式。
- 原文要求「将资源正确释放后安全退出」，`process::exit` 不执行 Drop，与此相悖；而 lint 恰好把 panic / exit 当作出口，需要规范写明。

依据：POC G.CTF.03-02 / 03

**3. 新增递归反例**

```diff
+ // 不符合：递归没有终止条件
+ fn depth(n: u64) -> u64 {
+     depth(n + 1)
+ }
```

理由：标题含「递归」，原文却只有循环的示例。

依据：POC G.CTF.03-06

**4. 新增常驻循环正例**

```diff
+ // 符合：有意常驻的服务循环，用 `!` 返回类型显式声明不会返回
+ fn serve(listener: std::net::TcpListener) -> ! {
+     loop {
+         if let Ok((stream, _)) = listener.accept() {
+             handle(stream);
+         }
+     }
+ }
```

理由：对应第 2 条，给出可以照写的合规形式。

**5. 删除重复正例**

```diff
- fn main() { ... }      // 第二份重复的正例
- fn should_exit(...) { ... }
```

理由：格式问题，同一段正例出现了两次。

### G.EXP.01 避免复合条件表达式永远为 true 或 false

修订后标题：**避免条件表达式永远为 true 或 false**

**必要性：保留。** 恒真 / 恒假条件几乎总是逻辑错误（掩码写错、比较方向写反），会让分支变成死代码。

**准确性：标题需修订。** 三个反例中前两个（`(x & 1) == 2`、`(x & 3) < 4`）都不是复合条件，「复合」一词把范围收窄了；lint 覆盖的也是一般条件表达式。描述本身准确。

**定级：建议 → 要求。** ①这类表达式几乎没有正当用途，属于缺陷而非风格；②1.89 中对应的 Clippy lint 全部属 correctness 组、默认 deny，现有代码在默认配置下已被拦截，升级不增加整改成本；③唯一的意图正常场景（配置常量导致恒值）可局部 allow，见新增【例外】。

**lint：部分支持。** 原：clippy::bad_bit_mask；建议：`clippy::bad_bit_mask`、`clippy::overly_complex_bool_expr`、`clippy::impossible_comparisons`、`clippy::absurd_extreme_comparisons`、`unused_comparisons`、`clippy::eq_op`。bad_bit_mask 只覆盖前两个反例；第三个反例 `(x < y) && false` 需要 overly_complex_bool_expr。区间矛盾、类型极值比较、自比较分别由 impossible_comparisons、absurd_extreme_comparisons / unused_comparisons、eq_op 覆盖。漏报：`x % 2 == 2`、`x != 1 || x != 2` 全量 lint 均不报。误报风险：掩码来自配置常量、某些构建下为 0 时 bad_bit_mask 报警。版本提示：overly_complex_bool_expr 在 1.97 已降为 pedantic，升级工具链后需显式开启。

#### 修订项

**1. 标题：删除「复合」**

```diff
- 避免复合条件表达式永远为 true 或 false
+ 避免条件表达式永远为 true 或 false
```

理由：

- 原文三个反例中，`(x & 1) == 2`、`(x & 3) < 4` 都只有一个比较，不是复合条件，标题与示例不一致。
- 最常见的恒值条件是单个比较，如 `u32 >= 0`、`x == x`，按字面却不在本条范围内。
- 对应 lint 不区分是否复合；本条升为「要求」后，范围不一致会引发「算不算复合」的争议。

**2. 新增反例：区间矛盾**

```diff
+ if x > 10 && x < 5 { // 不符合：区间矛盾，永远为 false
+     // ...
+ }
```

理由：最常见的恒假写法之一，原文没有覆盖；对应新增的 `impossible_comparisons`。

依据：POC G.EXP.01-02

**3. 新增【例外】**

```diff
+ 【例外】
+ 掩码或阈值来自构建配置生成的常量、在某些配置下恰好使表达式恒值时，
+ 可局部 `#[allow(...)]` 并注明原因。
```

理由：升为「要求」后 lint 会作为门禁，而用构建配置生成掩码是正常写法，在某些配置下 lint 会报（见下文误报风险）。

依据：POC G.EXP.01-04

#### lint 调整

```diff
- clippy::bad_bit_mask
+ clippy::bad_bit_mask
+ clippy::overly_complex_bool_expr
+ clippy::impossible_comparisons
+ clippy::absurd_extreme_comparisons
+ unused_comparisons
+ clippy::eq_op
```

检测能力：**部分支持**

理由：

- `bad_bit_mask` 只覆盖前两个反例；第三个 `(x < y) && false` 需要 `overly_complex_bool_expr`（POC G.EXP.01-01）。

### G.MAC.01 不应通过宏将 unsafe 代码伪装为 safe 代码

**必要性：保留。** 宏隐藏 unsafe 会绕过编译器对调用方的 unsafe 检查，属于健全性问题（参见 RUSTSEC-2020-0011 plutonium）。

**lint：部分支持。** 原：unsafe_block_in_proc_macro；建议：`clippy::macro_metavars_in_unsafe`、`clippy::undocumented_unsafe_blocks`。原文 lint `unsafe_block_in_proc_macro` 在 1.89 的 rustc 与 Clippy 中均不存在（源码检索为 0）。最接近的是 clippy::macro_metavars_in_unsafe（1.80+，suspicious）：检查声明宏元变量是否在 unsafe 块内展开。漏报：默认只检查导出宏，原文 make_safe! 是私有宏，默认不报（需 warn-unsafe-macro-metavars-in-private-macros = true）；只检查被调用过的宏；宏内写死的 unsafe 调用不报；过程宏完全不覆盖。

## 5. 共性问题

1. **lint 名称写法不统一、部分不合法**：rustc 内建 lint 没有工具前缀（应写 `unused_must_use`，`rustc::` 是编译器内部 lint 的命名空间）；Clippy lint 必须带 `clippy::`（`infinite_loop` 缺前缀）；`unsafe_block_in_proc_macro` 在 1.89 中不存在。修订稿统一按「rustc lint 无前缀、Clippy lint 带 `clippy::`」书写。
2. **大量 lint 默认不开启**：建议使用的 lint 中，restriction / pedantic 组共 14 个，rustc 的 ambiguous_negative_literals 默认 allow，均需显式开启，否则「有 lint」不等于「在检查」。附录 A 给出可直接使用的配置。
3. **检测结论依赖工具链版本**：1.89 与 1.97 之间：overly_complex_bool_expr 从 correctness 降为 pedantic；unnecessary_unwrap 新增字段接收者支持；infinite_loop 修复了 async 块误报。规范的【检测】字段应注明基线版本，升级工具链时复跑 POC。
4. **条款标题情态词与级别不一致**：例如 G.CTF.03 用「必须」却定为建议，G.ERR.01、G.MOD.01、G.FUD.01 用「应」也定为建议。本次只修正与级别直接矛盾的「必须」，其余建议在下一轮统一约定（如：要求用「应 / 不应」，建议用「宜 / 不宜」）。
5. **原文缺少检测信息**：原规范正文没有 lint 字段，lint 映射只存在于条款清单中。修订稿为每条新增【检测】字段，写明 lint、支持度和所需配置，便于门禁对齐。
