> 基线：rustc / Clippy 1.89.0 lint 列表。每条新增【检测】字段，写明对应 lint、检测能力（完全支持 / 部分支持 / 不支持）和需要开启的配置。修订理由逐条见《评审报告》，原文对照见对照页。

## 表达式与流程控制

### G.CTF.01 宜优先使用模式匹配而非判断后再取值

**【级别】** 建议

**【描述】**

使用 Rust 语言的模式匹配特性会让代码更优雅和简洁，在解构数据结构时，宜使用模式匹配方式，而不是通过 if 判断后再取值。

**【反例】**

```rust
let opt: Option<i32> = Some(2);
// 不符合
if opt.is_some() {
    let value = opt.unwrap();
    // ...
}

let list: &[f32] = &[1.23];
// 不符合
if !list.is_empty() {
    let first = list[0];
    // ...
}
```

**【正例】**

```rust
// 符合
if let Some(value) = opt {
    // ...
}
// 符合
if let [first, ..] = list {
    // ...
}
// 符合：index 为任意 usize 下标
if let Some(val) = list.get(index) {
    // ...
}
```

**【检测】** 部分支持

- `clippy::unnecessary_unwrap`（complexity，默认 warn）：检出对 Option / Result 先 `is_some()` / `is_ok()` 判断、再 `unwrap()` 的写法。
- 不覆盖：切片判空后用下标取值（第二个反例）。1.89 中只识别局部变量，对结构体字段（如 `self.v`）先判断后 unwrap 的写法不报。

### G.CTF.02 在 Match 分支的 Guard 语句中不宜使用带有副作用的条件表达式

**【级别】** 建议

**【描述】**

Guard 的条件表达式不应该携带副作用。当分支使用 `|` 组合多个模式时，Guard 会针对每个匹配成功的子模式各执行一次，直到某次返回 true 为止，因此同一个 Guard 可能被执行多次。

**【说明】**

副作用是指对执行状态产生影响，包括：修改对象、修改文件等。在某些情况下副作用会给程序带来不必要的麻烦，其产生的错误十分难以查找，并降低程序的可读性。

**【反例】**

```rust
use std::cell::Cell;

fn main() {
    let i: Cell<i32> = Cell::new(0);
    let opt = Some(1);
    // 不符合：代码最终会输出两次 "add 1"
    match opt {
        // 这个条件表达式带有副作用：打印并修改了变量 i 内部的值。
        // Some(1) 与 Some(_) 两个子模式都匹配，Guard 返回 false，因此执行两次
        Some(1) | Some(_) if condition(&i) => {}
        _ => {}
    }
    assert_eq!(i.get(), 2);
}

// 带有副作用，匹配时多次执行可能会出现预想不到的逻辑问题
fn condition(i: &Cell<i32>) -> bool {
    println!("add 1");
    i.set(i.get() + 1); // 如果函数被执行两次，这里也会被设置两次
    false
}
```

**【正例】**

```rust
use std::cell::Cell;

fn main() {
    let i: Cell<i32> = Cell::new(0);
    let opt = Some(1);
    // 符合：代码最终输出一次 "add 1"
    match opt {
        // 注意有副作用的函数被移动到了Guard语句之后调用以作判断
        Some(1) => if condition(&i) {}
        Some(_) => if condition(&i) {}
        _ => {}
    }
    assert_eq!(i.get(), 1);
}

// 带有副作用，匹配时多次执行可能会出现预想不到的逻辑问题
fn condition(i: &Cell<i32>) -> bool {
    println!("add 1");
    i.set(i.get() + 1); // 如果函数被执行两次，这里也会被设置两次
    false
}
```

**【检测】** 不支持

rustc / Clippy 无相应 lint，需人工评审。

### G.CTF.03 宜确保循环或递归能够安全退出

**【级别】** 建议

**【描述】**

在应用程序中，一个重复提供服务的逻辑循环，应当包含相应的退出机制，并且将资源正确释放后安全退出。

循环应能安全退出，递归也应能安全结束。

- 有意常驻、不会返回的循环（如服务主循环），应将所在函数的返回类型声明为 `!`，明确表达意图；需要支持停机时，应提供退出信号（如关闭标志、通道关闭）并在退出前释放资源。
- `panic!`、`std::process::exit` 不属于安全退出：后者不会执行栈上对象的析构（Drop）。

**【反例】**

```rust
fn main() {
    let mut counter = 0;

    loop {
        counter += 1;
        // 不符合：循环无退出条件
    }
}
```

```rust
// 不符合：递归没有终止条件
fn depth(n: u64) -> u64 {
    depth(n + 1)
}
```

**【正例】**

```rust
fn main() {
    let mut counter = 0;

    loop {
        counter += 1;
        // 符合：循环包含退出条件
        if should_exit(counter) {
            break;
        }
    }
}

fn should_exit(count: u32) -> bool {
    count >= 5
}
```

```rust
// 符合：有意常驻的服务循环，用 `!` 返回类型显式声明不会返回
fn serve(listener: std::net::TcpListener) -> ! {
    loop {
        if let Ok((stream, _)) = listener.accept() {
            handle(stream);
        }
    }
}

fn handle(_stream: std::net::TcpStream) {
    // ...
}
```

**【检测】** 部分支持

- `clippy::infinite_loop`（restriction，需显式开启）：检出没有 `break` / `return` 的 `loop`；所在函数返回 `!` 时不报。
- `clippy::while_immutable_condition`（correctness，默认 deny）：检出条件在循环体内不会改变的 `while` 循环。
- `unconditional_recursion`（rustc，默认 warn）：检出没有任何出口的递归。
- 不覆盖：以 `panic!` / `process::exit` 为出口的循环会被当作可退出；递归有终止分支但实际到达不了时不报。
- 误报：1.89 中，未 await 的 `async` 块（如 `spawn(async { loop { .. } })`）里的常驻循环会被误报，需局部 `#[allow]` 并写明原因。

### G.EXP.01 避免条件表达式永远为 true 或 false

**【级别】** 要求

**【描述】**

条件表达式永远为 true 或 false 通常是因为代码编写错误。

**【反例】**

```rust
let x = 2;
if (x & 1) == 2 { // 不符合：该表达式会永远是 false
    // ...
}

if (x & 3) < 4 { // 不符合：判断表达式结果永远为 true
    // ...
}

let y = 0;
if (x < y) && false { // 不符合：判断表达式结果永远为 false
    // ...
}

if x > 10 && x < 5 { // 不符合：区间矛盾，永远为 false
    // ...
}
```

**【正例】**

```rust
let x = 2;
// 符合
if x == 2 {
    // ...
}
```

**【例外】**

掩码或阈值来自构建配置生成的常量、在某些配置下恰好使表达式恒值时，可局部 `#[allow(...)]` 并注明原因。

**【检测】** 部分支持

- `clippy::bad_bit_mask`：位掩码与比较组合恒值（反例 1、2）。
- `clippy::overly_complex_bool_expr`：布尔表达式中可消去的项（反例 3）。
- `clippy::impossible_comparisons`：区间矛盾（反例 4）。
- `clippy::absurd_extreme_comparisons`、rustc `unused_comparisons`：与类型极值比较（如 `u32 >= 0`）。
- `clippy::eq_op`：两侧相同的比较（如 `x == x`）。
- 以上 Clippy lint 在 1.89 均属 correctness（默认 deny），rustc 的 `unused_comparisons` 默认 warn。
- 不覆盖：如 `x % 2 == 2`、`x != 1 || x != 2`。

### G.EXP.02 用括号明确表达式的操作顺序，避免过分依赖默认优先级

**【级别】** 建议

**【描述】**

宜使用括号强调表达式的优先级顺序，增加可读性，防止开发者因不熟悉默认的优先级而导致错误。

**【反例】**

```rust
1 << 2 + 3 // 不符合
-1i32.abs() // 不符合
```

**【正例】**

```rust
(1 << 2) + 3 // 符合
(-1i32).abs() // 符合
```

**【检测】** 部分支持

- `clippy::precedence`（complexity，默认 warn）：算术运算与位移 / 位运算混用（反例 1）。
- `ambiguous_negative_literals`（rustc，allow-by-default，需显式开启）：负号字面量后接方法调用（反例 2）。
- `clippy::precedence_bits`（restriction，需显式开启）：位运算与移位混用（如 `x & 0xF0 >> 4`）。
- 不覆盖：`&&` 与 `||` 混用。

## 函数与闭包

### G.FUD.01 内存拷贝代价大的参数应按地址传递

**【级别】** 建议

**【描述】**

Rust 中按值传递参数（包括所有权转移）时，语义上会按位拷贝该类型自身大小的内存，不包括其指向的堆数据；编译器可能消除该拷贝，但不作保证。因此需要考虑内存拷贝的代价，设计合理的参数类型：

- 对于输入参数，拷贝代价小的类型使用值传递，拷贝代价大的类型传递只读引用。类型大小可通过 `std::mem::size_of::<T>()` 获取，超过 256 字节的类型可视为拷贝代价大。
- 对于返回类型，如果拷贝代价大，宜设计传递可写借用参数并返回它。

**【反例】**

对于输入参数：

```rust
// 不符合
fn func(val: [i32; 1000]);
```

**【正例】**

对于输入参数：

```rust
// 符合
fn func(val: &[i32]);
```

**【反例】**

对于返回类型：

```rust
// 不符合：Self 拷贝代价大时，每次调用都可能拷贝整个 Self
fn set_property(self, name: &str, value: &str) -> Self;
```

**【正例】**

对于返回类型：

```rust
// 符合：传递可写借用参数并返回它，适合链式调用的场景
fn set_property(&mut self, name: &str, value: &str) -> &mut Self;
```

**【说明】**

Self 拷贝代价小时，消费 self 并返回 Self 的写法（消费型 Builder）同样适用，不在本条约束范围。

**【检测】** 部分支持

- `clippy::large_types_passed_by_value`（pedantic，需显式开启）：按值传入且超过 `pass-by-value-size-limit`（默认 256 字节）的 **Copy** 类型参数。
- 默认跳过导出 API（`avoid-breaking-exported-api = true`），需在 clippy.toml 中设为 false 才检查 pub 函数；注意该开关同时影响其他多个 lint。
- `clippy::needless_pass_by_value`（pedantic）：可部分补充非 Copy 类型，只在函数体未消费参数时报。
- 不覆盖：非 Copy 大类型被消费的情形；返回类型部分。

### G.FUD.02 宜合理使用 Result 类型或 must_use 修饰，保证用户有效处理返回值

**【级别】** 建议

**【描述】**

Rust 中有以下方法可以在用户忽略函数返回值的时候出现编译告警：

- 返回值类型是 Result。
- 函数定义增加 `#[must_use]` 修饰。
- 函数返回的专有数据类型增加 `#[must_use]` 修饰。

**【说明】**

以下写法会使上述告警失效，需在评审中关注：

- `let _ = f();` 显式丢弃返回值；
- `f().ok();` 把 Result 转为 Option 后丢弃；
- 标注了 `#[must_use]` 的类型被包在 `Option` 等容器中返回时，类型上的标注不再生效。对关键返回值，宜在函数上同时标注 `#[must_use]`。

**【反例】**

```rust
#[must_use]
fn foo1() -> i32 {
    0
}

fn caller() {
    // 不符合：静默丢弃了 must_use 返回值
    let _ = foo1();
}
```

**【正例】**

```rust
// 符合
#[must_use]
fn foo1() -> i32 {
    // ...
    0
}

// 符合
#[must_use]
struct MyError(i32, i32);

fn foo2() -> MyError {
    // ...
    MyError(0, 0)
}
```

**【检测】** 部分支持

- `unused_must_use`（rustc，默认 warn）：调用方直接忽略 must_use 值。
- `clippy::let_underscore_must_use`（restriction）：用 `let _ =` 丢弃 must_use 值。
- `clippy::unused_result_ok`（restriction）：`.ok();` 丢弃 Result。
- `clippy::must_use_candidate`、`clippy::return_self_not_must_use`（pedantic）：从定义方提示缺失的 `#[must_use]`。
- 不覆盖：must_use 类型包在 Option 中返回。

## 泛型与 trait

### G.TRA.01 在实现相等性、排序和散列类 trait 时，应保证一致性

**【级别】** 要求

**【描述】**

在手动实现 Hash 和 PartialEq/Eq 时必须满足约束：当 k1 和 k2 相等时，hash(k1) 等于 hash(k2)。

在手动实现 PartialOrd 和 Ord 时必须满足约束： k1.cmp(&k2) 等于 k1.partial_cmp(&k2).unwrap()。

排序与相等性也必须保持一致：k1 == k2 当且仅当 k1.partial_cmp(&k2) == Some(Ordering::Equal)；实现了 Ord 时，即当且仅当 k1.cmp(&k2) == Ordering::Equal。同时实现 Ord 与 PartialOrd 时，宜将 partial_cmp 写为 `Some(self.cmp(other))`。

若类型实现了 Borrow trait，也应保证上述等式对借用后的类型同样成立，即：

- hash(k1) == hash(k2) 等效于 hash(k1.borrow()) == hash(k2.borrow())，且
- k1.borrow().cmp(&k2.borrow()) 等效于 k1.borrow().partial_cmp(&k2.borrow()).unwrap()。

通常情况下，可以通过 derive 属性宏来自动实现这些 traits。但相等性，排序和散列在不同应用场景可能存在不同的定义，又或是因为依赖的某种类型未实现其中一个 trait 而不能使用 derive 时，就需要开发者手动实现以上 traits，这时就要注意保持一致性。

一旦不一致，可能导致出现非预期的函数行为，例如 HashMap / HashSet 查找失败，BTreeMap / BTreeSet 把不相等的元素当作同一元素丢弃。

**【反例】**

```rust
// 不符合：雇员(Employee)类型包括 uid 及 name，通过宏自动实现的 Hash 会同时考虑所有成员变量，
// 但是手动实现的 PartialEq trait 仅考虑到了 uid，这将会导致结果不一致。
// 因为当两个雇员(假设为 a 和 b)的 name 不同，但 uid 相同时, a == b 为 true, 但 hash(a) 不等于 hash(b)
#[derive(Hash, Eq)]
struct Employee {
    uid: u32,
    name: String,
}

impl PartialEq for Employee {
    fn eq(&self, other: &Self) -> bool {
        self.uid == other.uid
    }
}
```

**【正例】**

```rust
// 符合：都使用 derive 自动实现
#[derive(Hash, PartialEq, Eq)]
struct Employee {
    uid: u32,
    name: String,
}
```

或

```rust
use std::hash::{Hash, Hasher};

#[derive(Eq)]
struct Employee {
    uid: u32,
    name: String,
}

// 符合：都使用手动实现的方式且保证一致性，
// 与 hash 一样都使用 uid 作为唯一条件
impl PartialEq for Employee {
    fn eq(&self, other: &Self) -> bool {
        self.uid == other.uid
    }
}

impl Hash for Employee {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.uid.hash(state)
    }
}
```

**【反例】**

```rust
use std::cmp::Ordering;

#[derive(Ord, PartialEq, Eq)]
struct Employee {
    uid: u32,
    name: String,
}

// 不符合：Ord 和 PartialOrd 的实现不一致
impl PartialOrd for Employee {
    fn partial_cmp(&self, other: &Employee) -> Option<Ordering> {
        Some(self.uid.cmp(&other.uid))
    }
}
```

```rust
use std::cmp::Ordering;

// 不符合：derive 的 PartialEq/Eq 比较全部字段，而 Ord 只比较 uid。
// uid 相同、name 不同时 a != b，但 a.cmp(&b) == Ordering::Equal，
// 放入 BTreeSet 时其中一个会被当作重复元素丢弃
#[derive(PartialEq, Eq)]
struct Employee {
    uid: u32,
    name: String,
}

impl PartialOrd for Employee {
    fn partial_cmp(&self, other: &Employee) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Ord for Employee {
    fn cmp(&self, other: &Self) -> Ordering {
        self.uid.cmp(&other.uid)
    }
}
```

**【正例】**

```rust
// 符合：都使用 derive 自动实现
#[derive(PartialOrd, Ord, PartialEq, Eq)]
struct Employee {
    uid: u32,
    name: String,
}
```

或

```rust
use std::cmp::Ordering;

#[derive(Eq)]
struct Employee {
    uid: u32,
    name: String,
}

// 符合：相等性与排序都只以 uid 为准，且 partial_cmp 复用 cmp
impl PartialEq for Employee {
    fn eq(&self, other: &Self) -> bool {
        self.uid == other.uid
    }
}

impl PartialOrd for Employee {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Ord for Employee {
    fn cmp(&self, other: &Self) -> Ordering {
        self.uid.cmp(&other.uid)
    }
}
```

**【检测】** 部分支持

- `clippy::derived_hash_with_manual_eq`（correctness）：derive(Hash) 与手写 PartialEq 混用。
- `clippy::derive_ord_xor_partial_ord`（correctness）：Ord 与 PartialOrd 一个 derive、一个手写。
- `clippy::non_canonical_partial_ord_impl`（suspicious）：同时实现 Ord 时，partial_cmp 未写为 `Some(self.cmp(other))`。
- `clippy::impl_hash_borrow_with_str_and_bytes`（correctness）：Borrow<str> 与 Borrow<[u8]> 并存时 Hash 不一致。
- 不覆盖：两边都手写但口径不一致；derive(PartialEq) 与手写 Ord 口径不一致。需配合单元测试校验。

### G.TRA.02 宜实现 From 而不是 Into

**【级别】** 建议

**【描述】**

优先为类型实现 From 而非 Into。因为实现了 From，Into 也会被自动实现。并且在错误处理的时候，`?` 操作符会通过调用 From 实现自动进行错误类型转换。
但是在泛型限定上，优先 Into 。

**【反例】**

```rust
struct StringWrapper(String);
// 不符合
impl Into<StringWrapper> for String {
    fn into(self) -> StringWrapper {
        StringWrapper(self)
    }
}
```

**【正例】**

```rust
struct StringWrapper(String);
// 符合
impl From<String> for StringWrapper {
    fn from(s: String) -> StringWrapper {
        StringWrapper(s)
    }
}
```

**【检测】** 完全支持

- `clippy::from_over_into`（style，默认 warn）。

## 错误处理

### G.ERR.01 应正确处理返回类型 Option 和 Result

**【级别】** 建议

**【描述】**

对于返回类型为 Option 或 Result 的函数，应使用不会导致 panic 的方法显式处理返回的 None / Err 值。

处理方法包括但不限于：

- 使用 match 语句。
- 使用 unwrap_or / unwrap_or_else / unwrap_or_default 等函数（传入的闭包本身不应 panic）。
- 在当前函数返回值同为Option或Result类型时，使用 `?` 语法糖。

例外：如下两种场景可直接调用 unwrap / expect，宜优先使用 expect 并在消息中说明为何不会失败：

- 调用返回 Option / Result 函数之前通过输入参数的提前校验，可以保证返回值一定不会是 None / Err。
- 业务模块的设计要求对于返回 None / Err 的情况 panic，依赖更高层的可靠性机制检测故障并实现故障恢复。

**【反例】**

```rust
use std::fs;

const CONFIG_PATH: &str = "/etc/app/config.toml";

pub fn main() {
    // 不符合：配置文件缺失或无权限时直接 panic，无法区分错误原因
    let config_content = fs::read_to_string(CONFIG_PATH).unwrap();
    // ...
}
```

**【正例】**

```rust
use std::fs;
use std::io::ErrorKind;

const CONFIG_PATH: &str = "/etc/app/config.toml";

pub fn main() {
    // 符合：针对不同情况做出应对措施，有利于定位错误
    let config_content = match fs::read_to_string(CONFIG_PATH) {
        Ok(content) => content,
        Err(e) => {
            match e.kind() {
                ErrorKind::NotFound => {
                    // 处理文件找不到的情况
                }
                ErrorKind::PermissionDenied => {
                    // 处理文件权限不够的情况
                }
                _ => {
                    // 处理其它错误情况
                }
            }
            return;
        }
    };

    // ...
}
```

**【检测】** 部分支持

- `clippy::unwrap_used`、`clippy::expect_used`（restriction，需显式开启）。
- 例外场景会被报告，用 `#[expect(clippy::unwrap_used, reason = "...")]` 局部豁免并写明理由。
- 测试代码默认也会报，宜在 clippy.toml 中设置 `allow-unwrap-in-tests = true`、`allow-expect-in-tests = true`。
- 不覆盖：`unwrap_or_else(|e| panic!(..))` 等等价写法，可开启 `clippy::panic`（restriction）兜底。

## 模块

### G.MOD.01 导入模块中的类型或函数时，应避免直接使用通配符

**【级别】** 建议

**【描述】**

使用通配符导入会污染命名空间，比如导入相同命名的函数或类型。为了避免这种情况，使用导入的类型或函数时需要带模块名前缀。有两个例外：当一个 crate 提供了 prelude 时，可以用 `prelude::*`；测试模块中可以用 `use super::*` 导入被测模块。

对于标准库中，很多人都熟知的类型 ，比如 Arc/ Rc/ Cell/ HashMap 等 ， 可以导入它们直接使用。

但是对于可能引起困惑的函数，比如 std::ptr::replace 和 std::mem::replace ，在使用它们的时候，就必须得带上模块前缀。

使用一些第三方库中定义的类型或函数，也建议带上 crate 或模块前缀。如果太长的话，可以考虑使用 as 或 type 来定义别名。

以上考虑都是为了增强代码的可读性、可维护性。

**【反例】**

```rust
use std::sync::Arc;
use std::ptr::*;

fn main() {
    let foo = Arc::new(vec![1.0, 2.0, 3.0]); // 直接使用 Arc
    let a = foo.clone();

    let mut rust = vec!['b', 'u', 's', 't'];

    let b = unsafe {
        // 不符合
        // 不知道 `replace` 是来自 `std::ptr` 还是 `std::mem` 模块
        replace(&mut rust[0], 'r')
    };
}
```

**【正例】**

```rust
use std::sync::Arc;
use std::ptr;

fn main() {
    let foo = Arc::new(vec![1.0, 2.0, 3.0]); // 直接使用 Arc
    let a = foo.clone();

    let mut rust = vec!['b', 'u', 's', 't'];

    let b = unsafe {
        // 符合
        // 需要带上 ptr 前缀，因为 `std::mem::replace` 也有同样的效果
        ptr::replace(&mut rust[0], 'r')
    };
}
```

**【检测】** 部分支持

- `clippy::wildcard_imports`（pedantic，需显式开启）：默认豁免 `prelude::*` 和 `pub use` 再导出，与本条例外一致。
- `clippy::enum_glob_use`（pedantic）：枚举变体的通配导入（`use Enum::*`），wildcard_imports 不报。
- 不覆盖：`cfg(test)` 编译时 wildcard_imports 整体跳过，测试模块内除 `use super::*` 以外的通配导入（如 `use std::collections::*`）也不报。

## 宏

### G.MAC.01 不应通过宏将 unsafe 代码伪装为 safe 代码

**【级别】** 要求

**【描述】**

不应通过宏将 unsafe 代码伪装为 safe 代码，以此来规避 Rust 静态分析检查。

尤其不应把调用方传入的代码（声明宏的元变量、过程宏的输入）直接展开在 unsafe 块内：调用方由此可以不写 unsafe 就执行不安全操作。应先在 unsafe 块外求值并绑定到局部变量，再在 unsafe 块内使用。

**【反例】**

```rust
// 不符合：用 Rust 的过程宏封装 libc 的函数 printf 来打印一个 C 字符串
// 这个宏的输入参数必须是一个有效的 C 字符串指针，整个宏的使用是不安全的，
// 但是因为过程宏中包括了 unsafe，导致调用过程宏 rprintf 被伪装为 safe 操作
//
// rprintf!(b"hello\0" as *const u8);

#[proc_macro]
pub fn rprintf(input: TokenStream) -> TokenStream {
    let expr = parse_macro_input!(input as syn::Expr);
    // 这里包括 unsafe 代码，这样整个宏可以在 safe 代码中使用
    quote!({
        unsafe {
            printf(b"%s\n\0" as *const _ as *const u8, #expr);
        }
    }).into()
}
```

**【正例】**

```rust
// 符合：用 Rust 的过程宏封装 libc 的函数 printf 来打印一个 C 字符串
// 这个宏的输入参数必须是一个有效的 C 字符串指针，同时也是调用外部函数，
// 因此必须在 unsafe 代码块中使用
//
// unsafe { rprintf!(b"hello\0" as *const u8) };

#[proc_macro]
pub fn rprintf(input: TokenStream) -> TokenStream {
    let expr = parse_macro_input!(input as syn::Expr);
    // 这里不能包括 unsafe 代码，而是要求整个宏在 unsafe 代码块中使用
    quote!({
        printf(b"%s\n\0" as *const _ as *const u8, #expr);
    }).into()
}
```

**【反例】**

```rust
// 定义声明宏，不经过任何安全检查，将 unsafe 函数伪装为 safe 函数
macro_rules! make_safe {
    ($safe_name:ident, $unsafe_fn:expr) => {
        fn $safe_name() {
            unsafe {
                $unsafe_fn();
            }
        }
    };
}

// 不安全函数，解引用空指针
unsafe fn dangerous_function() {
    let ptr: *const i32 = std::ptr::null();
    println!("value: {}", unsafe { *ptr }); // 解引用空指针，导致未定义行为
}

// 不符合：使用声明宏将 unsafe 函数伪装为 safe 函数
make_safe!(safe_function, dangerous_function);
```

**【例外】**

如果宏（或宏生成的函数）在执行 unsafe 操作前完整校验了它的全部前置条件，并用 `// SAFETY:` 注释说明理由，则可以对外提供 safe 接口：

```rust
macro_rules! checked_get {
    ($slice:expr, $idx:expr) => {{
        // 符合：元变量先在 unsafe 块外求值，调用方传入的表达式仍受正常的安全检查
        let slice: &[_] = $slice;
        let idx: usize = $idx;
        if idx < slice.len() {
            // SAFETY: 上一行已确认 idx < slice.len()，下标在界内
            Some(unsafe { *slice.get_unchecked(idx) })
        } else {
            None
        }
    }};
}
```

**【相关讨论】**

- [RUSTSEC-2020-0011](https://rustsec.org/advisories/RUSTSEC-2020-0011.html)
- [rustsec/advisory-db#275](https://github.com/rustsec/advisory-db/issues/275)
- [rust-lang/unsafe-code-guidelines#278](https://github.com/rust-lang/unsafe-code-guidelines/issues/278)

**【检测】** 部分支持

- `clippy::macro_metavars_in_unsafe`（suspicious，默认 warn）：声明宏的元变量在 unsafe 块内展开。默认只检查导出宏，需在 clippy.toml 中设置 `warn-unsafe-macro-metavars-in-private-macros = true`；只检查实际被调用过的宏。
- 可选 `clippy::undocumented_unsafe_blocks`（restriction）：要求 unsafe 块带 `// SAFETY:` 注释，便于评审。
- 不覆盖：过程宏生成的 unsafe 块；宏内写死的 unsafe 调用（不经过元变量）。

### P.MAC.DCL.01 定义和使用声明宏时，应保证卫生性

**【描述】**

标识符（包括变量、泛型、生命周期名称）建议作为宏的参数传递，而不是在宏定义时硬编码，这样可以在提升代码可维护性的同时，让宏的适用范围更广泛。

在宏内引用宏外部的 item，如函数或宏时应使用绝对路径：

- 当宏定义和宏内引用的 item 在同一个 crate 中定义时，应该使用 `$crate` 元变量来指代当前被调用宏的路径。
- 当宏内引用的 item 在其他 crate 中定义时，宜在宏所在的 crate 中再导出该 crate（如 `#[doc(hidden)] pub use dep as __dep;`），宏内通过 `$crate::__dep::item` 引用。直接写 `::dep::item` 要求调用方也直接依赖该 crate。

**【说明】**

声明宏是半卫生宏，变量标识符在宏内外是隔离的，不会产生命名冲突，符合卫生性。但是在宏内定义的泛型及生命周期标识符的做法是不卫生的。

卫生宏定义请参考 [卫生宏 Wiki](https://en.wikipedia.org/wiki/Hygienic_macro)。

**【反例】**

```rust
// 使用宏为带生命周期的类型实现 impl
macro_rules! impl_for {
    ($name:ty) => {
        // 不符合：这里使用的 'a 是宏内部定义
        impl<'a> $name {
            fn get(&self) -> i32 {
                *self.0
            }
        }
    };
}

struct Foo<'a>(&'a i32);
// 程序能正常编译运行，但宏内外的 'a 被共用，不卫生，也不利于可维护性
impl_for!(Foo<'a>);
// ...

struct Bar<'b>(&'b i32);
// 但如果要用相同的宏为生命周期为 'b 的类型实现 impl 时,
// 编译会失败: use of undeclared lifetime name 'b
impl_for!(Bar<'b>);
```

**【正例】**

```rust
// 使用宏为带生命周期的类型实现 impl
macro_rules! impl_for {
    // 符合：这里不直接使用宏内部定义的 'a ，而是通过 $lifetime 从外部传入的，
    // 从而避免因宏不卫生引发的问题
    ($name:ty, $lifetime:tt) => {
        impl<$lifetime> $name {
            fn get(&self) -> i32 {
                *self.0
            }
        }
    };
}

struct Foo<'a>(&'a i32);
impl_for!(Foo<'a>, 'a); // 这里的 'a 是从宏外部传入到宏内

struct Bar<'b>(&'b i32);
impl_for!(Bar<'b>, 'b); // 同时，宏的适用范围更加广泛
```

**【反例】**

```rust
// 宏定义在 crate a（包名 helper_macro）中
#[macro_export]
macro_rules! helped {
    () => { helper!() } // This might lead to an error due to 'helper' not being in scope.
}

#[macro_export]
macro_rules! helper {
    () => { () }
}

// 在 crate b 中使用 crate a 的两个宏
// 注意：helper_macro::helper 并没有导入进来
use helper_macro::helped;

fn unit() {
    // Error! 这个宏会出现问题，因为 helped 宏内部调用的 helper 宏的路径会被编译器认为是在当前的 crate b 中
    helped!();
}
```

**【正例】**

```rust
// 宏定义在 crate a（包名 helper_macro）中
#[macro_export]
macro_rules! helped {
    () => { $crate::helper!() }
}

#[macro_export]
macro_rules! helper {
    () => { () }
}

// 在crate b 中使用 crate a 的两个宏
// 注意：helper_macro::helper 并没有导入进来
use helper_macro::helped;

fn unit() {
    // OK! 这个宏能运行通过，因为 $crate 正确地展开成 helper_macro 所在的 crate a 的路径（而不是使用者 crate b 的路径）
    helped!();
}
```

**【检测】** 部分支持

- `clippy::crate_in_macro_def`（suspicious，默认 warn）：导出宏中误用 `crate::`，应改为 `$crate::`。
- 不覆盖：宏内使用裸路径（如 `helper!()`、`helper()`）；硬编码生命周期 / 泛型名。

### G.MAC.DCL.01 编写宏匹配规则时，宜遵从匹配范围从小至大的顺序

**【级别】** 建议

**【描述】**

因为声明宏中，是按规则的编写顺序来匹配的。当第一个规则被匹配到，后面的规则将永远不会匹配到。
所以，编写声明宏规则时，需要先写匹配范围最小的，最具体的规则，然后逐步编写匹配范围更广泛的规则。

参考 [The Little Book of Rust Macros](https://veykril.github.io/tlborm/)。

**【说明】**

规则顺序还会影响能否编译：如果前面的规则已经开始解析 `$e:expr` 等片段，而解析失败（如 `m!(1 +)`），编译器会直接报错，不会再尝试后面的规则。

**【反例】**

```rust
// 不符合：$($other:tt)* 匹配条件在这个宏定义中匹配范围最大却放在了第一位。
macro_rules! match_tokens {
    // 可能会导致调用时代码被错误地匹配到了这一条规则。
    ($($other:tt)*) => {"got something else"};

    ($a:tt + $b:tt) => {"got an addition"};

    ($i:ident) => {"got an identifier"};
}

// 以下的三种语法：caravan, 3 + 6, 5 均被匹配为该宏的同一条规则
assert_eq!(
    format!("{},{},{}",
        match_tokens!(caravan),
        match_tokens!(3 + 6),
        match_tokens!(5)
    ),
    "got something else,got something else,got something else"
);
```

**【正例】**

```rust
// 符合：匹配范围从小到大
macro_rules! match_tokens {
    ($a:tt + $b:tt) => {"got an addition"};

    ($i:ident) => {"got an identifier"};

    ($($other:tt)*) => {"got something else"};
}

// 匹配合理，宏将 caravan 识别为 identifier, 3 + 6 识别为 addition, 5 识别为 something else
assert_eq!(
    format!("{},{},{}",
        match_tokens!(caravan),
        match_tokens!(3 + 6),
        match_tokens!(5)
    ),
    "got an identifier,got an addition,got something else"
);
```

**【检测】** 不支持

rustc / Clippy 不提示被前序规则遮蔽的宏规则，需人工评审。

### P.MAC.PRO.01 定义和使用过程宏时，应保证卫生性

**【描述】**

过程宏在展开时，有时可能会直接引用输入代码中的标识符（变量、函数名等）。如果过程宏引入了与周围代码冲突的标识符，就会导致不卫生的情况。

要避免不卫生的情况，包括以下常用方法：

- 宏内部使用的局部变量，用 `Span::mixed_site()` 生成标识符（如 `quote_spanned!(Span::mixed_site()=> ...)`），获得与声明宏相同的局部变量卫生性。
- 无法使用 `mixed_site` 时，确保宏生成代码的符号与外部有差异，如增加 `__` 前缀。
- 对库中程序项使用绝对路径。

**【反例】**

```rust
// crate guide
#[proc_macro]
pub fn my_macro(input: TokenStream) -> TokenStream {
    let expanded = quote! {
        // 不符合：直接使用外部的变量 x
        x = 999;
        // 不符合: 宏内定义的变量 local 被外部使用
        let local = "hello";

        // ...
    };
    expanded.into()
}

// crate b
fn main() {
    let mut x = 0;
    let local = "";

    guide::my_macro!();

    assert_eq!(x, 999);
    assert_eq!(local, "hello");
}
```

**【正例】**

```rust
use proc_macro2::Span;
use quote::quote_spanned;

#[proc_macro]
pub fn my_macro(input: TokenStream) -> TokenStream {
    let expanded = quote_spanned! {Span::mixed_site()=>
        // 符合：mixed_site 生成的局部变量对调用方不可见，也不会遮蔽调用方的同名变量
        let local = "hello";

        // ...
    };
    expanded.into()
}
```

**【正例】**

```rust
#[proc_macro]
pub fn my_macro(input: TokenStream) -> TokenStream {
    let expanded = quote! {
        // 符合：宏内变量增加 __ 前缀
        let __x = 0;
        let __local = "hello";

        // ...
    };
    expanded.into()
}
```

**【正例】**

过程宏生成的代码宜使用绝对路径，防止命名冲突产生意想不到的后果。

可以配合使用 `#![no_implicit_prelude]` 属性来验证标识符是否都使用了绝对路径：

```rust
#![no_implicit_prelude]

#[derive(MyMacro)]
struct A;
```

```rust
// 符合：使用绝对路径
quote!(::std::string::ToString::to_string(a))
```

```rust
quote! {{
    // 符合：使用绝对路径
    use ::std::string::ToString;
    a.to_string()
}}
```

**【检测】** 不支持

rustc / Clippy 无相应 lint。可在测试 crate 中用 `#![no_implicit_prelude]` 验证生成代码是否使用绝对路径。
