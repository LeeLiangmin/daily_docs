## G.CTF.01 宜优先使用模式匹配而非判断后再取值

分类：表达式与流程控制

### 文本调整

**1. 反例代码：修正类型错误**

```diff
- let list: &[f32] = vec![1.23];
+ let list: &[f32] = &[1.23];
```

理由：原示例无法编译（E0308：`Vec<f32>` 不能赋给 `&[f32]`），读者照抄会先撞上编译错误。

依据：POC G.CTF.01-04

**2. 正例注释：说明 index 来源**

```diff
- // 符合
+ // 符合：index 为任意 usize 下标
```

理由：原示例中 `index` 没有定义也没有说明，读者无法判断示例是否完整。

依据：POC G.CTF.01-05

### 定级

维持「建议」。属于惯用法与可读性改进，不构成独立的正确性风险。

### lint

```diff
- （无）
+ clippy::unnecessary_unwrap
```

检测能力：**部分支持**

理由：

- 原文没有配置 lint；`unnecessary_unwrap` 默认开启（complexity，warn），能检出第一个反例（判断后 unwrap）。
- 第二个反例（判空后下标取值）没有 lint 能覆盖，所以是部分支持。

### 补充说明

1. `clippy::unnecessary_unwrap`（complexity，默认 warn）：检查先用 `is_some()` / `is_ok()` 判断、再调用 `unwrap()` 的写法。

   ```rust
   if opt.is_some() {
       let value = opt.unwrap();   // 报警：called `unwrap` on `opt` after checking its variant with `is_some`
   }
   ```

### 漏报、误报风险

漏报：

1. 切片判空后用下标取值，全量 lint（all + pedantic + nursery）均不报（POC G.CTF.01-02）：

   ```rust
   pub fn demo(list: &[f32]) -> f32 {
       if !list.is_empty() {
           let first = list[0];   // 不报
           return first;
       }
       0.0
   }
   ```

   restriction 组的 `clippy::indexing_slicing` 会报，但它对所有下标访问都报，不区分是否已判空，不适合用于本条。

2. 1.89 只识别局部变量，对结构体字段先判断后 unwrap 不报；1.97 起可以检出（POC G.CTF.01-03）：

   ```rust
   impl Cfg {
       pub fn get(&self) -> i32 {
           if self.v.is_some() { self.v.unwrap() } else { 0 }   // 1.89 不报
       }
   }
   ```

### POC

门禁 PoC（bot-gate-lab）：

- `cases/clippy/unnecessary-unwrap`：`clippy::unnecessary_unwrap` 命中 1 次

学习用例（playground）：`cases/guideline/g-ctf-01/`，共 5 个：G.CTF.01-01、G.CTF.01-02、G.CTF.01-03、G.CTF.01-04、G.CTF.01-05

## G.CTF.02 在 Match 分支的 Guard 语句中不宜使用带有副作用的条件表达式

分类：表达式与流程控制

### 文本调整

**1. 描述：点明多次执行的前提**

```diff
- 在 match 分支中，匹配几次就会执行 Guard 几次。Guard 的条件表达式不应该携带副作用。
+ Guard 的条件表达式不应该携带副作用。当分支使用 `|` 组合多个模式时，Guard 会针对每个
+ 匹配成功的子模式各执行一次，直到某次返回 true 为止，因此同一个 Guard 可能被执行多次。
```

理由：原句没有说明前提，容易理解成「所有 Guard 都会重复执行」。实测去掉 `|` 后 Guard 只执行 1 次，多次执行只来自或模式：

```rust
Some(1) | Some(_) if condition(&i) => {}   // condition 执行 2 次
Some(_) if condition(&i) => {}             // condition 执行 1 次
```

依据：POC G.CTF.02-01 / 02

**2. 反例注释：与新描述对应**

```diff
- // 这个条件表达式带有副作用：打印并修改了变量 i 内部的值，因为匹配两次，所以会执行两次
+ // 这个条件表达式带有副作用：打印并修改了变量 i 内部的值。
+ // Some(1) 与 Some(_) 两个子模式都匹配，Guard 返回 false，因此执行两次
```

理由：让读者从注释直接看出执行两次的原因。

### 定级

维持「建议」。风险只出现在「或模式 + 副作用」的组合下，且没有 lint 可检测。

### lint

无变化。

检测能力：**不支持**

理由：

- rustc / Clippy 都没有相应 lint，全量 lint 下原文反例零告警。

### 补充说明

无。

### 漏报、误报风险

没有对应 lint，全部依赖人工评审。原文反例在 all + pedantic + nursery 下只有一条与副作用无关的 `clippy::unnested_or_patterns`（建议把 `Some(1) | Some(_)` 写成 `Some(1 | _)`）。

### POC

门禁 PoC（bot-gate-lab）：

- 无（没有对应 lint）

学习用例（playground）：`cases/guideline/g-ctf-02/`，共 2 个：G.CTF.02-01、G.CTF.02-02

## G.CTF.03 循环或递归必须安全退出

分类：表达式与流程控制

### 文本调整

**1. 标题：去掉「必须」**

```diff
- 循环或递归必须安全退出
+ 宜确保循环或递归能够安全退出
```

理由：本条级别是「建议」，标题用「必须」，两者矛盾。

**2. 描述：给常驻循环合规写法，明确什么不算安全退出**

```diff
- 循环必须安全退出，递归也必须安全结束。
+ 循环应能安全退出，递归也应能安全结束。
+ - 有意常驻、不会返回的循环（如服务主循环），应将所在函数的返回类型声明为 `!`，明确表达意图；
+   需要支持停机时，应提供退出信号（如关闭标志、通道关闭）并在退出前释放资源。
+ - `panic!`、`std::process::exit` 不属于安全退出：后者不会执行栈上对象的析构（Drop）。
```

理由：

- 服务主循环、工作线程是正常设计，原文没给合规写法，这类代码按字面无法合规。`-> !` 正是 `clippy::infinite_loop` 认可的豁免方式。
- 原文要求「将资源正确释放后安全退出」，`process::exit` 不执行 Drop，与此相悖；而 lint 恰好把 panic / exit 当作出口，需要规范写明。

依据：POC G.CTF.03-02 / 03

**3. 新增递归反例**

```diff
+ // 不符合：递归没有终止条件
+ fn depth(n: u64) -> u64 {
+     depth(n + 1)
+ }
```

理由：标题含「递归」，原文却只有循环的示例。

依据：POC G.CTF.03-06

**4. 新增常驻循环正例**

```diff
+ // 符合：有意常驻的服务循环，用 `!` 返回类型显式声明不会返回
+ fn serve(listener: std::net::TcpListener) -> ! {
+     loop {
+         if let Ok((stream, _)) = listener.accept() {
+             handle(stream);
+         }
+     }
+ }
```

理由：对应第 2 条，给出可以照写的合规形式。

**5. 删除重复正例**

```diff
- fn main() { ... }      // 第二份重复的正例
- fn should_exit(...) { ... }
```

理由：格式问题，同一段正例出现了两次。

### 定级

维持「建议」。常驻循环在服务、嵌入式场景是正常设计，是否需要退出路径依赖业务判断。

### lint

```diff
- infinite_loop
+ clippy::infinite_loop
+ clippy::while_immutable_condition
+ unconditional_recursion
```

检测能力：**部分支持**

理由：

- 原写法缺 `clippy::` 前缀，不是合法 lint 名，写进配置会被当作未知 lint。
- `infinite_loop` 只查 `loop`；`while` 形式的死循环靠 `while_immutable_condition`（POC G.CTF.03-05）。
- 标题含「递归」，补 rustc 的 `unconditional_recursion`（默认开启，POC G.CTF.03-06）。

### 补充说明

1. `clippy::infinite_loop`（restriction，需显式开启）：检查没有 `break`、`return` 等退出路径的 `loop`。函数返回类型为 `!` 时豁免。

   ```rust
   pub fn run() {
       loop {              // 报警：infinite loop detected
           work();
       }
   }

   pub fn serve() -> ! {
       loop {              // 不报：已用 `-> !` 声明有意常驻
           work();
       }
   }
   ```

2. `clippy::while_immutable_condition`（correctness，默认 deny）：检查 `while` 条件依赖的变量在循环体中从不改变，循环要么一次不进，要么永不退出。

   ```rust
   pub fn wait(ready: bool) {
       while !ready {      // 报警：ready 在循环体内不会变化
           std::hint::black_box(0);
       }
   }
   ```

3. `unconditional_recursion`（rustc，默认 warn）：检查所有执行路径都会递归调用自身、无法正常返回的函数。

   ```rust
   pub fn depth(n: u64) -> u64 {
       depth(n + 1)        // 报警：function cannot return without recursing
   }
   ```

### 漏报、误报风险

漏报：

1. `infinite_loop` 把任何返回 `!` 的调用都当作出口，包括 `panic!` 和 `process::exit`。以 panic 作为唯一出口的循环不报，但这不是本条要求的安全退出（POC G.CTF.03-03）：

   ```rust
   pub fn run(limit: u32) {
       let mut counter = 0u32;
       loop {                       // 不报
           counter += 1;
           if counter > limit {
               panic!("overflow");
           }
       }
   }
   ```

2. 递归只要有语法上的终止分支就不报，即使该分支实际到达不了（POC G.CTF.03-07）：

   ```rust
   pub fn depth(n: u64) -> u64 {
       if n == 0 { 0 } else { depth(n + 1) }   // n > 0 时永不终止，但不报
   }
   ```

误报：

1. 1.89 中，未 await 的 `async` 块里的常驻循环会被 `infinite_loop` 误报（1.97 已修复，POC G.CTF.03-04）。常见于 `spawn(async { loop { .. } })` 形式的后台任务，需要局部 `#[allow(clippy::infinite_loop, reason = "...")]`：

   ```rust
   pub fn start() -> impl std::future::Future<Output = ()> {
       async {
           loop {                   // 1.89 报警，1.97 不报
               std::hint::black_box(0);
           }
       }
   }
   ```

### POC

门禁 PoC（bot-gate-lab）：

- `cases/clippy/infinite-loop`：`clippy::infinite_loop` 命中 1 次
  - `pass/never-return`（边界）：函数返回类型为 `!` 时豁免，与规范「有意常驻的循环声明为 `-> !`」一致。
  - `pass/panic-exit`（漏报）：以 panic 为唯一出口的循环被视为可退出，但不属于规范要求的安全退出。
- `cases/clippy/while-immutable-condition`：`clippy::while_immutable_condition` 命中 1 次
- `cases/rustc/unconditional-recursion`：`unconditional_recursion` 命中 1 次
  - `pass/unreachable-base`（漏报）：n > 0 时永不终止，但存在终止分支，不报。

学习用例（playground）：`cases/guideline/g-ctf-03/`，共 7 个：G.CTF.03-01、G.CTF.03-02、G.CTF.03-03、G.CTF.03-04、G.CTF.03-05、G.CTF.03-06、G.CTF.03-07

## G.EXP.01 避免复合条件表达式永远为 true 或 false

分类：表达式与流程控制

### 文本调整

**1. 标题：删除「复合」**

```diff
- 避免复合条件表达式永远为 true 或 false
+ 避免条件表达式永远为 true 或 false
```

理由：

- 原文三个反例中，`(x & 1) == 2`、`(x & 3) < 4` 都只有一个比较，不是复合条件，标题与示例不一致。
- 最常见的恒值条件是单个比较，如 `u32 >= 0`、`x == x`，按字面却不在本条范围内。
- 对应 lint 不区分是否复合；本条升为「要求」后，范围不一致会引发「算不算复合」的争议。

**2. 新增反例：区间矛盾**

```diff
+ if x > 10 && x < 5 { // 不符合：区间矛盾，永远为 false
+     // ...
+ }
```

理由：最常见的恒假写法之一，原文没有覆盖；对应新增的 `impossible_comparisons`。

依据：POC G.EXP.01-02

**3. 新增【例外】**

```diff
+ 【例外】
+ 掩码或阈值来自构建配置生成的常量、在某些配置下恰好使表达式恒值时，
+ 可局部 `#[allow(...)]` 并注明原因。
```

理由：升为「要求」后 lint 会作为门禁，而用构建配置生成掩码是正常写法，在某些配置下 lint 会报（见下文误报风险）。

依据：POC G.EXP.01-04

### 定级

建议 → 要求。理由：

- 恒真 / 恒假的条件几乎没有正当用途，属于缺陷而不是风格问题；
- 1.89 中对应的 Clippy lint 全部属于 correctness 组、默认 deny，现有代码在默认配置下已经会被拦截，升级不增加整改成本；
- 唯一的意图正常场景（配置常量导致恒值）由【例外】处理。

### lint

```diff
- clippy::bad_bit_mask
+ clippy::bad_bit_mask
+ clippy::overly_complex_bool_expr
+ clippy::impossible_comparisons
+ clippy::absurd_extreme_comparisons
+ unused_comparisons
+ clippy::eq_op
```

检测能力：**部分支持**

理由：

- `bad_bit_mask` 只覆盖前两个反例；第三个 `(x < y) && false` 需要 `overly_complex_bool_expr`（POC G.EXP.01-01）。
- 其余几个覆盖区间矛盾、类型极值比较、自比较，同属恒真 / 恒假（POC G.EXP.01-02）。
- 1.89 中这些都是 correctness 组（`unused_comparisons` 默认 warn），开启几乎不增加整改成本。

### 补充说明

1. `clippy::bad_bit_mask`（correctness）：检查掩码和比较值不相容、导致条件恒真或恒假的位运算比较。

   ```rust
   if (x & 1) == 2 { }   // 报警：incompatible bit mask: `_ & 1` can never be equal to `2`
   if (x & 3) < 4 { }    // 报警：`_ & 3` will always be lower than `4`
   ```

2. `clippy::overly_complex_bool_expr`（1.89 为 correctness；1.97 降为 pedantic，升级工具链后需显式开启）：检查布尔表达式中可以直接消去的项。

   ```rust
   if (x < y) && false { }   // 报警：this boolean expression contains a logic bug
   ```

3. `clippy::impossible_comparisons`（correctness）：检查同一变量的多个比较组合后不可能同时成立。

   ```rust
   if x > 10 && x < 5 { }   // 报警
   ```

4. `clippy::absurd_extreme_comparisons`（correctness）与 `unused_comparisons`（rustc，默认 warn）：检查与类型最小值或最大值的无意义比较。

   ```rust
   let x: u32 = get();
   if x >= 0 { }   // 报警：无符号数恒 >= 0
   ```

5. `clippy::eq_op`（correctness）：检查比较或运算两侧是同一表达式。

   ```rust
   if x == x { }   // 报警
   ```

### 漏报、误报风险

漏报：取模的值域、用 `||` 连接的 `!=` 等恒值写法，全量 lint 均不报（POC G.EXP.01-03）：

```rust
pub fn demo(x: u32) -> u32 {
    let mut n = 0;
    if x % 2 == 2 { n += 1; }        // 恒为 false：x % 2 只能是 0 或 1
    if x != 1 || x != 2 { n += 1; }  // 恒为 true：本意通常是 &&
    n
}
```

误报风险：掩码来自构建配置生成的常量，在某些构建下为 0 时，`bad_bit_mask` 报警（POC G.EXP.01-04）。在该构建下表达式确实恒假，lint 说的是事实，但代码意图正常。升级为「要求」后会卡住门禁，需按【例外】处理：

```rust
const TRACE_MASK: u32 = 0; // 由构建配置生成，关闭 trace 时为 0

#[allow(clippy::bad_bit_mask, reason = "TRACE_MASK 由构建配置生成，关闭 trace 时为 0")]
pub fn traced(flags: u32) -> bool {
    flags & TRACE_MASK != 0   // 不加 allow 时报警：&-masking with zero
}
```

### POC

门禁 PoC（bot-gate-lab）：

- `cases/clippy/absurd-extreme-comparisons`：`clippy::absurd_extreme_comparisons` 命中 1 次
- `cases/clippy/bad-bit-mask`：`clippy::bad_bit_mask` 命中 2 次
- `cases/clippy/eq-op`：`clippy::eq_op` 命中 1 次
- `cases/clippy/impossible-comparisons`：`clippy::impossible_comparisons` 命中 1 次
- `cases/clippy/overly-complex-bool-expr`：`clippy::overly_complex_bool_expr` 命中 1 次
- `cases/rustc/unused-comparisons`：`unused_comparisons` 命中 1 次

学习用例（playground）：`cases/guideline/g-exp-01/`，共 4 个：G.EXP.01-01、G.EXP.01-02、G.EXP.01-03、G.EXP.01-04

## G.EXP.02 用括号明确表达式的操作顺序，避免过分依赖默认优先级

分类：表达式与流程控制

### 文本调整

无。描述与示例准确，正文不改。

### 定级

维持「建议」。可读性规则。

### lint

```diff
- clippy::precedence
+ clippy::precedence
+ ambiguous_negative_literals
+ clippy::precedence_bits
```

检测能力：**部分支持**

理由：

- 第二个反例 `-1i32.abs()` 在 1.89 已不归 `precedence` 检查（实测 0 条），要用 rustc 的 `ambiguous_negative_literals`（POC G.EXP.02-02）。
- 1.86 起「位运算 + 移位」拆到了 `precedence_bits`，只开 `precedence` 会漏（POC G.EXP.02-03）。

### 补充说明

1. `clippy::precedence`（complexity，默认 warn）：检查算术运算与位移 / 位运算混用但缺少括号的表达式。

   ```rust

   ```

2. `ambiguous_negative_literals`（rustc 自带，默认 allow，需显式开启）：检查负号字面量后接方法调用的写法。方法调用的优先级高于一元负号，`-1i32.abs()` 的结果是 -1。


3. `clippy::precedence_bits`（restriction，1.86 起）：检查位运算与移位混用时缺少括号的表达式。1.86 起这类情况从 `precedence` 拆出，只开 `precedence` 不会报（POC G.EXP.02-03）。



分类：函数与闭包

### 文本调整

**1. 描述首句：修正拷贝的说法**

```diff

+ Rust 中按值传递参数（包括所有权转移）时，语义上会按位拷贝该类型自身大小的内存，不包括其指向的堆数据；
```

```diff
+ - 对于输入参数，拷贝代价小的类型使用值传递，拷贝代价大的类型传递只读引用。类型大小可通过
+   `std::mem::size_of::<T>()` 获取，超过 256 字节的类型可视为拷贝代价大。
```

## G.TRA.01 在实现相等性、排序和散列类 trait 时，应保证一致性

分类：泛型与 trait

### 文本调整

**1. 描述：补充排序与相等性的一致性约束**

```diff
+ 排序与相等性也必须保持一致：k1 == k2 当且仅当 k1.partial_cmp(&k2) == Some(Ordering::Equal)；
+ 实现了 Ord 时，即当且仅当 k1.cmp(&k2) == Ordering::Equal。
+ 同时实现 Ord 与 PartialOrd 时，宜将 partial_cmp 写为 `Some(self.cmp(other))`。
```

理由：

- 这是 std 文档对 PartialOrd / Ord 的要求，原文漏了。
- 正因为漏了，原文第二组 Ord「正例」实际不合规（见第 2 条）。

**2. 原 Ord「正例」改为反例**

```diff
- // 符合：都使用手动实现的方式且保证一致性
- #[derive(PartialEq, Eq)]
- struct Employee { uid: u32, name: String }
- impl Ord for Employee {
-     fn cmp(&self, other: &Self) -> Ordering { self.uid.cmp(&other.uid) }
- }
+ // 不符合：derive 的 PartialEq/Eq 比较全部字段，而 Ord 只比较 uid
+ #[derive(PartialEq, Eq)]
+ struct Employee { uid: u32, name: String }
+ impl Ord for Employee {
+     fn cmp(&self, other: &Self) -> Ordering { self.uid.cmp(&other.uid) }
+ }
```

理由：uid 相同、name 不同时，`a == b` 为 false，`a.cmp(&b)` 却是 `Equal`。实测放进 `BTreeSet` 后丢了一个元素：

```text
eq=false cmp=Equal
btreeset_len=1
```

依据：POC G.TRA.01-03

**3. 新增正确的 Ord 正例**

```diff
+ #[derive(Eq)]
+ struct Employee { uid: u32, name: String }
+
+ // 符合：相等性与排序都只以 uid 为准，且 partial_cmp 复用 cmp
+ impl PartialEq for Employee {
+     fn eq(&self, other: &Self) -> bool { self.uid == other.uid }
+ }
+ impl PartialOrd for Employee {
+     fn partial_cmp(&self, other: &Self) -> Option<Ordering> { Some(self.cmp(other)) }
+ }
+ impl Ord for Employee {
+     fn cmp(&self, other: &Self) -> Ordering { self.uid.cmp(&other.uid) }
+ }
```

理由：第 2 条把原正例改成了反例，需要给出正确写法；实测 `a == b` 与 `cmp` 结果一致，相关 lint 零告警。

依据：POC G.TRA.01-05

**4. 示例补导入**

```diff
+ use std::cmp::Ordering;
```

理由：原示例用了 `Ordering` 却没导入，无法编译。

**5. 后果描述具体化**

```diff
- 一旦不一致，可能导致出现非预期的函数行为。
+ 一旦不一致，可能导致出现非预期的函数行为，例如 HashMap / HashSet 查找失败，
+ BTreeMap / BTreeSet 把不相等的元素当作同一元素丢弃。
```

理由：「非预期的函数行为」太笼统；写出具体后果，读者能理解为什么是「要求」。

依据：POC G.TRA.01-03 / 04

**6. 删除重复正例**

```diff
- #[derive(PartialEq, Eq)] struct Employee ...   // 第二份重复的正例
```

理由：格式问题，同一段正例出现了两次。

### 定级

维持「要求」。违反约束会导致标准容器行为错误（实测 BTreeSet 丢元素），属于正确性问题。

### lint

```diff

- clippy::derived_hash_with_manual_eq
```

**3. 正例补齐导入与常量**

```diff

+ use std::io::ErrorKind;
+

```

理由：原正例用了 `fs` 和 `CONFIG_PATH` 却没导入、没定义，无法编译。


理由：原条款只有正例；反例与正例读同一个文件，放在一起能看出分别处理 NotFound / PermissionDenied 的区别。

### 定级

维持「建议」。条款本身允许「设计上要求 panic」的例外，适用面依赖业务。

### lint

```diff

+ clippy::unwrap_used
+ clippy::expect_used
+ clippy::panic          # 可选
```

检测能力：**部分支持**

理由：

- 条款覆盖 unwrap 和 expect，`unwrap_used` 只查 unwrap（POC G.ERR.01-02）。

3. `clippy::panic`（restriction）：检查生产代码中的 `panic!`，可兜底 `unwrap_or_else(|e| panic!(..))` 这类写法。

漏报：

1. `expect()`：只开 `unwrap_used` 时不报。
2. `unwrap_or_else(|e| panic!(..))`：`unwrap_used` 和 `expect_used` 都不报，需 `clippy::panic`（POC G.ERR.01-03）。

## G.MAC.01 不应通过宏将 unsafe 代码伪装为 safe 代码

分类：宏

### 文本调整

**1. 描述：点明问题本质和改法**

```diff
+ 尤其不应把调用方传入的代码（声明宏的元变量、过程宏的输入）直接展开在 unsafe 块内：
+ 调用方由此可以不写 unsafe 就执行不安全操作。应先在 unsafe 块外求值并绑定到局部变量，
+ 再在 unsafe 块内使用。
```

理由：原文只说「不应伪装」，没说怎样算伪装、该怎么改。两个反例的共同问题都是调用方代码被放进 unsafe 块：

```rust
($e:expr) => { unsafe { $e } };               // 不符合：调用方写 bad!(*ptr) 不需要 unsafe
($e:expr) => {{ let v = $e; unsafe { /*v*/ } }}; // 符合：$e 在块外求值，仍受安全检查
```

`clippy::macro_metavars_in_unsafe` 也按这个原理检测。

**2. 【例外】示例重写**

```diff
- // 安全函数，解引用指针前进行了校验
- unsafe fn safe_function() {
-     let ptr: *const i32 = std::ptr::null();
-     if !ptr.is_null() {
-         println!("value: {}", *ptr);
-     }
- }
+ macro_rules! checked_get {
+     ($slice:expr, $idx:expr) => {{
+         // 符合：元变量先在 unsafe 块外求值
+         let slice: &[_] = $slice;
+         let idx: usize = $idx;
+         if idx < slice.len() {
+             // SAFETY: 上一行已确认 idx < slice.len()，下标在界内
+             Some(unsafe { *slice.get_unchecked(idx) })
+         } else {
+             None
+         }
+     }};
+ }
```

理由：

- 注释说「安全函数」，却声明为 `unsafe fn`，自相矛盾。
- 指针恒为 null，校验分支是死代码，演示不了「校验后安全」。
- 只判空不能保证指针有效（悬垂、未对齐同样是 UB），作为「保证安全」的范例会误导。
- 2024 版次下 unsafe fn 体内的不安全操作必须放进 unsafe 块，实测告警 E0133（POC G.MAC.01-05）。

依据：新示例开启私有宏检查后零告警，运行正确（POC G.MAC.01-06）

**3. 反例中的解引用放进 unsafe 块**

```diff
- println!("value: {}", *ptr);
+ println!("value: {}", unsafe { *ptr });
```

理由：原写法在 2024 版次下有额外告警，干扰读者关注反例本身的问题。

**4. 相关讨论补链接**

```diff
- RUSTSEC-2020-0011
- rustsec/advisory-db#275
- rust-lang/unsafe-code-guidelines#278
+ [RUSTSEC-2020-0011](https://rustsec.org/advisories/RUSTSEC-2020-0011.html)
+ [rustsec/advisory-db#275](https://github.com/rustsec/advisory-db/issues/275)
+ [rust-lang/unsafe-code-guidelines#278](https://github.com/rust-lang/unsafe-code-guidelines/issues/278)
```

理由：原文只有编号。RUSTSEC-2020-0011 是 plutonium crate（专门用宏隐藏 unsafe），是本条最直接的真实案例。

### 定级

维持「要求」。属于健全性问题。

### lint

```diff
- unsafe_block_in_proc_macro
+ clippy::macro_metavars_in_unsafe       # clippy.toml: warn-unsafe-macro-metavars-in-private-macros = true
+ clippy::undocumented_unsafe_blocks     # 可选
```

检测能力：**部分支持**

理由：

- 原 lint 在 1.89 的 rustc 与 Clippy 源码中都检索不到，不存在，配了也不生效。
- `macro_metavars_in_unsafe` 检查的正是文本调整第 1 条的问题；默认只查导出宏，原文 `make_safe!` 是私有宏，不加配置不报（POC G.MAC.01-01 / 02）。
- `undocumented_unsafe_blocks` 要求 `// SAFETY:` 注释，对应【例外】「写明理由」；它查所有 unsafe 块，范围比本条大，所以可选。

### 补充说明

1. `clippy::macro_metavars_in_unsafe`（suspicious，默认 warn，1.80 起）：检查声明宏的元变量是否在 unsafe 块内展开。默认只检查导出宏（`#[macro_export]`）；原文 `make_safe!` 是私有宏，需要打开上面的配置才会报（POC G.MAC.01-01 / 02）。

   ```rust

       ($safe_name:ident, $unsafe_fn:expr) => {
           pub fn $safe_name() {
               unsafe { $unsafe_fn(); }   // 开启私有宏检查后报警：this macro expands metavariables in an unsafe block
           }
       };
   }
   ```

2. `clippy::undocumented_unsafe_blocks`（restriction）：要求每个 unsafe 块带 `// SAFETY:` 注释，便于评审核对前置条件。

### 漏报、误报风险

漏报：

1. 私有宏默认不检查（需配置，见上）。
2. 只检查实际被调用过的宏。定义了但没有调用的宏不报，因为 lint 检查的是宏展开结果。
3. 宏内写死的 unsafe 调用不经过元变量，同样是伪装，但不报（POC G.MAC.01-03）：

   ```rust

   macro_rules! expose {
       ($name:ident) => {
           pub fn $name() -> i32 {
               unsafe { dangerous_function() }   // 不报
           }
       };
   }
   ```

4. 过程宏完全不覆盖。与原文过程宏反例同构的写法，编译、运行均通过且零告警（POC G.MAC.01-04）：

   ```rust
   // 过程宏：把调用方的表达式放进 unsafe 块
   #[proc_macro]
   pub fn run_unchecked(input: TokenStream) -> TokenStream {
       format!("{{ unsafe {{ {input} }} }}").parse().unwrap()
   }

   // 调用方没有写 unsafe，却执行了 unsafe fn，不报
   let got = rmacro::run_unchecked!(read_raw(p));
   ```

   过程宏只能靠评审，可要求过程宏 crate 的生成代码中出现 `unsafe` 时必须经过安全评审。

## P.MAC.PRO.01 定义和使用过程宏时，应保证卫生性

分类：宏

### 文本调整

**1. 方法列表：新增 Span::mixed_site() 并列为首选**

```diff
- - 确保宏生成代码的符号与外部有差异，如增加 `__` 前缀。
- - 对库中程序项使用绝对路径。
+ - 宏内部使用的局部变量，用 `Span::mixed_site()` 生成标识符
+   （如 `quote_spanned!(Span::mixed_site()=> ...)`），获得与声明宏相同的局部变量卫生性。
+ - 无法使用 `mixed_site` 时，确保宏生成代码的符号与外部有差异，如增加 `__` 前缀。
+ - 对库中程序项使用绝对路径。
```

理由：

- `__` 前缀只是降低冲突概率；调用方也用了 `__x`，或两个宏用了同一前缀名，仍会冲突。
- `Span::mixed_site()`（1.45 起稳定）由编译器保证隔离。实测同一个调用方：`quote!` 生成时输出 `x=999 local="hello"`（宏改写了调用方变量），`mixed_site` 生成时输出 `local=""`（互不可见）。

依据：POC P.MAC.PRO.01-01 / 02
