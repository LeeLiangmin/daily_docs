## 1 概述

Bot Analyzer 是一个 VS Code 插件，把 bot-metric 的 Rust 代码度量放到代码旁边，回答三个问题：当前文件哪些函数要改；整个项目能不能过门禁、问题落在哪些模块；某一段代码（函数、impl、类型）怎么样。

| 入口 | 回答什么 |
| --- | --- |
| 侧栏「当前文件」 | 这个文件的问题、全部函数、度量 |
| 侧栏「整个项目」 | 规模、门禁结论与原因、问题全表、质量目标、函数与度量 |
| 状态栏左边 | 整个项目能不能过门禁，问题总数 |
| 状态栏右边 | 当前文件有几条问题 |
| 编辑器 | 波浪线、悬停、CodeLens、快速修复、重复代码竖线 |
| 右键「检测光标所在的代码项」 | 只检测函数、impl、类型（struct、enum、union）、trait 和内联模块；光标在 use、字段、常量、宏上时检测包住它的那一项 |
| 规则说明 | 唯一的「Bot Analyzer 规则说明」页签：全部规则、为什么、怎么改、本项目最严重的一处 |
| 导出 | 把侧栏某一页写成 Markdown 报告 |

## 2 写法约定（全插件统一）

| 约定 | 例 |
| --- | --- |
| 术语、上限、目标用半角括号紧跟名称 | 函数过长(NLOC 上限 50)、平均文件代码行(AFS 目标 ≤ 300) 370.5（侧栏里「目标 ≤ 300」换到名称下面一行，12px 次要色；提示和规则说明里照旧写在括号里） |
| 比例写算出的百分比，分子/分母紧跟在括号里 | 超长函数占比(LFR) 1.57%(38/2,414) |
| 分子是 0 时括号省掉（第二十六轮） | 超大目录占比(ODR) 0%（不写 0%(0/60)）；注释掉的代码密度(CCD) 0（不写 0(0)）。分母是 0 时按「不适用」「无法判定」走，不写 0% |
| 密度写每千行的值，括号里是个数 | 注释掉的代码密度(CCD) 0.098(4) |
| 不写显然的单位（个、行、项、段、处） | 问题 52、函数 2,414 |
| 行号照 VS Code 状态栏的说法（第二十五轮）：单行「行 500」，范围「行 548–685」（en dash），带列「行 5，列 3」，悬停位置「行 548–685，共 138 行」；跨文件「dir.rs:500」「dir.rs:548–685」；配置错误「bot-metric.toml:2」 | 行 226–276 另 1 处：行 279–329；matcher.rs:596–638 |
| 用时写秒 | 用时 0.5s、0.09s |
| 不用「+」「=」拼句子，构成逐项列出 | 函数 41，下面 有问题 3、没有问题 38 |
| 名称左对齐，值右对齐；子项缩进一级 | 侧栏概览、状态栏提示 |
| 一种颜色一种意思 | 橙＝超出上限 / 未通过 / 新增，黄＝接近（≥ 90%）/ 无法判定，绿＝通过 / 消除，红只给检测失败和插件自己的故障；0 写灰；度量类别不上色，用加粗小标题；状态栏按钮只用 VS Code 的警告、错误两种底色 |
| 单元测试是否检测、依据是哪一方，写在侧栏概览和状态栏提示里 | 单元测试(默认配置) 不检测；状态栏文字不写，提示里单独一行「单元测试  不检测(默认配置)」 |
| 条数和数值分开 | 分组的条数用灰色圆角标；叶子的数值带缩写：NLOC 119、CCN 27、2 处 |

「有问题」是有函数过长、圈复杂度过高或 unsafe 代码的函数，与函数达标率(FCR)同一口径：dir.rs 有问题 3、没有问题 38，FCR 92.7%(38/41)；ripgrep 有问题 42、没有问题 2,372，FCR 98.3%(2,372/2,414)。悬停「有问题」列出函数名。各类问题的条数只在「问题」里。

状态行：检测中写「检测中，下面是上一次的结果」；有未保存的改动时数字变淡；单文件检测没能分析这个文件（配置写错、语法错误）时写「检测失败：…；下面是上一次的结果」。这一行只写时间，不写「（随整个项目）」（第二十六轮去掉：这一行本身只在没有单独检测过这个文件时出现，加括注是重复信息）。

概览先写规模，再按因果链排：

1. 检测（今天 14:32，用时 0.5s；只有「待更新」「检测失败」「分析不完整」三种状态下面才多一行「重新检测整个项目」，正常时这一行不显示——第二十六轮，避免和侧栏标题栏的 ⟳ 重复）；配置（默认配置 / bot-metric.toml），下面逐行写检测范围：条件编译 全部分支、单元测试(默认配置) 不检测、集成测试(默认配置) 检测，悬停写依据和怎么改（见第 7 节）；工具（bot-metric 1.2.3）。
2. 门禁：结论、阻塞项，无法判定时写原因。阻塞策略不单列一行（第十八轮），写在「门禁」「阻塞项」的悬停里：「阻塞策略：warning、error（bot-metric.toml 的 [rules] blocking_severities，默认 warning、error）／bot-metric 内置规则都是 warning」。
3. 问题：按 bot-metric 的口径，含质量目标未达标(项目级)；都不阻塞时写「按 bot-metric.toml 的阻塞策略，这些问题都不阻塞」。

5. 函数 2,414，下面 有问题 42、没有问题 2,372。
6. 最长函数(NLOC) 185 与最高圈复杂度(CCN) 34 单独成行（不属于上面的拆分），都是 HiArgs::from_low_args，超限所以名字也标橙，可点。

阻塞策略的依据（实测）：bot-metric 1.2.3 默认 blocking_severities = warning、error（config.rs），内置规则只产生 warning；ripgrep 默认阻塞 52，只阻塞 error 时 0，blocking_rules 去掉 unsafe 时 47。

门禁的四种结论都在 ripgrep 上实跑得到：

| 结论 | 条件（gate.status） | ripgrep 实测 | 状态栏左边 |
| --- | --- | --- | --- |
| 未通过 | blocked：阻塞项 > 0 | bot-metric 默认配置，阻塞项 52 | 盾牌 未通过 52，警告底色 |
| 通过 | passed | 只阻塞 error，禁用增长率目标 | 带勾盾牌 通过 |

**问题详情成树（第二十六轮改，问题详情修改 1–3）**：类别 → crate（或包）→ 模块（或文件）→ 函数；质量目标未达标直接列出那一项目标；重复代码块按文件归组。组的条数是灰色圆角标，叶子的值带缩写（HiArgs::from_low_args NLOC 185、defs.rs NLOC 7,025、gethostname 2 处），不再把条数和行数混在同一列。

按模块还是按目录由设置 `botAnalyzer.sidebar.problemGrouping` 决定，三个值：

| 值 | 意思 | 分节标题右边 |
| --- | --- | --- |
| `module`（默认） | 只按模块：crate → 模块 → 函数 | **不显示**切换 |
| `dir` | 只按目录：包 → 文件 → 函数 | **不显示**切换 |
| `both` | 两种都能切 | 显示「按模块 / 按目录」控件，默认停在**按模块** |

要点：
- **只选一种时，标题右边那个「按模块 / 按目录」分段控件不出现**——设置已经定了用哪种，再给一个切换是多余的信息（第二十六轮反馈 2）。选 `both` 才出现，切换只影响本次会话，不写回设置；重载窗口后回到设置里的值。
- 默认 `module`，也就是默认只显示按模块的内容（反馈 3）。
- 两种树的节点形态：按模块是 crate → 模块 → 函数（crate 行悬停写包名，`mod` 为空写「根模块」）；按目录是包 → 文件 → 函数（包名与 crate 不同名时补 detail）。两棵树共用同一份问题数据，只是分组的键不同。

## 6 编辑器

### 6.1 波浪线、CodeLens、快速修复

不向编辑器发诊断（发诊断，编辑器就一定在悬停顶部再显示一遍）。插件自己画橙色波浪线，只画在函数名、unsafe 关键字或文件行 1；滚动条右侧同色标记。CodeLens：

```
$(warning) 函数过长(NLOC)：119 行（上限 50）　·　圈复杂度过高(CCN)：27（上限 20）
```

- **开头带 `$(warning)` 图标**，和状态栏「未通过」一样表示有问题。限制：CodeLens API 不能给单条 lens 设颜色，VS Code 的样式把图标渲染成与文字同色（`editorCodeLens.foreground`，灰色），所以图标不是黄色；要改颜色只能改用户主题的 `editorCodeLens.foreground`，会影响所有扩展的 CodeLens，插件不这样做。

- **只写这次真的超限的规则**：CCN 没超上限就不出「圈复杂度过高」那一段。例如 `Ignore::add_parents`（NLOC 57 超、CCN 14 没超）只写 `函数过长(NLOC)：57 行（上限 50）`；`Ignore::matched_ignore`（两项都超）才写两段。
- **两项合成一条 CodeLens，分隔符自己写**：全角空格夹中点（`　·　`）。不要把两项拆成两条 CodeLens——VS Code 会在多条之间插它自己的 `NBSP|NBSP`，而它渲染时会 `title.trim()`，标题首尾的普通空格和 U+00A0 都被吃掉，右边那个空隙既改不动也保证不了等宽（这一轮在竖线/点上来回试了几版才定位到）。合成一条后分隔符完全由我们控制，两边必然等宽。
- 写法：规则名 + 缩写，值带单位，上限放进括号跟在值后面。不写「函数体代码行」「圈复杂度」这两个旧称（与规则名统一，超限时才出现的 CodeLens 一眼能对上是哪条规则）。
- 文件过大写 `$(warning) 文件过大(NLOC)：7,025 行（上限 2,000）`。
- 悬停卡片里仍然是旧写法（`函数体代码行(NLOC 上限 50) 119，超出 69`），因为它写的是「超出多少」而不是「上限多少」；导出报告的表头也照旧（`代码行(NLOC 上限 50)`）。灯泡（Ctrl+.）里是「查看规则说明：函数过长（BM001）」等和「在 Bot Analyzer 视图中显示」；不再有忽略，也没有「复制函数的完整路径」（第二十六轮连命令一起删掉）。

悬停、快速修复里的规则编号和「查看规则说明」打开规则说明页签（见 6.4）。悬停截图见 0.6.0 交付的「界面实拍」；这一版去掉了「在此处忽略…」，unsafe 改名「unsafe 代码」（「需要安全审查」留在解释里）。

impl / 类型的悬停只在名字所在行出现，有未保存的改动时不出现（bot-metric 读的是磁盘上的文件）。不写 item 级的函数个数和平均值：bot-metric 在这一层把闭包也算成函数（impl Ignore 算出 29 个），与侧栏口径不同。trait 只算它自己（direct-impls 不含为别的类型写的 impl），悬停第一行写 `trait 路径`，不写成「类型」。

**带泛型参数的类型**：bot-metric 1.2.3 的 `--item-relation direct-impls` 按名字把 impl 关联到类型（`service.rs:919-957`），而 `impl<'a> IgnoreMatch<'a>` 的名字是 `IgnoreMatch < 'a >`，与 `IgnoreMatch` 对不上，所以带泛型或生命周期参数的类型取不到 impl 块。插件不自己补算，只在悬停里写明「未统计：带泛型参数的类型暂无法关联 impl 块」，代码行数照写类型本身。不带泛型的类型（如 struct Ignore）不受影响。

**值这一列统一左对齐**：悬停表格右侧的值，第一行（如「问题」的条数 2、代码行数 461）和下面的子行（每条问题的描述、按类别列出的问题、类型本身与各 impl 块的代码行数）从同一个左边缘开始，子行不缩进。

**悬停里的行号都可以点**：「位置」一行（① ② 函数、③ unsafe、⑤ ⑥ ⑧ 代码项、⑦ 重复代码块），③ 里「本文件」其余几处 unsafe，⑥ 里 impl 块括号中的行号，都写成链接（`botAnalyzer.openLocation`，参数 `{uri, line, endLine}`），点了跳到这个文件的那几行并选中；unsafe 只在一行里时参数多带 `col`、`endCol`（0 基，终点不含，取自报告的 start_col/end_col），只选中 `unsafe { … }` 那几列。文字不变，仍是「行 548–685」。文件级问题「整个文件（…标在行 1）」是说明，不做成链接。

**「在 Bot Analyzer 视图中显示」的行为约定**（第二十六轮，反馈 8）：悬停卡片、CodeLens、快速修复里的这个链接一律切到侧栏「当前文件」页并选中对应函数那一行（`sidebar.reveal(函数键)`）。实现上**必须把函数键直接放进命令参数**，不能再靠「文件 + 行号」在客户端反查：0.11.0 的悬停链接只带 `{uri, line}`，客户端拿它去 `Marks.functionAt` 里找函数，一旦标记还没到、已过期或这一行没命中，就会弹出「光标不在任何函数里」而什么也不做——这正是反馈 8 看到的现象。行号只作为兜底：键取不到时才退回按行查找，两者都没有才提示「光标不在任何函数里；Bot Analyzer 视图只能定位到函数。」

**链接按位置定位**：侧栏「当前文件」能选中的是函数行、「全部函数」里的组（impl 块、内联模块）和各分节。悬停、CodeLens、灯泡里的这个链接：在函数上（含函数里的 unsafe）带函数键，选中这个函数；文件级问题（如文件过大 BM003）和不在函数里的 unsafe（unsafe impl、unsafe trait）展开「问题详情」并滚到那一节。impl、类型、trait、模块的悬停（⑤ ⑥）和右键检测的结果面板（⑧，含落在函数上时）不显示这个链接；要定位到侧栏，用编辑器右键里的「在 Bot Analyzer 视图中显示」。重复代码块（⑦）落在某个函数里时显示（定位到包住它的最内层函数），不在任何函数里时不显示。编辑器右键和命令面板里的「在 Bot Analyzer 视图中显示」（原名「…这个函数」）不再提示「光标不在任何函数里」，按光标位置定位：函数 → 选中函数；impl 块、内联模块或类型定义 → 展开「全部函数」里那一组（类型定义归到它的 impl 组，先找 impl X，再找 impl Trait for X；服务端随标记发下各组的行范围 `FileMarks.groups`：impl 组取包住组内函数的 impl 块，同一类型的多个 impl 块各算一段；模块组取组内函数的首尾）；别处（文件顶层、trait、同一文件里没有 impl 的类型） → 打开「当前文件」页。

**为什么改**：悬停是在服务器端算出来的，那一刻它手上就有这个函数的稳定键（`FnState.key`，与侧栏 `fnKey` 同源）；把它一起发下来，客户端不需要再依赖一份可能过期的标记表。

### 6.3 右键与「检测光标所在的代码项」⑧

编辑器右键的「Bot Analyzer ▸」子菜单：检测光标所在的代码项 | 在 Bot Analyzer 视图中显示、查看规则说明 | 重新检测当前文件、重新检测整个项目。菜单项一直显示（不按光标位置显示或隐藏）。「在 Bot Analyzer 视图中显示」按光标位置定位：在函数里选中这个函数；在 impl 块或内联模块里（不在函数里）展开「全部函数」里对应的组；在结构体、枚举、联合体的定义里展开这个类型的 impl 组（先找 impl X，没有再找 impl Trait for X）；别处（文件顶层、trait、同一文件里没有 impl 的类型）打开「当前文件」页。「查看规则说明」打开光标所在函数（或这一行上的文件级问题、unsafe）的第一条规则；光标所在位置没有问题时提示「光标所在位置没有问题。」；「检测光标所在的代码项」一直在菜单里（0.10.0 起不再按光标位置显示或隐藏）；光标不在可检测的代码项里（如文件开头的 use、两个语法项之间的空行、模块声明 `mod x;`）时，点了提示「光标不在可检测的代码项里（函数、impl、类型、trait 或模块）」。

**「复制函数的完整路径」去掉**（第二十六轮，反馈 7）：菜单最后一项和它上面的分隔线一起去掉，`botAnalyzer.copyPath` 命令本身也一并删掉（命令声明、菜单项、命令面板条目、客户端实现与注册）。理由：函数名已经在侧栏（菜单上方的「在 Bot Analyzer 视图中显示」）和悬停里给了，复制路径这一步用的人少，菜单留四项更好读。

**为什么改**（第二十三轮，真实界面复现）：0.9.0 的菜单项靠「光标是否在函数里」这类上下文键决定出不出现，而这些键由插件异步更新；右键落在别的位置时，菜单出现的那一刻用的还是上一个光标位置的值，所以菜单会少一项或多一项，要先左键点一下再右键才对。现在菜单项一直显示，光标位置由检测请求自己带上。另外两处：不含单元测试时落在测试里的提示原来指向已经不存在的「配置单元测试…」，改为指向侧栏「单元测试」一行；选中一段文字再右键检测，选区原样保留（浮层用 editor.action.showHover，不再移动光标）。

## 7 检测范围与单元测试（第十七至十九轮）

检测范围只由 bot-metric.toml 决定，插件不加 feature 设置。bot-metric 1.2.3 实测：

## 9 导出报告

侧栏标题栏「重新检测」右边的导出按钮：在哪页导出哪页；「⋯」菜单和命令面板里也有两项。保存对话框默认项目根目录，文件名 `bot-analyzer-名称-检测时间.md`（如 bot-analyzer-ripgrep-20261010-1432.md）；写完后提示「已导出 Bot Analyzer 报告：…」，可「打开」或「在文件夹中显示」。

- 整个项目：基本信息（范围、包与名字、文件、代码行数、检测时间、工具、配置、单元测试）、门禁（阻塞项，无法判定时写原因；不写阻塞策略）、问题全表（每类按数值从大到小，含质量目标未达标、重复代码块）、质量目标、函数（有问题、没有问题，最长函数与最高圈复杂度带位置）、度量（每项都写口径）。
- 当前文件：基本信息（含单元测试）、概览（函数拆成有问题、没有问题；另有或含测试函数几个）、问题、全部函数（表头 代码行(NLOC 上限 50)、圈复杂度(CCN 上限 20)，最后一列写明问题）、度量；门禁和质量目标看整个项目，只在项目报告里。
- 结果不是最新、检测中或失败时，报告开头写明。
- 两份输出与画布「导出报告」的样张逐字一致（自动测试核对）。

## 10 什么时候检测

| 时机 | 做什么 |
| --- | --- |
| 打开项目 | 常规分析与「全部函数」两次并行（ripgrep 约 0.5 秒） |
| 切到一个文件 | 补取这个文件的度量与测试函数个数 |
| 保存一个 .rs 文件 | 先检测这个文件（0.07–0.09s），文件项与项目问题数立即更新；2 秒内没有再保存就在后台检测整个项目。内容与上一次分析一样时不重跑（未改动就保存、改了又改回原样），也不写「待更新」 |
| 手动「重新检测当前文件」 | 同上；内容没变时不重跑，也不写「待更新」（重新检测这个动作本身不代表项目内容变了） |
| 大项目 | 上次检测整个项目超过 analyze.projectAfterSave 秒（默认 3）时不自动跑；这时只有内容真的变了才写「待更新」（见第 5 节） |
| Cargo.toml、bot-metric.toml 改动 | 重新检测整个项目 |
| 改设置 analyze.includeTests | 重新检测整个项目 |
| 大量 .rs 变化（切分支） | 重新检测整个项目 |
| 删掉 .rs 文件 | 从结果里去掉，并像保存一样安排检测整个项目 |
| 悬停在 impl / 类型名上、右键检测 | 只检测这一项（本机实测 180–310ms），按文件修改时间缓存 |

单文件检测也会算出质量目标并报 BM005（dir.rs 单文件的平均文件代码行 1,203 > 300），插件丢弃单文件结果里的 BM005，只用整个项目的。

## 11 命令与设置

命令面板 11 条：打开 Bot Analyzer 视图；重新检测当前文件（Ctrl+Alt+Shift+M）；重新检测整个项目；检测光标所在的代码项；导出当前文件报告；导出整个项目报告；在 Bot Analyzer 视图中显示；查看规则说明；查看 Bot Analyzer 输出日志；指定 bot-metric 可执行文件路径；打开 Bot Analyzer 设置（设置界面只列本插件的设置）。侧栏「⋯」菜单：导出两项、打开 Bot Analyzer 设置、查看输出日志（不放「打开 bot-metric.toml」：检测失败时侧栏给出这个链接，「单元测试」一行变灰时点它也会打开）。导出命令名不标注格式（文件名后缀 .md 已说明是 Markdown），末尾也不带「…」。

（命令面板的截图见 0.8.0 交付的「界面实拍」）

设置 9 项，都在 botAnalyzer 命名空间下，走 VS Code 的设置：个人习惯写在用户设置里，跟项目走的写在工作区的 .vscode/settings.json。会影响检测结果和门禁的（上限、测试、条件编译、质量目标、阻塞策略）只放 bot-metric.toml，和 CI 共用。插件声明不在受限模式（未信任的工作区）下运行：它会运行 bot-metric 分析工作区的代码。用词约定：「设置」只指本插件的 VS Code 设置（写全键名），「配置」只指 bot-metric.toml；没有 bot-metric.toml 时写「bot-metric 默认配置」。

| 设置 | 默认 | 说明 |
| --- | --- | --- |
| botAnalyzer.analyze.on | save | 自动检测的时机，打开项目时总会检测一次整个项目。`save`：保存 `.rs` 文件时检测该文件，并按 `projectAfterSave` 在后台检测整个项目；`Cargo.toml`、`bot-metric.toml` 变化时也重新检测。`manual`：仅在执行「重新检测」时检测 |
| botAnalyzer.codeLens.enabled | true | 在超出上限的函数（NLOC、CCN）和过大文件上方显示 CodeLens |
| botAnalyzer.analyze.projectAfterSave | 3 | 保存后自动检测整个项目的耗时上限（秒）：上次检测整个项目用时超过此值时不自动检测，状态栏显示「待更新」，点击即可检测；`0` 表示不自动检测；仅在 `analyze.on` 为 `save` 时生效 |
| botAnalyzer.analyze.includeTests | false | 检测时包含测试代码：每次调用 bot-metric 时加 `--include-tests`，计入 `#[cfg(test)]` 代码及测试、基准、示例 target；结果可能与 CI 不同。也可点击侧栏「单元测试」一行切换。`bot-metric.toml` 已设置 `include_tests = true` 时无法关闭 |
| botAnalyzer.notify.gateChanged | false | 整个项目检测后门禁结论发生变化（如「通过」变为「未通过」）时弹出通知 |
| botAnalyzer.botMetric.binaryPath | 空 | bot-metric 可执行文件路径（需 1.2.1 及以上），仅可在用户设置中指定。留空时依次查找插件自带、`PATH`、`~/.cargo/bin`；指定的路径不可用时报错，不再查找其他位置 |
| botAnalyzer.statusBar.showProject | true | 在状态栏左侧显示「整个项目」（门禁结论与问题总数） |
| botAnalyzer.statusBar.showFile | true | 在状态栏右侧显示「当前文件」（问题条数） |
| botAnalyzer.sidebar.problemGrouping | module | 侧栏「整个项目」中问题详情的分组方式：`module` 按模块（crate → 模块 → 函数），`dir` 按目录（包 → 文件 → 函数），`both` 两种都提供、可在问题详情标题右侧切换（切换结果不写回设置） |

（设置的截图见 0.8.0 交付的「界面实拍」）

## 12 架构

两个进程：客户端只画（侧栏 webview、状态栏两项、波浪线与竖线装饰、命令、菜单、选择框、保存对话框），不认识度量工具，也不拼文案；语言服务器算好全部文字。只有 `server/src/process.ts` 起子进程（自动测试守着这一条）。

| 文件 | 职责 |
| --- | --- |
| shared/protocol.ts | 两边共用的消息与视图模型类型 |
| server/src/report.ts | 解析 bot-metric JSON（1.2.1 / 1.2.3）：问题、度量、质量目标、门禁、启用的规则、错误、selection、related_locations |
| server/src/model.ts | 项目模型：全部函数、按文件的问题、是否含单元测试、保存后逐文件替换、「与上次相比」的差异、重复代码的另几处 |
| server/src/botconfig.ts | 只读 bot-metric.toml（是否存在、重复检测、include_tests）；0.10.0 起不再改写 |
| server/src/names.ts | 拆函数名：内联模块、trait、类型、函数 |
| server/src/source.ts | 字节偏移换算成行、列（related_locations 与 selection 只给字节范围；列按字符算，与 --item-at 一致） |
| server/src/items.ts | 粗扫源码，得到函数、impl、类型的行范围（服务端判断光标落在哪一项） |
| server/src/engine.ts | 检测编排：项目检测、单文件检测、后台检测整个项目、item 检测与缓存、失败处理 |
| server/src/present/summary.ts | 门禁、问题计数、质量目标、分析不完整、最长函数（侧栏、状态栏、导出共用，保证三处一致） |
| server/src/present/sidebar.ts | 侧栏两页 |
| server/src/present/status.ts | 状态栏两项与提示 |
| server/src/present/editor.ts | 波浪线、悬停 ①–⑧、CodeLens、快速修复 |
| server/src/present/picks.ts | 问题选择框 |
| server/src/present/rules.ts | 规则说明面板的内容 |
| server/src/present/export.ts | 导出 Markdown |
| client/src/*.ts、media/view.js、media/rules.js | 画界面（侧栏、规则说明面板）、执行命令 |

自定义消息：服务端 → 客户端 `botAnalyzer/view`、`/status`、`/marks`；客户端 → 服务端 `/activeFile`、`/dirty`、`/recheck`、`/settings`；请求 `/testsState`（bot-metric.toml 是否已包含测试，已包含时带一句提示语）、`/rulePanel`、`/configPath`、`/problems`、`/export`、`/checkAt`。侧栏「单元测试」一行的点击由客户端只做一件事：改设置，或打开 bot-metric.toml；文字由服务端给，客户端不出现工具名。悬停和状态栏提示里的链接只允许执行插件自己的命令。「检测光标所在的代码项」：客户端发 `/checkAt`，服务端检测并把结果钉在那个位置，客户端再执行 `editor.action.showHover`，结果就在光标处弹出。

调用 bot-metric 的方式：

| 用途 | 命令 |
| --- | --- |
| 项目常规分析 | `analyze <项目根> --format json` |
| 全部函数 | `analyze <项目根> --huge-function-lines 1 --huge-complexity 1 --format json` |
| 单文件 | `analyze <文件> --format json`、全部函数；数测试函数时另一种口径再取一次全部函数（不含测试时加 `--include-tests`，插件设置包含时不加） |
| 包含单元测试 | 插件设置 include 时，上面每条都加 `--include-tests` |
| 一个语法项 | `analyze <相对路径> --item-at <相对路径>:<行>[:<列>] [--item-relation direct-impls] --format json`，在项目根目录下运行，路径写相对路径和正斜杠，避免 Windows 盘符里的冒号 |
