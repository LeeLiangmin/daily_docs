# 工具辅助代码迁移复盘

适用场景：用一套工具（自研或第三方，含 AI 辅助转译）把代码从一种语言迁移到另一种语言（典型是 C/C++ → Rust）之后，对整个过程做复盘。

报告骨架见 `references/report-template.md`，本地数据统计脚本见 `scripts/collect-stats.sh`。

## 核心原则

1. **用数据还原，少靠回忆。** git 历史、工具日志、工具版本记录优先；回忆只用来补数据解释不了的部分，并标注为"主观"。
2. **先对齐事实，再讨论原因，最后定行动。** 三步不要混在一起。
3. **一切对照目标。** 没有第 0 维度的目标和成功标准，就没有"好"与"不好"。
4. **对事不对人。** 分析流程、工具、决策，不追究个人。
5. **人为介入是核心数据。** 迁移工具的价值 = 它省掉了多少人工；复盘重点是把每一次人工介入找出来、分类、归因。
6. **数据不出本地。** 数据敏感时，只在本地执行统计，对外只给脱敏汇总数字。

## 开始前先问清楚（最多问一轮）

- 源语言 / 目标语言、代码规模（行数、模块数）
- 工具是自研还是第三方（自研会多出"工具演进"和"工具回馈"两部分）
- 个人项目还是团队项目（决定是否组织复盘会）
- 过程数据保留情况：git 历史、工具日志、工具版本记录、issue、会议记录
- 复盘读者：团队、管理层、工具开发者（决定产出侧重）

## 复盘框架：8 个维度

### 0. 背景与目标（基准线）
- 为什么迁移：内存安全、维护成本、性能、生态
- 当初的成功标准：功能等价、性能不退化、unsafe 占比上限、工期、人力
- 范围与策略：全量迁移 / 渐进式 FFI 混编 / 按模块替换

### 1. 输入
- 规模：LOC、模块数、文件数
- 代码特征：宏、全局可变状态、裸指针与手动内存管理、union、goto、函数指针回调、内联汇编、模板/继承（C++）
- 外部依赖与构建系统：CMake/Make、第三方库、平台相关代码
- 已有资产：测试与覆盖率、文档、CI
- 团队：目标语言经验、对原代码的熟悉度
- **要回答：** 哪些输入特征后来成了主要难点？（用于下次做前期评估）

### 2. 工具的使用
- 工具链清单，以及每个工具负责的阶段（如 转译 → 清理 → 安全化重构 → 验证）
- 自研工具拆到内部环节：解析 → 转译 → 类型/所有权推断 → 代码生成 → 后处理；记录失败发生在哪个环节
- 关键配置、参数或 prompt
- 产出质量指标：一次编译通过率、测试通过率、unsafe 块/行数、lint 告警数、生成代码可读性
- 语言特征覆盖矩阵：哪些特征处理得好、没覆盖、处理错了
- **要回答：** 工具擅长什么、在哪里失败、失败有没有规律？

### 3. 时间节点
- 里程碑时间线：计划 vs 实际
- 各阶段耗时占比：工具自动处理 vs 人工处理
- 阻塞期：卡在哪、卡多久、怎么解开
- 自研工具画**双时间线**：项目进度线 + 工具版本线，对照看每次改工具后介入量是否下降

### 4. 人为介入（核心）
逐条整理成介入表：

| 阶段 | 模块 | 问题现象 | 介入类型 | 根因归类 | 耗时 | 能否自动化 | 工具回馈 |
|---|---|---|---|---|---|---|---|

根因归类三选一：
- **工具能力不足**：工具做不到，人来补
- **工具出错**：工具产出错误结果，人来纠正（最危险，重点统计有没有漏网的）
- **设计决策**：本就该由人决定（所有权模型、API 重设计、错误处理策略）

介入类型参考：修编译错误、消除 unsafe、重构所有权/生命周期、修语义差异、改错误处理、性能调优、适配构建/FFI。

工具回馈（自研工具）：已修进工具 / 计划修 / 不适合自动化。

**量化方法：** 工具原始输出与最终代码的 diff 即人工改动量。统计每模块人工改动行数占生成行数的比例，以及改动集中在哪类代码。

### 5. 产出结果
- 正确性：测试结果、差分测试（新旧实现同输入对比输出）、fuzzing
- 性能：基准对比（吞吐、延迟、内存）
- 安全性：unsafe 残留数量及每处保留原因
- 可维护性：是否符合目标语言惯用写法，团队是否愿意接手
- 对照第 0 维度逐项判断：达成 / 部分达成 / 未达成

### 6. 成本核算
- 总成本 = 工具开发投入（自研）+ 迁移过程人工投入
- 与"纯人工重写"的估算对比，回答"工具值不值"
- 区分项目专用投入与可复用投入
- 沉淀估算模型：每千行源码的人工介入耗时

### 7. 反思与行动项
- 分**项目层面**（流程、分工、节奏）和**工具层面**（设计假设哪些成立/不成立）两块写
- 做对了什么（保留）、没做好什么（改进）
- 对"没做好"追问根因（5 Whys），不停在表面现象
- 关键决策回看：尤其是"改工具 vs 人工绕过"的每次选择；如果重来会改哪个决策
- 行动项必须有：具体动作、负责人、完成时间

## 模块对照表

| 模块 | 源 LOC | 目标 LOC | 一次通过率 | 人工改动比例 | 耗时 | unsafe 残留 | 难点特征 |
|---|---|---|---|---|---|---|---|

按"人工改动比例"排序，观察与"难点特征"的关联，回答"什么样的源代码最难迁移"。

## 数据源与用途

| 数据源 | 用途 |
|---|---|
| git 历史 | 还原时间线；按作者/提交信息区分工具提交与人工提交；阶段耗时 |
| 工具原始输出 vs 最终代码 diff | 量化人工介入 |
| 工具日志 | 失败环节、触发失败的语言特征 |
| 工具版本记录 | 工具演进线、改进效果 |
| issue / PR / 会议记录 | 阻塞原因、决策背景 |
| 测试与基准报告 | 产出结果 |

## 本地统计

运行 `scripts/collect-stats.sh`（先按脚本顶部说明改配置）。它输出：
- `timeline.csv`：每日提交数、增删行数（区分工具/人工）
- `modules.csv`：各模块源/目标行数、unsafe 次数、工具输出到最终版本的改动行数
- `unsafe.txt`：unsafe 出现位置排行

脚本只做机械统计。介入的分类、归因需要人工结合日志和上下文判断。注意：
- unsafe 按单词匹配计数，注释里的 unsafe 也会被算进去，需要精确数字时人工复核 `unsafe.txt`
- 模块按目录下第一级子目录划分；源代码与目标代码的模块名不一致时，对照表需要人工对齐
- "工具输出后人工改动行数"依赖 `TOOL_REV`；如果工具输出分多次提交，可以按模块分别指定再跑

## 执行流程

1. **收集数据**：按数据源清单逐项确认可用性。
2. **重建时间线**：串起提交、里程碑、工具版本，标出关键事件和介入点。
3. **填介入表和模块对照表**，分类统计（最花时间，也最有价值）。
4. **逐维度分析**，全部对照第 0 维度。
5. **复盘讨论**（团队项目）：事实 → 原因 → 行动项，分三段进行。
6. **产出**：按 `references/report-template.md` 填写。

## 产出

1. **复盘报告**（团队/管理层）：结论摘要（一段话：目标达成情况、总成本、最重要的 3 条经验）→ 8 个维度 → 行动项。
2. **工具改进清单**（工具开发者）：按"介入频次 × 单次耗时"排序，每项附典型案例和建议修复方式。
3. **迁移 playbook**（下个项目）：前期评估清单（输入维度的难点特征）、推荐流程、常见问题与处理方式对照、工期估算模型。

## 常见陷阱

- 只写"遇到的困难"，不量化、不归因
- 把工具出错当成工具能力不足，低估了风险
- 没有目标基准，结论只能是"整体顺利"
- 忽略工具开发成本，导致"工具值不值"无法回答
- 行动项没有负责人和时间，复盘后无人跟进
