01 · 能不能缓存

缓存指令

no-cache 不是“不缓存”，no-store 才是

指令含义典型场景
max-age=NN 秒内视为新鲜，可直接使用带指纹的 JS / CSS
no-cache可存储，但每次使用前必须向源站校验HTML 入口页
no-store不得存储任何副本银行、个人隐私页面
private只允许浏览器缓存，CDN 不得缓存带登录态的个人数据
public共享缓存也可存储公开的图片、字体
immutable新鲜期内刷新也不再校验文件名含哈希的资源

默认可缓存的状态码

200 203 204 206
300 301 308 404 405 410 414 501

其余状态码需要显式的缓存头才会被存储。

方法限制

通常只有 GET 和 HEAD 的响应会被缓存；POST 需显式声明且很少被实现。

配置前先问：响应含个人数据吗？含，就加 private，别让 CDN 存。

02 · 缓存多久

新鲜度判定

先看 max-age，再看 Expires，最后才启发式估算

① 有 s-maxage？

共享缓存（CDN）优先用它，忽略 max-age。

→

② 有 max-age？

新鲜期 = max-age，忽略 Expires。

→

③ 有 Expires？

新鲜期 = Expires − Date，依赖时钟。

→

④ 都没有

启发式：常取 (Date − Last-Modified) × 10%。

推导示例

Last-Modified 距今 30 天，无任何缓存头：
新鲜期 ≈ 30 × 10% = 3 天

10% 是规范建议的常见做法，不是强制值；浏览器实现各异。

Age 头

响应经过 CDN 时会带 Age: N，表示它已在缓存里放了 N 秒。
剩余新鲜期 = max-age − Age。

03 · 过期之后

条件请求

用 ETag 校验，未变化时只传 304 头部

# 第一次请求
GET /app.js HTTP/1.1

HTTP/1.1 200 OK
ETag: "a1b2c3"
Cache-Control: max-age=60

# 过期后再次请求
GET /app.js HTTP/1.1
If-None-Match: "a1b2c3"

HTTP/1.1 304 Not Modified
ETag: "a1b2c3"
1响应带 ETag，浏览器连同副本一起保存。
2过期后请求带上 If-None-Match。
3源站比对一致，返回 304，无正文。
4浏览器继续使用本地副本，并刷新新鲜期。

03 · 过期之后

ETag 与 Last-Modified

优先用 ETag，Last-Modified 作为兜底

强校验

ETag

  • 内容哈希或版本号，字节级精确
  • 对应请求头 If-None-Match
  • 计算有成本，多台源站要保证一致
  • 适合：需要精确判定“是否真的变了”的资源

弱校验

Last-Modified

  • 时间戳，精度只到秒
  • 对应请求头 If-Modified-Since
  • 内容回滚或同秒多次修改会误判
  • 适合：静态文件，或没有 ETag 的老旧源站

所以：两者都发时，服务端按 If-None-Match 优先判断。

04 · 收益

一次 304 省多少

头部约几百字节，正文可能是几百 KB

≈99%

300 KB 脚本，304 后只传头部

推导

1 − 400 / (300 × 1024 + 400) ≈ 99.87%
数字为示意，取整后写作“约 99%”。

不省的部分

仍有一次往返（RTT）。max-age 内直接命中则连这次往返也省掉。

怎么验证

curl -sI -H 'If-None-Match: "a1b2c3"' https://example.com/app.js

应返回 304 Not Modified，且没有正文。

05 · 怎么配置

三类资源

按“文件名是否带哈希”和“是否个人数据”分类配置

资源响应头原因
1带哈希的静态文件max-age=31536000, immutable内容变则文件名变，可放心缓存一年
2HTML 入口页no-cache要每次校验，才能拿到指向新文件名的页面
3个人数据接口private, no-store防止共享缓存和磁盘残留他人数据
# nginx 示例
location ~* \.(js|css)$ { add_header Cache-Control "public, max-age=31536000, immutable"; }
location = /index.html  { add_header Cache-Control "no-cache"; }

所以：先改文件名，再谈缓存时间；HTML 永远不要设长 max-age。

06 · 常见坑

六个坑

多数缓存事故来自这六种误配

坑 1

HTML 设长 max-age

发布后用户长时间看到旧页面，只能等过期。

坑 2

把 no-cache 当禁用

它仍会存储；敏感内容要用 no-store。

坑 3

忘记 Vary

按 Accept-Encoding 或语言变化的响应，缓存会串内容。

坑 4

多源站 ETag 不一致

负载均衡后校验总失败，304 变 200。

坑 5

依赖客户端时钟

Expires 与本机时间比较，时钟错乱就失效。

坑 6

Cookie 拖垮 CDN

带 Set-Cookie 的响应常不被共享缓存存储。
