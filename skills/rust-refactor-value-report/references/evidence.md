# 代码对照与佐证

> 执行清单步骤 2、7、8 · 步骤 2 跑两个指向新实现的脚本，步骤 7 做代码对照（必做），步骤 8 用历史与计数加权（可选）。

## 步骤 7：代码对照

### 选取标准

- **服务于上层结论**：每组对照挂在某条架构或设计模式结论下面。找不到它服务哪条结论的，不贴。
- **同功能**：来自对应关系表里的同一对
- **短**：单侧 30 行以内，超了截取核心并用 `// ...` 标注省略
- **有代表性**：不要用旧实现里最烂的一段对比新实现里最好的一段。选取时说明为什么这段有代表性——核心路径、扇入最高、或被修改次数最多
- **真实**：可为可读性做最小删减（去掉无关字段、缩短标识符），但不能虚构，须注明"已简化"

数量不设上限——**上层有几条结论就配几组对照**，但不要为凑数贴无关的。

### 判断一组对照有没有价值

能用一句话填完这个模板，才值得贴：

> 旧实现在这里靠 ______ 维持正确性，新实现靠 ______ 维持正确性。

左边填出来是"程序员记得/注释/约定/人工审查/运行时检查"，右边是"编译器/类型系统"——有价值。两边同类——没价值。

### 呈现格式

```
**旧实现**（`src/conn.h:18`）
```c
// 代码
```

**新实现**（`src/conn.rs:56`）
```rust
// 代码
```
```

紧接一段**连贯文字**，说清两边各靠什么维持正确性、这个差异属于哪一档归因、代价是什么。**不要用"差异/归因/代价"三行式**——那是底稿格式。

### 高频对照速查

| C/C++ 形态 | 靠什么维持 | Rust 机制 | 归因 |
|---|---|---|---|
| 手动 malloc/free | 程序员配对 | 所有权 + Drop | L1 |
| `goto cleanup` | 每个早退分支都记得跳 | Drop + `?` | L1 |
| 返回 -1/errno | 调用方记得检查 | Result + must_use | L1 |
| 可能返回 NULL | 调用方记得判空 | `Option<T>` | L1 |
| 裸数组 + 长度参数 | 长度算对 | 切片 | L1 |
| 容器扩容后旧指针 | 程序员避开 | 借用规则 | L1 |
| 隐式数值转换 | 程序员当心 | 无隐式转换 | L1 |
| 锁与数据分离 + 注释 | 注释 + 人 | `Mutex<T>` | L1 |
| unlock 散在各分支 | 每条路径都记得 | MutexGuard 的 Drop | L1 |
| "只能在 X 线程调用" | 注释 + review | Send/Sync | L1 |
| `#define` 状态 + switch | 记得改全 | 枚举 + 穷尽 match | L1 |
| `void *ctx` + 函数指针 | 注册方与调用方约定 | trait 对象 | L1 |
| 宏展开多份类型代码 | 宏写对 | 泛型 + trait | L2 |
| 都是 int，语义靠命名 | 命名约定 | newtype | L2 |
| "必须先 init 再 use" | 注释 + 人 | typestate | L2 |
| 构造后再逐个校验 | 调用方自觉 | 私有字段 + 构造校验 | L2 |
| 用 0/NULL 当哨兵 | 约定 | NonZeroU32 / NonNull | L2 |
| `buf` + `len` 两参数 | 保持一致 | 切片 / const generics | L2 |
| 结构体字段全 public | 约定不要乱改 | 可见性控制 | L2 |
| 加锁顺序约定 | 人 | **无对应，Rust 不防死锁** | 不写 |

**两条不要说死**：`Rc`/`Arc` 循环引用仍会泄漏；整数溢出 release 下默认回绕。

### 反向自查（必做）

贴对照之前，在新实现里统计一遍：

```
scripts/code_metrics.py --old <cpp> --new <rust>
scripts/find_design_signals.py --new <rust>      # 末尾也给体检数字
```

- `unsafe` 块的数量与分布——编译期保证被绕过的地方
- `unwrap()`/`expect()`/`panic!` 密度——高说明编译期保证被换成了运行时崩溃
- 被迫的 `clone()`——所有权设计不顺畅的信号

**主动写进"代价与局限"**，比被评审问出来强得多，且能显著提升前面所有结论的可信度。

### 低价值对照，不要贴

纯语法糖（`for` 循环 vs 迭代器链）除非能说明它消除了索引越界；行数变少除非能说清少的是哪一类代码；"更现代""写起来更爽"这类主观感受；用旧实现里最烂的一段对比新实现里最好的一段。

## 步骤 8：佐证加权（可选）

**这一步只给已有的价值点加重量，不产生新的价值点。** 跳过它文档依然成立。

用法：已经从当前代码看出某个设计差异，去历史里找它是否兑现过。找到了就补一句"这里出过 N 次事故"。

### 六个脚本

**先跑这两个**（指向新实现，产出主体章节要写的内容）：

```
scripts/find_vanished.py       --old <cpp> --new <rust>   # 旧机制消失了什么
scripts/find_design_signals.py --new <rust>               # 新设计出现了什么
```

`find_vanished.py` 的输出按扇入排序。**成组出现的消失对应同一个设计决策**，把这一组合并成文档的一节。

**定位与加权**：

```
scripts/rank_core_symbols.py --old <cpp-src> [--repo <cpp>]   # 扇入排序、核心×热点交集
scripts/find_change_cost.py  --repo <cpp>                     # 补漏对、变更热点、变更耦合
scripts/mine_fix_commits.py  --repo <cpp>                     # 按缺陷类别归类 fix commit
scripts/code_metrics.py      --old <cpp> --new <rust>         # 危险模式计数、体检、构建系统
```

统一参数：`--old`（C/C++）、`--new`（Rust）、`--repo`（git 仓库）、`--top`、`--json`。

### 纪律

- **所有输出都是未复核线索**，引用前抽样打开对应代码确认
- 文档中注明**统计口径与复核比例**
- commit message 质量差时命中率低，**不影响主线**，如实说明佐证不足即可
- `find_vanished.py` 的候选必须人工分三类：**真的消失了**（价值点）／**只是改了名**（去掉）／**功能被砍了**（属于范围决策，写进"背景与对比基准"而非价值点）

### 读代码的手段

grep 能回答"出现了多少次"，回答不了"谁调用了谁""改这里会波及哪些地方"——而模块边界这一维度只能靠结构化信息支撑。

- **GitNexus**：`npx gitnexus analyze` 建索引（tree-sitter + KuzuDB，支持 C/C++/Rust），MCP 提供 `context`（调用者/被调用者）、`impact`（影响半径）、`cypher`。新旧仓库各建一次。需 Node ≥ 18，大仓库先用 `--skip-embeddings`
- 替代方案：C/C++ 用 `cscope`/`clangd`/`clang -H`；Rust 用 `cargo modules structure`、`cargo tree`、`cargo geiger`

图谱输出同样是线索，进文档的结论都要回源码确认；工具版本、索引时间、查询语句写进附录，否则评审无法复现。
