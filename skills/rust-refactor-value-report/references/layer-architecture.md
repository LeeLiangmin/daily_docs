# 架构层

> 执行清单步骤 3 · 挖掘第一层：状态归属、依赖方向、模块边界、并发拓扑、扩展机制。
>
> 对象是**当前两份代码的结构**，不需要 git 历史。

**每条架构结论必须指向一个可数的东西或一段具体代码**：环的数量、直接访问字段的文件数、扇入、影响半径。写不出这类落点的结论（"边界更清晰了""耦合降低了"）删掉。

## 一、状态归属（先做这个）

**这个系统的状态存在哪里，谁能改？**

C 项目的架构问题大多以"全局可变状态"的形式存在，所以这一问产出最高。

1. 列出旧实现的全局状态：`g_` 前缀变量、文件级 `static`、单例、进程级注册表、全局配置。`grep -rn "^static \|^[a-z_]* \*g_" src/`
2. 对每一个问：谁写它？谁读它？写入点分散在几个文件？有无并发保护？初始化时机由谁保证？
3. 在新实现里找对应物，通常三种下场：
   - **变成了值**，由调用方构造并传递（最常见，也最有价值）
   - **仍是全局**，用 `OnceLock`/`static` 表达（说明这处确实需要全局，如实写）
   - **消失了**，设计变了不再需要（价值最高）

**把因果链写全**：全局可变状态同时导致初始化顺序约束、测试无法并行、并发保护的必要性、依赖关系不可见。一条结论带出这四项，写成一节；不要拆成四条并列的改进。

**取证**：全局状态数量（旧 N → 新 M）；每个的写入点分布；测试能否并行运行。

## 二、依赖方向

**模块之间谁依赖谁，有没有环？**

C 项目的依赖是隐式的：除 `#include` 外，全局变量、extern 函数、回调注册都构成依赖，而后几种在依赖图上不可见却真实存在——**它们往往才是环的来源**。

- 有图谱工具：直接查依赖图与环
- 没有：`clang -H` 导出头文件包含关系，再手工补上隐式依赖
- Rust 侧：crate 间天然无环（cargo 强制），模块级用 `cargo modules structure`

**"新实现没有循环依赖"这句本身不用写**，cargo 强制无环。要写的是为了拆成无环 crate 而做的设计决策：哪些东西被提取成公共层？哪些双向依赖被改成单向 + 回调/事件？

**取证**：依赖环数量；被最多模块引用的头文件（"上帝头文件"）；crate 划分与依赖方向。

## 三、模块边界

**一个模块的内部状态，外部能不能直接碰？**

1. 找出核心数据结构（`rank_core_symbols.py` 第一张表）
2. 数有多少个文件直接访问了它的字段，而不是通过函数
3. 新实现里对应类型的字段是 `pub` 还是私有？访问是否通过方法？
4. 有没有构造函数校验——**"一经构造即合法"是模块边界的强形式**，值得单独讲

**判断口径**：旧实现若靠"头文件里不暴露定义"，那是**可见性隐藏**，能被绕过（谁都能自己写一份 struct 定义）；新实现若是私有字段 + 构造校验，那是**类型强制**，绕不过去。

**取证**：直接字段访问的文件数（旧 vs 新）；`pub` 字段占比；有构造校验的类型数量。

## 四、并发拓扑

**有几种线程，它们之间怎么通信，谁能碰谁的数据？**

1. 画出旧实现的线程拓扑：几个线程/线程池、共享哪些状态、用什么同步
2. 找出"这个字段只在 X 线程访问"这类约定（grep 注释，或问团队）
3. 新实现仍是共享内存 + 锁，还是改成了消息传递？哪些数据被 `Send`/`Sync` 约束标记？
4. **关注拓扑本身的变化**：从"多线程共享一个大状态"变成"每个连接一个 task + channel"，是架构级重构，不只是"用了 Mutex"

**注意**：Rust 不防死锁与逻辑竞态，不要算进优势。

**取证**：锁的数量与粒度；共享状态数量；channel/actor 使用；`unsafe impl Send/Sync` 数量（有的话是重点审查区，如实写）。

## 五、扩展机制

**新增一种协议/编解码器/后端/状态，要动多少地方？**

这一问直接对应变更成本方面，也最容易拿到硬证据。

1. 找出旧实现的扩展点：函数指针表、注册表、`switch` 分发、`#ifdef`
2. 新实现的扩展点是什么？trait 的必填方法？枚举的穷尽匹配？
3. 判断关键：**新增时，编译器会不会告诉你还有哪里要改？**
4. 可选加权：`find_change_cost.py` 找"新增 X"后跟着"漏改 X"的 commit 对，补漏率就是这个缺陷的量化指标

## 写文档时

**每节开头一句粗体结论**，读者应能只读粗体句走完这一章。

**顺序**：先说新架构怎么组织、为什么这么组织，再说因此旧实现里的哪些问题失去了土壤。

照这个样子写：

> **新实现把连接表定成 `Mutex<Vec<Conn>>`，由 `Server` 值持有，而不是放在全局。** 这个选择有两层考虑：把数据关进锁里，访问路径就只有一条；由 `Server` 持有而非全局，则让每个测试能构造自己的实例。团队也考虑过 `static LOCK` + `static LIST` 的直译方案，放弃的原因是它只把旧结构搬了过来，锁与数据的绑定仍要靠人记。
>
> 这个结构一旦确定，旧实现里的一整类问题就失去了土壤。旧实现的连接表是全局变量 `g_conn_list`，保护它的 `g_conn_lock` 是另一个全局变量，绑定关系写在头文件注释里（`conn.h:18`）——任何模块都能直接遍历连接表而不加锁。新结构里"忘记加锁"不是会被检查出来，而是**不存在这个动作**：拿不到锁就拿不到数据。
>
> 连带收益：连接模块第一次可以被单独测试……

**分清"语言给的"和"设计做的"**：cargo 的无环依赖、模块可见性是语言给的（L1）；为适配它而做的层次划分是设计做的（L3）。两者都写，各自标注。

**架构层不贴大段代码**，贴的是结构：依赖图、状态归属表、线程拓扑图。代码留给 `evidence.md`。
