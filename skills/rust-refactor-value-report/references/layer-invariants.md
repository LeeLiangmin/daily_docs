# 不变性层

> 执行清单步骤 5 · 挖掘第三层：旧实现靠人维持的规则，在新实现里的归宿。
>
> 台账来源是**当前旧代码里的注释、断言、命名约定**，不是历史 commit。历史违反次数只是"这条规则有多难维持"的佐证，没有历史记录不影响本层成立。

**不变量 = 程序在某点上必须成立、但语言不保证的事实。**

「访问这个字段前必须持有那把锁」「必须先 `init()` 再 `use()`」「这个 int 是索引不是 ID」「`buf` 与 `len` 必须一致」——C/C++ 里这些由**人**维持，编译器一无所知。

本层的作用是**给上两层做实证**：架构层说"状态归属变了"，设计模式层说"用值传递取代了全局注册表"，不变性层则证明——原来那三条必须靠人记住的规则，现在一条都不需要记了。

## 四种归宿

| 归宿 | 含义 | 怎么用 |
|---|---|---|
| **消失** | 结构变了，这条规则不再需要存在 | 价值最高，优先展开 |
| **编码进类型** | 违反它编译不过 | 主力证据 |
| **变成运行时检查** | `assert!`、构造校验、返回 `Err` | 部分改进，说明"仍可能运行时失败" |
| **仍是注释约定** | 换了语言但约定没变 | 写进"代价与局限"，也是团队下一步该改的地方 |

**在文档里点破"消失"与"编码进类型"的区别。** 以「访问 `g_conn_list` 前必须持有 `g_conn_lock`」为例：

- 新实现是 `static LOCK: Mutex<()>` + `static LIST: Vec<Conn>` → 规则还在，只是编译器帮着查
- 新实现是 `Mutex<Vec<Conn>>` → **规则消失了**，不存在"忘记加锁"这个动作

**归宿是"消失"的优先展开写**：它来自设计决策，而非语言特性的直接应用。

**第四种如实列出**，放进"代价与局限"。它们同时是团队下一步该改的地方。

## 根因分组

**同一个设计选择往往同时产生多条不变量。**「parse 前必须先 init」「register 必须在 init 之后」「g_table 未初始化时不可访问」——三条全部源自"注册表是全局可变状态"这一个决策，改成值持有后三条一起消失。

填台账时给每条标一个分组编号，**填完看哪个分组条目最多，那就是最值得展开写的一节**。单条不变量是轶事，一组同根因的不变量才是设计决策。分组不必提前设计，边填边归。

## 怎么找（按效率排序）

1. **grep 约定型注释**：`必须`、`不要`、`仅`、`只能`、`需先`、`调用方`、`注意`、`确保`、`前提`、`must`、`should`、`caller`、`before calling`、`do not`、`ensure`、`assumes`、`requires`。唯一能机械执行的，先做。
2. **看断言**：`assert`、`BUG_ON`、`abort` 每一处都是显式写下的不变量，比注释可靠——写断言的人当时是认真的。
3. **看必须配对的函数名**：`init`/`destroy`、`lock`/`unlock`、`begin`/`end`、`acquire`/`release`。
4. **看字段之间的协同关系**：`buf` 与 `len` 必须一致、`state` 与 `fd` 必须匹配、两数组必须等长。这类往往没有注释，只能靠读逻辑发现，但价值很高。
5. **直接问团队**：「这块代码有什么坑是新人一定会踩的？」回答几乎都是不变量，而且是最痛的那些。
6. **看反复出现的历史缺陷**（可选）：某个 bug 反复出现，背后通常有条难以维持的不变量。

## 台账

工作底稿，**只进附录，不进正文**：

| # | 不变量（旧实现原话） | 旧位置 | 谁维持 | 新位置 | 归宿 | 承载机制 | 根因组 | 备注 |
|---|---|---|---|---|---|---|---|---|
| 1 | 访问 g_conn_list 前必须持有 g_conn_lock | conn.h:18 | 注释+人 | conn.rs:56 | 消失 | `Mutex<Vec<Conn>>` | G1 | 同一约定在 4 处被重复叮嘱 |

「备注」栏记**同一条约定被重复叮嘱的次数**。这个数字用来在正文里说明这条规则有多难维持——没有它，读者会觉得"不就是加个锁吗"。

## Rust 承载不变量的机制

| 机制 | 能表达什么 | 旧实现里的形态 |
|---|---|---|
| 所有权 / 移动 | 唯一持有、用后失效 | "调用方负责释放"、"调用后本对象失效" |
| 借用规则 | 别名与可变性、引用不悬垂 | "这期间不要修改它" |
| `Send` / `Sync` | 跨线程移动/共享的安全性 | "只能在 IO 线程调用" |
| `Mutex<T>` | 访问必须持锁 | "访问 X 前必须持有 Y" |
| `Result` + `?` | 错误必须被处理 | "记得检查返回值" |
| 枚举 + 穷尽 match | 状态空间封闭 | `#define` 常量 + `switch` |
| newtype | 语义区分（ID vs 索引、已校验 vs 未校验） | 都是 `int`，靠命名 |
| typestate | 操作顺序、状态相关的能力 | "必须先 init"、"握手后才能发" |
| 私有字段 + 构造校验 | 一经构造即合法 | 构造后再逐个校验、或不校验 |
| `NonZeroU32` / `NonNull` | 值域约束 | 用 0/NULL 当哨兵 |
| `Drop` | 资源在所有路径上释放 | `goto cleanup` |
| const generics | 长度与缓冲区一致 | `buf` + `len` 两个参数 |

**前六项在任何 Rust 项目里都一样**（语言给的）；**后六项体现团队对自己业务的判断**（设计做的）。后者更值得展开写——它讲的是你们的设计，不是 Rust 的教程。

## 写文档时

每个根因组按这个顺序写：**新实现的哪个设计决策 → 因此这几条规则同时失去了存在的必要 → 这几条规则原来有多难维持**（重复叮嘱次数、历史违反次数）。

历史违反次数用于支撑第三段的"难维持"，不单独成段。
