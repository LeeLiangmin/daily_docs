# Rust 价值清单（正向扫描）

> 执行清单步骤 4 之后做一遍。其余各层从**旧代码**出发找差异，本文从**Rust 的能力**出发逐项核对，两个方向交叉才算扫全。

其余各层只能找到在 C/C++ 侧留下痕迹的优势。**旧代码里没有对应物的那些——行为层面的、旧实现因为不敢而根本没做的、生态复合的——只有正向扫才能发现。**

## 怎么用

逐项过一遍，每项判三种结果之一：

- **兑现了** → 按"取证"一栏找本项目证据，进对应的方面
- **没兑现** → 记下来，写进文档的"代价与局限"或"后续可做的"
- **不适用** → 跳过（例如纯计算库不涉及并发）

**"没兑现"要如实写。** 一份只报喜的清单可信度低；写出"这次迁移没吃到 Rust 的哪几项优势、为什么"，反而让兑现的部分更可信。

**每一项都要有本项目证据。** 没有证据的条目不写进文档——那是 Rust 宣传册，不是价值分析。

---

## A. 编译期保证

价值形态：某类错误从"运行时才发现"变成"写不出来"。归因 **L1**，最容易论证，也最容易写成教科书。

| 能力 | 取证 | 归入方面 |
|---|---|---|
| 所有权与借用 | 旧实现里手工生命周期管理的机制有多少（`CopyString` 类、引用计数字段、地址区间判归属）；新实现的对应物 | 1、6 |
| `Send`/`Sync` | 旧实现里"只能在 X 线程调用"的约定有几处；新实现靠什么表达 | 1 |
| `Result` + `#[must_use]` | 旧实现里未检查返回值的调用点数量 | 1、7 |
| 穷尽 `match` | 旧实现里同类分发点的分布；新增类型时的历史补漏记录 | 1、2 |
| 生命周期标注 | 旧实现里"返回的指针在对象销毁后失效"这类文档警告出现几次 | 1、7 |
| 类型编码的不变量（newtype、typestate、私有字段+构造校验） | 不变量台账里"编码进类型"那几条 | 1 |

**常见误写**：「Rust 有所有权所以没有内存安全问题」。改成：旧实现的 X 机制（N 行、M 条纪律）在新实现里没有对应物，因为所有权关系由编译器验证。

## B. 零成本抽象与资源

价值形态：抽象不再需要用运行时开销换。

| 能力 | 取证 | 归入方面 |
|---|---|---|
| 泛型单态化 / trait 静态分发 | 旧实现为避免虚函数开销写了什么（宏展开、手写特化）；新实现是否统一 | 3、4 |
| 无 GC + 确定性析构 | 是否有延迟释放、对象池、内存水位控制这类机制在新实现中消失 | 4、6 |
| 零拷贝（切片、`Bytes`、`Cow`） | 旧实现里为生命周期安全做的防御性拷贝有几处；新实现是否消除 | 4 |
| 内存布局可控（`repr`、`NonZero` 的布局优化） | 是否用到；若用于 FFI 边界，说明取代了什么 | 4 |

**这一栏是少数不需要 benchmark 就能论证的性能收益**：指着代码说"这条路径原来有一次 memcpy，现在没有了"。**但不要据此推断整体性能**——没有实测就说没有。

## D. "敢做型"收益（行为层面）

**这一类是其余方法完全够不着的，也往往是团队感受最强的。** 价值不在代码里，在人的行为里：某件事以前不敢做，现在敢做了。

统一取证方法（三选二即可）：

1. **问团队**：「旧实现里有没有哪块代码是大家不敢碰的？新实现里同样的改动现在是什么体验？」
2. **看改动史**（有 git 历史时）：那块代码的改动频率是不是明显低于其余部分——**低不一定是稳定，也可能是没人敢动**
3. **看新实现的实际行为**：新实现有没有做过同类改动？靠什么保证没改坏——类型系统 + 测试，还是仍然靠人工审查

| 能力 | 具体形态 | 取证要点 | 归入方面 |
|---|---|---|---|
| 无畏并发 | 改并发代码从需要专家评审变为编译器可验证 | 另见 `layer-architecture.md` 4.2、4.3：还要挖旧实现**为回避并发付出的代价**（大锁、防御性拷贝、per-thread 状态、整块单线程） | 2、7 |
| 无畏重构 | 改类型/接口后编译器列出所有待改点 | 找一次新实现里的真实结构性改动，对比旧实现同类改动的做法（grep + 祈祷 vs 编译一次） | 2 |
| 无畏升级依赖 | 依赖升级后编译期发现不兼容 | 旧实现里 vendored 的第三方源码有多少、升级一次要改几处；新实现是不是一条命令 | 5 |
| 无畏优化 | 改数据结构不怕破坏正确性 | 新实现有没有做过性能相关的结构改动，靠什么保证行为不变 | 2、4 |

**措辞注意**：写「数据竞争在新实现里写不出来」（准确），不要写「新实现没有并发问题」（死锁与逻辑竞态照旧存在）。

## E. 旧实现因为不敢/不能而没做的事

**反向发现**：不看旧代码里有什么，看**新实现敢做而旧实现没做**的事，回头问为什么没做。

逐项问：

- 新实现用了并行的地方，旧实现是串行的吗？为什么——不需要，还是不敢？
- 新实现抽象出的东西（trait、泛型），旧实现是复制粘贴的吗？为什么不抽象——是不是在 C 里抽象的代价太高？
- 新实现引入的依赖，旧实现是自己造轮子的吗（自研日志、自研 UTF-8 编解码、自研容器）？为什么自研？
- 新实现开着的检查（clippy、`deny(warnings)`、sanitizer、fuzz），旧实现开了吗？没开是因为噪音太大还是接入成本太高？

**"因为不敢所以没做"这类代价不在代码里，只能这样反推出来**，而它往往比"少了几个 bug"更能说明问题——它衡量的是一整类做法当年不可行。

## F. 生态与工具链

价值形态：某件工程动作的接入成本从"要立项"降到"一条命令"。归因多为 **L2/L3**，如实标注。

| 能力 | 取证 | 归入方面 |
|---|---|---|
| cargo + lockfile | 旧实现升级一个依赖要改几处、出过版本不一致事故吗 | 5 |
| 内置测试 / doc test | 写一个新测试要改几个文件；doc test 保证示例不过期——旧实现的文档示例编译过吗 | 5、7 |
| `cargo-fuzz` / property test | 接入成本对比（旧实现手搭 libFuzzer 的代码量） | 5 |
| clippy / `deny(warnings)` | 旧实现开了哪些 warning、多少被 suppress | 5、7 |
| 交叉编译 | 旧实现的平台条件分支有几处；新实现几条命令 | 5 |
| `cargo-audit` / 语义化版本 | 供应链审计手段的有无 | 5 |
| features 取代 `#ifdef` | 旧实现的 `#ifdef` 组合数；有多少组合从未被编译过 | 3、5 |

**别把这些全归到"Rust 的优势"**——多数是生态与工具链成熟度（L2/L3）。但它们是"为什么是 Rust"的真实组成部分，值得写，只是要标对来源。

## G. 边界与长期风险

| 能力 | 取证 | 归入方面 |
|---|---|---|
| `unsafe` 隔离审计面 | 新实现 `unsafe` 的数量与分布——**这同时是代价一节的内容**，主动披露 | 1 |
| FFI 边界显式 | 保留 FFI 时，边界处的检查与所有权约定写在哪 | 1 |
| 内存安全合规趋势 | 客户/监管是否有相关要求 | 6（对管理者受众尤其有效） |
| 人员储备 | **双刃剑，两面都写**：吸引力 vs 招聘难度 | 代价一节 |

## 扫完之后

产出两份东西：

1. **兑现清单**：每项配本项目证据，分派到对应方面，进主体章节
2. **未兑现清单**：写进"代价与局限"或"后续可做的"

再做一次检查：**兑现的项是不是集中在 A（编译期保证）？** A 类最好挖、工具最多，但它也最容易写成教科书。D（敢做型）、E（不敢做的事）、F（生态）通常才是团队感受最强、评审最买账的部分——**如果这三类一条都没挖到，说明正向扫没做透，回去重来**。
