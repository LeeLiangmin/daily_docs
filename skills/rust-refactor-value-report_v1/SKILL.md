# Rust 重构价值分析报告

产出一份详细文档，论证 Rust 实现相对当前 C/C++ 实现的优势，以及为此付出的代价。

## 目标与主线

**把今天的 C/C++ 代码和今天的 Rust 代码摆在一起比。** 每条价值点都要能落到这个句式上：

> **今天这份旧代码里，这类问题仍然写得出来；新代码的结构让它写不出来。**

git 历史、缺陷记录、静态计数是可选的加权手段。用法是反向查证：**先从当前代码看出差异，再去历史里找它是否兑现过**。找到了，论据从"结构上更好"升级为"这里出过 N 次事故"；没找到就不写，不影响结论成立。没有 git 历史的项目照样能做。

**优势来源不限**：语言给的、新架构给的、生态给的都算，用归因标注区分来源即可。

## 五条铁律

违反任何一条，文档就废了。

**1. 主语是新设计。** 随便翻开一段，主语应该是新实现的某个设计选择，旧实现出现在句子里是作为对照。讲新设计的字数不少于讲旧问题的字数。每条价值点都要回答"新设计是怎么想的"——为什么选这个结构、还考虑过什么、为什么没选。

**2. 结论前置。** 文档第一屏必须让读者知道这次重写值多少钱：一句话总结 → 三条核心结论 → 一行代价 → 然后才是背景与范围。**绝对不要用被砍功能清单开头。** 每节同样以一句粗体结论开头，读者应能只读粗体句走完全文。

**3. 证据可查。** 每条价值点指向具体文件与行号。不编造性能数字、事故记录、旧代码里不存在的写法；没有的数据就说没有，并说明为什么没有。反推出来的设计意图必须标明是推断，不要冒充作者原话——评审席上可能坐着当初写代码的人。

**4. 代价必须写。** 功能断层、性能退化、`unsafe`/`unwrap` 自查数字、新实现自身的瑕疵、学习曲线与供应链。集中在一节，前面各节只留一句话。**只讲好处的文档，懂行的人第一反应是不信；主动认账是可信度的来源。**

**5. 给眼睛留节奏。** 行号引用放段末括号而非嵌在句中；至少一个视觉锚点（数据流骨架图）；连续三段纯文字要插代码或小表；表格只用于同类项汇总与附录。台账、评级、对应关系表是工作底稿，不进正文。

## 两个轴

**方面**回答"这是哪一类优势"，**层**回答"挖到多深"。两者正交——一条架构层的发现可能同时属于变更成本与正确性两个方面。

### 优势的六个方面（内容轴）

| 方面 | 核心问题 |
|---|---|
| 1 正确性与安全性 | 今天这份旧代码里，哪类错误仍然写得出来？新实现靠什么排除？ |
| 2 变更成本 | 改一处要付出什么代价？谁保证没改漏？ |
| 3 表达力与抽象 | 有没有旧语言根本写不出来、或代价高到没人写的设计？ |
| 4 性能与资源 | 同样的活儿花了多少资源？ |
| 5 工程化与交付 | 从代码到上线，路径变了多少？ |
| 6 简化本身 | 一整套机制是不是不再需要存在了？ |

**方面 6 要单独扫一遍。** 忠实移植型的重写往往没有新类型可看，价值集中在"旧实现那套基础设施整个消失了"，跑 `find_vanished.py` 取证。

挑真正有东西的 3-4 个方面写。某个方面没有实质变化，如实说明。

### 挖掘的四个层次（深度轴）

| 层 | 挖什么 | 参考文件 |
|---|---|---|
| 一 架构 | 状态归属、依赖方向、模块边界、并发拓扑、扩展机制 | `layer-architecture.md` |
| 二 设计模式 | C/C++ 惯用法被什么 Rust 模式取代，消除了什么固有代价 | `layer-patterns.md` |
| 三 不变性 | 旧实现靠人维持的规则，在新实现里的归宿 | `layer-invariants.md` |
| 四 代码 | 具体对照，给上面三层做实证 | `evidence.md` |

**层与层是论证关系**：架构层给结论，设计模式层解释怎么落地，不变性层证明它被强制执行，代码层让读者亲眼看到。**一条价值点应当贯穿四层**；只停在第四层的，是 RAII、`Result` 这类教科书条目，不写。

## 怎么选出重要的点

两份代码不可能全比。**筛选的目的是排序，不是否决**：把候选排好，从上往下写，写到篇幅够为止。

重要性 ≈ **影响面 × 结构性 × 可感知后果**，相乘而非相加，任一项接近零就不重要。

- **影响面**：在主干数据流上吗？扇入多少？消失的机制被引用过多少次？公共 API 还是内部细节？
- **结构性**：只修好一处，还是让某类问题在新实现里没有容身之处？同一决策消除了几条不变量？
- **可感知后果**：对正确性、维护成本、交付速度、性能中的哪一项产生可描述的后果？说不出后果的多半是教科书条目。

**快速排序法**：主干数据流上的 → 成组的（同根因的一组不变量、一批同源消失的机制）→ 扇入高的 → 能说出后果的 → 其余按"删掉它文档会弱多少"。前三条基本决定主体章节写什么，**排最前的三条就是开篇那三条核心结论**。

排完做一次**分布检查**：是不是全落在同一个方面（通常是正确性）？是的话回去按其余五个方面各扫一遍——工具的偏向会让人系统性漏掉方面 2、5、6。

**不要用这些排序**：历史 bug 数量（衡量的是哪里出过事，不是哪里重要）、代码行数变化（少掉 900 行编码转换是范围决策）、Rust 特性的稀有度（有 typestate 不等于重要）。

## 归因

| 标注 | 含义 |
|---|---|
| **L1 语言强制** | 违反它编译不通过 |
| **L2 语言促成** | 旧语言理论上能做，但代价高到几十年来没人这么做 |
| **L3 重写红利** | 与语言无关，重新设计就能得到 |

**三档都是合法优势**，标注只说明来源。L3 的架构改进同样算这次重构的收益，只是不算在"Rust 这门语言"头上。

**写 L2 时补一句"为什么旧实现没这么做"。** 旧语言里能做到而实际没做，原因通常是代价高、不是默认写法、编译器不强制——把这个原因写出来，L2 才立得住。

归因在每节末尾写一次，不要每段都标（铁律 3 的密度要求）。

## 执行清单

按顺序执行。**每步的"完成标志"没达成，不要进入下一步。**

### 步骤 0 · 事实基线
- **动作**：确认两份代码路径、各自规模、功能范围是否一比一、受众、有无性能数据、有无 git 历史
- **分支**：拿不到代码 → 停下来向用户要；用户给不了 → 说明"没有代码只能给通用说法"，不要继续
- **完成标志**：能写出一句话说明"比的是哪两份代码、范围差异在哪"
- **参考**：`references/scope-and-core.md`

### 步骤 1 · 定位核心
- **动作**：跑 `rank_core_symbols.py --old <cpp-src>`，找主干数据流载体；对前 3-5 名做数据流四问；画两边骨架图；填功能对应关系表
- **分支**：旧实现 < 5 万行 → 可通读结构，跳过扇入排序；> 50 万行 → 先分域，选 1-2 个域
- **完成标志**：有一张两边对照的数据流骨架图 + 一份 5-8 项的深挖清单
- **参考**：`references/scope-and-core.md`

### 步骤 2 · 跑两个"新实现"脚本
- **动作**：
  ```
  scripts/find_vanished.py       --old <cpp> --new <rust>
  scripts/find_design_signals.py --new <rust>
  ```
- **动作**：把 `find_vanished.py` 的候选人工分三类——真消失（价值点）／改名（丢弃）／功能被砍（写进背景一节）
- **完成标志**：有一份"消失了什么"清单和一份"出现了什么"清单，各自已人工复核
- **参考**：`references/evidence.md`

### 步骤 3 · 架构层挖掘
- **动作**：按状态归属 → 依赖方向 → 模块边界 → 并发拓扑 → 扩展机制五项逐一比对当前两份代码
- **完成标志**：每条结论都指向一个可数的东西（环数量、直接访问字段的文件数、扇入、影响半径）
- **参考**：`references/layer-architecture.md`

### 步骤 4 · 设计模式层挖掘
- **动作**：对照模式库逐条确认旧实现是否存在该模式，找新实现的对应做法，回答设计意图五问
- **分支**：问不到设计意图（无档案、作者不在）→ 用反推五法，结论标明是推断
- **完成标志**：每条模式都写得出"固有代价"那一栏
- **参考**：`references/layer-patterns.md`

### 步骤 5 · 不变性层挖掘
- **动作**：grep 约定型注释 + 看断言 + 看配对函数名 + 看字段协同关系，填不变量台账；标根因分组
- **完成标志**：台账四种归宿都有条目（全是"编码进类型"说明没认真找第四种）；根因分组已标
- **参考**：`references/layer-invariants.md`

### 步骤 6 · 选点与排序
- **动作**：按影响面 × 结构性 × 可感知后果给候选排序；做方面分布检查
- **分支**：候选全落在正确性一个方面 → 回步骤 3-5，按其余五个方面各扫一遍
- **完成标志**：排最前的三条已确定，它们就是文档开篇的三条核心结论
- **参考**：本文「怎么选出重要的点」

### 步骤 7 · 代码对照取证
- **动作**：为每条留下的结论配一组对照；跑 `code_metrics.py` 做反向自查（unsafe/unwrap/clone）
- **完成标志**：每组对照都能填完"旧实现靠 ___ 维持正确性，新实现靠 ___ 维持正确性"
- **参考**：`references/evidence.md`

### 步骤 8 · 佐证加权（可选）
- **动作**：跑 `find_change_cost.py`、`mine_fix_commits.py`，反向查证已有结论
- **分支**：无 git 历史或 commit message 质量差 → 跳过，在文档里说明佐证不足
- **完成标志**：引用的每个数字都已抽样复核，口径已记录
- **参考**：`references/evidence.md`

### 步骤 9 · 写文档
- **动作**：按开篇 → 背景 → 三个主体章节 → 工程化 → 性能 → 代价 → 附录的顺序写
- **完成标志**：八项交付前自查全部通过
- **参考**：`references/write-report.md`

## 卡住时怎么办

| 情况 | 做法 |
|---|---|
| 挖不出有分量的东西 | 回步骤 2，重点看 `find_vanished.py` 里扇入高的条目 |
| 候选全是 `Result`/`Option` 这类教科书条目 | 说明只挖了代码层，回步骤 3 从架构层重来 |
| 写出来像旧库的缺陷清单 | 违反铁律 1，检查每段主语；补设计意图五问 |
| 新实现没有 newtype/typestate/trait 可写 | 正常，忠实移植型重写的价值在方面 6，以 `find_vanished.py` 结果为主 |
| 无 git 历史 | 跳过步骤 8，不影响其余步骤 |
| 无设计档案，问不到"为什么这么设计" | 用反推五法，结论标明是推断 |

## 术语

| 术语 | 指什么 |
|---|---|
| **候选** | 挖掘阶段产出的未筛选发现，可粗糙、可推翻 |
| **价值点** | 经筛选与论证、确定写进文档的单元；文档每小节对应一个 |
| **结论** | 一个价值点或一章开头的那句粗体判断 |
| **方面** | 优势的六个内容类别 |
| **层** | 挖掘的四个深度，与方面正交 |
| **归因** | L1/L2/L3 三档来源标注 |
| **台账** | 不变量的完整清单，工作底稿，只进附录 |
