# 写文档

> 执行清单步骤 9 · 详细的叙述性文档。**能不能读，比挖得全不全更容易出错**——先过一遍 SKILL.md 的五条铁律。

## 结构

顺序经过刻意安排，不要改。尤其不要把范围声明提到前面。

```
0. 开篇：一句话 + 三条核心结论 + 一行代价     ← 第一屏，决定读者是否继续
1. 背景与对比基准（压缩，含范围声明与骨架图）
2. 架构层面的改变        ┐
3. 设计模式的替换        ├ 主体，占七成以上篇幅
4. 不变量：从人到编译器  ┘
5. 工程化与交付
6. 性能与行为等价性
7. 代价与局限
附录 A 不变量台账 / B 功能单元对应关系 / C 证据索引
```

代码对照穿插在 2-4 中，不独立成章。

## 0. 开篇（最重要的一屏）

**一句话**：这次重写做了什么、结果是什么。用具体数字，不用形容词。

> 一个 20 年历史、2000 行、至今仍在修内存 bug 的 C++ 库，被重写成 1068 行、零 `unsafe`、且产生那些 bug 的机制在结构上不存在的 Rust 实现。

**三条核心结论**：每条一个粗体小标题 + 三到五句，**主语是新设计**。不多不少三条——多了记不住，少了显得单薄。它们就是选点排序里排最前的三条。

> **1. 一整套所有权基础设施消失了。** 新实现的数据模型是一棵所有权树，删除一个键就是一行 `shift_remove_index(idx)`。旧实现围绕"指针池 + 地址区间判归属"建了约 200 行专用机制和 5 条必须靠人维持的纪律，新实现的对应物是：没有。这 200 行不是被替换了，是失去了存在的必要。

**一行代价**：第一屏就承认最主要的取舍。读者看到你主动认账，才会相信前面的结论。

**不要在第一屏出现**：被砍功能的完整清单、统计口径说明、分析方法论。

## 1. 背景与对比基准

必须有，但**压到最短**。范围声明是防守性内容，作用是让后面的对比成立，不是卖点。

- 两边是什么、规模多少（注明统计口径）
- **功能范围是否一比一**——有增删必须说明，用几行概括 + 指向附录 B，不在正文铺开完整清单
- 分析的覆盖范围与证据来源
- **数据流骨架图**放这里，它是全文的地图

## 2-4. 三个主体章节

写法见各层文件。共同要求：

- **开头一句粗体结论**
- **段落顺序**：新设计是什么、怎么想的 → 因此旧实现哪一整套东西失去了必要 → 旧模式的代价有多大（用数字）→ 连带收益 + 代价 + 归因一句话
- **归因在一节末尾写一次**，不要每段都标
- 行号引用放段末括号，不嵌在句子中间
- 每章至少覆盖 SKILL.md 六个方面中的一到两个，全书 3-4 个方面有实质内容

## 5. 工程化与交付

依赖管理、构建与交叉编译、测试与 fuzz 接入成本、静态检查、交付物体积。**用具体数字和步骤**，不要写"更简单了"——写"跨平台构建从 N 步变成 1 步""CMake 平台分支从 N 处降到 0"。这一方面多为 L2/L3，末尾统一标注一次。

## 6. 性能与行为等价性

- 有实测：给方法、环境、负载、结论，**同时报不利的维度**
- 没有实测：明确声明目标是"以可接受的性能换取安全性与可维护性"，不要用定性论证冒充数据
- **可静态指认的部分单独列**（消除了哪条路径的拷贝/分配），正负都列
- 行为等价性：测试移植对应关系、差分测试、灰度、线上时长；没做过就说明当前验证手段的边界

## 7. 代价与局限

集中在这里，前面各节只留一句话。至少覆盖：

- 功能断层：哪些用户无法迁移
- 已知的性能退化
- 体检数字：`unsafe` / `unwrap` / `expect` / 被迫的 `clone`
- **新实现自身的瑕疵**：过时的注释、临时脚手架、签名别扭之类——**主动列出来，这是最能建立可信度的部分**
- Rust 的固有代价：学习曲线、人员储备、编译时间、供应链审计
- 本次分析的局限：证据缺口、统计口径

## 附录

- **A 不变量台账**：完整表格，含根因分组，四种归宿都列
- **B 功能单元对应关系**：含"旧有新无"的完整清单
- **C 证据索引**：commit 列表、脚本与参数、工具版本与查询语句、代码对照原文位置、已简化片段清单

**证据索引必须有。** 评审会有人想自己查，能查证和不能查证的文档，可信度差一个量级。

## 受众调整

默认内部技术评审，上面结构直接用。

- **管理者**：另写 2-3 页摘要，不贴代码，结论翻译成风险与成本语言（事故率、定位耗时、交付周期、人力成本）。**不要用同一份文档应付两类受众。**
- **对外发布**：删掉内部事故细节与人员信息，统计数字要么给全口径要么不给

## 交付前自查

按顺序过一遍，任何一条不过就回去改：

1. **第一屏**：读完前 30 行，读者知道这次重写值多少钱吗？还是在看被砍功能清单？
2. **主语**：随机翻三段，主语是新设计还是旧代码的缺陷？讲新设计的字数够多吗？
3. **设计意图**：每条主要结论都回答了"为什么这么设计、还考虑过什么"吗？没有的话它就是缺陷报告。
4. **方面分布**：主体章节是不是全落在正确性一个方面？
5. **诚实密度**：归因和自辩是不是每段都来一次？反驳预案全文超过三处了吗？
6. **节奏**：每节开头有粗体结论吗？有没有连续超过三段的文字墙？有骨架图吗？
7. **代价**：包含体检数字和新实现自身的瑕疵了吗？
8. **底稿残留**：正文里还有台账、评级表、对应关系表吗？应该都在附录。
