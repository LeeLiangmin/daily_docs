# 基线与核心定位

> 执行清单步骤 0-1 · 确定比什么、深挖什么。

## 步骤 0：事实基线

不看代码不动笔。先确认六件事：

1. **两份代码库路径**，以及各自规模（非空非注释行，`scripts/code_metrics.py` 直接给）
2. **功能范围是否一比一** —— 有增删必须在文档里说明，否则任何规模与性能对比都不公平
3. 模块划分与技术栈（是否保留 FFI/unsafe 边界，还是纯 Rust）
4. **受众** —— 决定深度与术语密度，见 `write-report.md`
5. 是否有性能数据、事故记录（没有不影响主线）
6. 旧仓库 git 历史是否完整（**可选**，只影响步骤 6 的加权手段）

**没有代码就先要代码。** 只凭语言特性写出来的是通用宣传，不是这份文档该有的东西。拿不到就明确说明"没有代码只能给通用说法，价值有限"。

## 步骤 1：定位核心

### 规模分流

| 旧实现规模 | 做法 |
|---|---|
| < 5 万行 | 通读结构，列模块清单，直接进架构层 |
| 5 万 – 50 万行 | 主干数据流法（下文） |
| > 50 万行 | 先分域，选 1-2 个域深挖，其余不碰，文档里写明覆盖范围 |

介于两档之间选更保守的——**读不完却假装读完了，比读得少但说清楚范围更糟**。

### 主干数据流法

大项目可能有 200 个模块，给它们排序本身就是不可能任务。但**主干路径只有一两条**：一个请求从进入到响应、一份数据从读入到落盘。追这条路径经过的代码，自动得到核心集合。

**1. 定位入口。** 旧实现里找 `main()`、事件循环、协议入口（`*_parse`/`*_handle`/`on_*`/`*_dispatch`）、回调注册点、对外 API。新实现同样找一遍。**两边入口形态的差异本身就是第一条发现**——比如旧实现是全局注册表 + `init()`，新实现是构造一个值传下去。

**2. 找数据流的载体。** 在 C 项目里，系统的核心通常不是某个函数，而是**那几个到处传递的 struct**。

```
scripts/rank_core_symbols.py --old <cpp-src> --repo <cpp-repo>
```

第一张表（数据结构扇入）前 3-5 名就是。有代码图谱工具（GitNexus 等）时以图谱为准，脚本是退路。

**3. 数据流四问。** 对每个核心载体问四个问题，答案差异几乎必然是重点：

1. **谁构造它** —— 一处还是多处？构造完成时不变量就成立了吗，还是要调用方再补几步？
2. **谁修改它** —— 多少地方能改？靠什么防止并发修改和非法状态？
3. **谁消费它** —— 读的地方有什么隐含假设？
4. **谁负责生命周期** —— 何时释放？释放后还有谁可能持有指针？

C 里的答案通常是"很多地方都能改，靠约定"；Rust 里是一条所有权链。**一条数据流的对比能同时打穿架构层、设计模式层与不变性层**，比孤立地对比八个函数有力得多。

**4. 画两边的骨架图。** 把主干路径压成一条链，逐段对照：

```
旧：recv(fd,buf) → parse(buf,len,&frame) → frame.payload 指向 buf 内部
    → dispatch(&frame) → handler(ctx,...) → free(buf)
    ⚠ payload 有效期依赖 buf，靠注释约定

新：read() → Bytes → Frame::parse(buf) → payload: Bytes（共享所有权、零拷贝切片）
    → registry.dispatch(&frame) → Codec::decode(&[u8])
    ⚠ 生命周期由引用计数保证
```

**这张图直接进文档**，是少数几个适合用图而非文字表达的地方，也满足铁律 5 对视觉锚点的要求。

### 深挖清单

三份排序取交集：高扇入（`rank_core_symbols.py`）× 改动频繁（`find_change_cost.py` 变更热点）× 有补漏史（同脚本的补漏对）。

**"高扇入 × 改动频繁"是重点的高发区**——既是核心又一直在改，说明这里的复杂度从未被结构化解决。

清单控制在 5-8 个功能单元。**规模变大不该让清单变长，只该让筛选更严格。**

## 功能对应关系表

工作底稿，摘要进文档的"背景与对比基准"：

| 功能单元 | 旧实现位置 | 新实现位置 | 对应关系 | 备注 |
|---|---|---|---|---|

**对应关系本身就是发现**：

- **一对多**（大文件被拆开）：拆分依据是职责还是类型？
- **多对一**（重复实现被合并）：旧实现为什么重复？常见原因是 C 里做泛型代价太高，于是复制粘贴——**若是这个原因，属于语言促成（L2），不是单纯的重写红利**
- **被第三方替代**（自研日志换成 crate）：追问旧实现为什么自研，常见原因是 C/C++ 引入依赖的成本高
- **旧有新无**（功能被砍）：**必须写进"背景与对比基准"**，否则对比不公平
- **新有旧无**：多属重写红利；若是测试、fuzz、benchmark，归到工程化方面

## 抽样与诚实声明

大项目一定读不完，**关键不是读全，而是说清楚读了什么**：

> 本次分析覆盖 X 模块的主干请求路径（约 N 行，占旧实现 P%）与扇入前 5 的数据结构。未覆盖：管理面、监控、离线工具链。结论适用范围限于已覆盖部分。

这句话不削弱文档，反而加强它——评审最反感"看起来全面但经不起追问"。大项目的不变量台账也不能声称穷举，改为"主干路径上已穷举"并给出比例。
