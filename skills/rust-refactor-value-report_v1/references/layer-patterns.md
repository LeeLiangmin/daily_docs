# 设计模式层

> 执行清单步骤 4 · 挖掘第二层：C/C++ 惯用法被什么 Rust 模式取代，因此消除了什么固有代价。
>
> 对象是**现存的旧代码**。判断固有代价时问的是：**今天这份 C/C++ 代码里，这类问题仍然写得出来吗？** 历史上是否踩过，是步骤 6 的加权文档，不是本层的前提。

这一层承载文档的主要篇幅：比架构层具体，比代码层有设计含量。

## 工作流程

对每一条模式：

1. 在旧实现里确认它**确实存在**（给出文件位置与出现次数）
2. 找到新实现里的对应做法
3. **追问设计意图**（见下节）——每条都要做
4. 论证**固有代价**：这种组织方式**必然**带来的问题，换个人写、写得再小心也躲不掉。写不出这一栏说明这条还没想透
5. 归因一句话，写在该节末尾

**先跑 `scripts/find_design_signals.py --new <rust>` 和 `scripts/find_vanished.py --old <cpp> --new <rust>`**：前者列出新实现出现了哪些设计信号，后者列出旧实现哪些机制没有对应物。两份清单是本层的入口。

## 设计意图五问

对每条模式补上新实现这一侧的五个问题：

1. **为什么选这个结构**？
2. **当时还有哪些选项，为什么没选**？
3. **这个选择让什么变得容易了**？（不只是"消除了 bug"，还有"现在可以并行测试了"这类）
4. **它顺带解决了什么当初没打算解决的问题**？（连带收益往往是最好的论据）
5. **为此付出了什么**？

**没有这五问的答案就不要写这一条。**

### 问不到答案时：从代码反推

项目没有设计档案（单次交付、无 git 历史、作者不在了）时，用下面五种方法反推。反推出的意图在文档里标明是推断。

1. **跑信号扫描。** `find_design_signals.py` 每条信号后附了"该问"的问题，那就是追问入口。**出现次数少的信号往往比多的更有价值**——一个 typestate 比二十个 `Result` 更能说明团队做过判断。它列出的**未出现信号**同样有用：旧实现有"必须先 init"这类约定而新实现没有 typestate，说明这条不变量可能仍是注释约定，属于"代价与局限"。
2. **看"本可以更省事却没那么做"的地方。** 直译旧实现永远最省事，哪里偏离了直译，哪里就有决策。旧实现是全局锁 + 全局表，直译就是 `static LOCK` + `static LIST`，而新实现写成 `Mutex<Vec<Conn>>`——**这个偏离本身就是意图**。
3. **看类型签名里的"多余约束"。** 能写 `&mut self` 却写了 `&self`、能返回 `T` 却返回 `Result<T>`、能用 `String` 却用了 newtype、能不加却加了 `Send + Sync`。问：这个约束挡住了什么？
4. **看新实现里不存在的东西。** 跑 `find_vanished.py`。旧实现有而新实现完全没有对应物的机制（缓存、对象池、回滚、引用计数、转换层）是最有分量的设计决策。反推路径：这个机制当初解决什么问题 → 那个问题在新结构下还存在吗 → 是什么结构变化让它消失的。
5. **问团队一个问题就够。** 只问：**"重写时最纠结、改了不止一遍的是哪个地方？"** 纠结点就是设计决策所在，而且作者一定记得自己的取舍。比问"你们架构怎么设计的"有效得多。

反推不出来的，诚实地只写结构与效果，不编造动机。

## 写进文档的段落顺序

**按这个顺序写**：

> **段 1**：新设计是什么、怎么想的（结构 + 意图五问的 1、2）
> **段 2**：因此旧实现里的哪一整套机制失去了存在的必要（这里才引入旧实现，作为对照）
> **段 3**：旧模式的代价有多大——用数字（重复叮嘱次数、扇入、补漏率）
> **段 4**：连带收益 + 代价 + 归因一句话

段 3 用于支撑段 1 的设计选择，篇幅上段 1、2 之和不少于段 3。

## 模式对照库

### 1. 全局注册表 + init() → 值持有的注册表

**旧模式**：全局变量存注册表，`xxx_init()` 填充它，所有使用方隐式依赖"init 已经跑过"。

**固有代价**：初始化顺序成为不可见的全局约束，谁先谁后靠人记；无法在同一进程存在两份配置不同的实例，测试因此必须串行或靠 `reset()` 互相清理；"未初始化"是必须在每个入口挡一次的非法状态；依赖关系不出现在签名里，读代码看不出谁需要什么。

**新模式**：注册表是值，由调用方构造后传递。`Registry::new()` 返回的东西一经构造就可用。

**消除了什么**：初始化顺序不再是全局约束，而是数据流的自然结果——没法使用一个还没构造出来的值。"未初始化"这个状态不存在，因此不需要在每个入口挡。测试可以并行。

**归因 L2**。C++ 也能做依赖注入，但 C 里全局单例是默认选择，而 Rust 里全局可变状态需要 `static mut` + unsafe 或 `OnceLock`，**成本高到人们自然会选择传值**。语言换掉了默认选项。

**取证**：grep `_init(`、`g_` 前缀、文件级 `static`；数有多少函数的注释写着"必须在 init 之后调用"。

### 2. 回调 + void* ctx → trait 对象 / 枚举分发

**旧模式**：`struct handler { void (*fn)(void *ctx, ...); void *ctx; }`，注册方与调用方约定 ctx 的真实类型。

**固有代价**：类型正确性完全靠约定，转错了没有任何提示，错误在运行时以 crash 或脏数据出现；ctx 的生命周期与 handler 无关联，注销顺序错了就是 use-after-free；无法表达"这个回调需要哪些能力"；调试器与 IDE 看不穿。

**新模式**：`trait Handler { fn on_event(&mut self, ev: Event) -> Result<...>; }`，实现者持有自己的状态；对封闭集合可用枚举分发。

**消除了什么**：ctx 变成 `self`，类型由编译器保证；生命周期与实现者绑定。trait 方法签名本身就是"这个扩展点需要什么"的文档，而且是编译器强制的文档。加 `Send + Sync` 约束就能表达"这个回调会跨线程调用"——旧实现里这句话只能写在注释里。

**归因 L1**（类型安全）+ **L2**（生命周期绑定）。

**取证**：grep `void *ctx`、`void *user_data`、函数指针成员。

### 3. 整数状态 + switch → 枚举 + 穷尽匹配 / typestate

**旧模式**：`#define STATE_X 1` 系列，状态存在 `int` 字段，分发靠散落各处的 `switch`。

**固有代价**：状态集合开放，任何 `int` 都能塞进去，非法状态可以被构造；新增状态时需人工找全所有分发点，**分发点越分散漏改概率越高，且随代码增长单调上升**；状态与数据分离，`state == READY` 时哪些字段有效只能靠注释；非法转移只能运行时挡，且每个转移点都要挡一次。

**新模式**：`enum State` + 穷尽 `match`；进一步用 typestate（`Conn<Handshaking>` / `Conn<Ready>`）把"只有 Ready 才有 send 方法"变成编译期事实。

**消除了什么**：状态集合封闭，非法值构造不出来。新增变体时**编译器把所有需要修改的地方列出来**——这是维护成本上的质变。用 typestate 时，非法转移与非法操作直接不可表达。

**这一条最容易讲出彩**，因为有可量化的历史证据：`find_change_cost.py` 找"新增状态/类型"后跟着的"漏改分支"commit，复发率往往是 100%。

**归因 L1**（穷尽性）+ **L2**（typestate 是团队设计选择）。

### 4. 错误码传播 → 分层错误类型

**旧模式**：函数返回 `int`，`-1`/errno 表示失败，调用方逐层检查并向上传。

**固有代价**：错误可以被无声忽略，编译器不管；错误信息在传播中丢失（底层知道是"文件不存在"，传到上层只剩 `-1`）；错误路径与正常路径在代码上纠缠，清理逻辑重复；无法表达"可重试"或"应上报"这类分类。

**新模式**：分层错误枚举（每模块一个 `Error` 类型），`#[from]` 做层间转换，`?` 做传播，`source()` 保留因果链；边界处（FFI、对外 API）再转换成错误码。

**消除了什么**：忽略错误需显式写出；根因可追溯；错误分类由类型承载，`match err { Retryable(_) => ..., Fatal(_) => ... }` 是穷尽的。**连带效果**：错误类型的分层结构强制你想清楚模块边界——哪些错误本层处理、哪些该上传。旧实现里所有错误都是 `-1`，这个设计问题被掩盖了。

**归因 L1**（must_use + 穷尽）+ **L2**（错误分层是设计选择）。

**取证**：`code_metrics.py` 的"疑似丢弃返回值的调用语句"计数、`goto cleanup` 数量、errno 密度。**反向自查**：新实现的 `unwrap`/`expect` 密度，高说明编译期保证被换成了运行时崩溃。

### 5. 锁与数据分离 → 数据关进锁里 / 消息传递

**旧模式**：`pthread_mutex_t g_lock;` 和 `struct data *g_data;` 是两个独立的东西，绑定关系写在注释里。

**固有代价**：编译器不知道这个绑定，任何人都能绕过锁访问数据；"哪把锁保护哪些数据"随字段增加逐渐模糊，最终没人说得清；忘记解锁、异常路径漏解锁是常态；锁的粒度无法从代码结构看出。

**新模式**：`Mutex<T>` 把数据关在锁里；更进一步用消息传递（channel/actor），共享状态本身消失。

**消除了什么**：这里要讲清一个区别——`Mutex<T>` 不是"编译器帮你检查有没有加锁"，而是**"忘记加锁"这个动作不存在了**。守卫的 `Drop` 让解锁不再是需要记得的事。用 channel 时连"共享"都不存在，数据竞争无从谈起。

**归因 L1**。Rust 最强的一条，值得展开写。

### 6. 手工生命周期管理 → 所有权树 + 显式共享点

**旧模式**：谁 `malloc` 谁 `free` 靠约定，跨模块传指针时所有权靠文档，复杂场景加引用计数字段。

**固有代价**：所有权语义不在签名里，读函数声明看不出调用后自己还能不能用这个指针；释放时机分散，改一处要检查所有持有方；引用计数手工加减，漏减泄漏、多减 UAF；对象图的形状无法从代码看出。

**新模式**：所有权是一棵树，`&`/`&mut` 表达借用，需要共享处显式用 `Arc`。

**消除了什么**：签名即契约——`fn take(x: T)` 与 `fn borrow(x: &T)` 的区别是编译器强制的。**更重要的是：`Arc` 出现的地方就是这个系统真正需要共享的地方**，数一数有几个 `Arc` 就知道对象图有多复杂。旧实现里这个信息完全隐藏。

**归因 L1**（借用检查）+ **L2**（把共享点显式化是设计收益）。

**注意**：`Rc`/`Arc` 循环引用仍会泄漏，不要把"不会泄漏"说死。

### 7. 宏泛型 / 复制粘贴 → 泛型 + trait bound

**旧模式**：`DEFINE_QUEUE(int, int_queue)` 这类宏展开，或复制一份改类型名。

**固有代价**：宏展开后的代码不可调试、IDE 不认、编译错误指向宏内部；每个实例化是独立一份代码，改动要同步多处；无法对类型参数施加约束；复制粘贴的版本各自演化，最终变成几份似是而非的实现。

**新模式**：泛型 + trait bound，一份实现覆盖所有类型，约束写在 `where` 里。

**消除了什么**：单一实现单一维护点；类型约束显式化。**架构上的意义是：C 缺乏泛型导致的重复实现往往是模块边界模糊的根源**——复制一份比抽象一层便宜，代码就会朝重复的方向长。

**归因 L2**（C++ 模板能做到；旧实现若已用模板则不成立，如实说明）。

### 8. 不透明指针 / pimpl → 模块可见性 + newtype

**旧模式**：头文件里 `struct foo;` 前置声明，实现藏在 `.c` 里；或 C++ 的 pimpl。

**固有代价**：封装靠"不给你看头文件"，一旦字段暴露就守不住；每次访问都要走函数调用，无法内联；需要额外的堆分配与一层间接；构造/析构必须成对的工厂函数，误用只能运行时挡。

**新模式**：模块系统 + `pub`/`pub(crate)`/私有字段；需要类型级区分时用 newtype。封装是编译期的，且零成本。

**消除了什么**：封装不再依赖"看不见"，而是"不允许"，且不需要额外间接层。**newtype 让"这个 u32 是连接 ID 不是索引"成为类型事实**，旧实现里这只是命名约定。

**归因 L1**（可见性强制）+ **L2**（newtype 是设计选择）。

### 9. 缓冲区 + 长度参数 → 切片 / 零拷贝共享

**旧模式**：`f(char *buf, size_t len)`，两个参数必须保持一致；解析时把数据 memcpy 到新缓冲区以延长生命周期。

**固有代价**：指针与长度可能对不上，这是缓冲区漏洞的经典来源；为生命周期安全而做的防御性拷贝是纯粹的性能损失；"这个指针指向那个缓冲区内部，那个释放后就不能用"只能写注释。

**新模式**：`&[u8]` 把指针与长度绑成一个值；需要延长生命周期时用 `Bytes` 这类引用计数缓冲，切片共享底层内存而不拷贝。

**消除了什么**：长度不匹配不可能发生；**防御性拷贝可以安全地去掉**，因为生命周期由类型系统保证——这是性能方面少见的、不需要 benchmark 就能论证的收益：指着代码说"这里原来有一次 memcpy，现在没有了"。

**归因 L1**（切片边界）+ **L2**（零拷贝架构是设计选择）。

### 10. 线程 + 共享内存 → Send/Sync 边界

**旧模式**：起线程，共享全局状态，靠约定划分"哪个线程能碰哪些数据"。

**固有代价**：线程模型只存在于文档和人的脑子里；"这个对象不是线程安全的"无法表达，误用在压力测试或生产环境才暴露；线程生命周期与它使用的数据的生命周期没有关联。

**新模式**：`Send`/`Sync` 让"能否跨线程"成为类型属性，编译器在传递点检查；作用域线程或 task 让线程生命周期与数据挂钩。

**消除了什么**：线程模型从文档变成类型标注。**新增跨线程使用时，编译器会拒绝那些不该跨线程的东西**——旧实现里只能靠 review 抓。

**归因 L1**。

### 11. ifdef 森林 → features + trait

**旧模式**：`#ifdef` 控制平台差异与可选功能，组合爆炸，某些组合从未被编译过。

**固有代价**：**未启用的分支不参与编译检查，长期腐烂**；组合数随开关数指数增长而 CI 只覆盖少数几种。

**新模式**：cargo features + trait 抽象平台差异；`#[cfg]` 仍存在但粒度更粗，各组合可被 CI 系统性覆盖。

**归因 L2/L3**。常被归到工程化，但它其实是架构问题——**ifdef 森林会渗透进业务逻辑，而 feature + trait 强制你把平台差异收拢到边界上**。

## 怎么判断还有没有漏挖

1. **旧实现里有没有"大家都知道要小心"的地方？** 那里通常有一个模式和它的固有代价。
2. **新实现里有没有旧实现完全没有的结构？** 追问它替代了什么。
3. **旧实现里有没有为绕开语言限制而生的东西？** 宏、`void *`、手写虚表、`container_of`、复制粘贴——每一个都对应一条模式。

挖到新模式时按本文格式补充：旧模式 → 固有代价 → 新模式 → 消除了什么 → 归因 → 取证。**"固有代价"是核心，写不出来说明这条还没想透。**
