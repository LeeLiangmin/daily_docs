# Writing Style: 中文优先、信达雅、避免模板膨胀

## 目标

最终报告应该像一篇优秀的技术设计评审或架构分析文章，而不是工具生成的审计清单。

核心原则：

> 分析更深，表达更短。

## 1. 中文优先

除非用户明确要求其他语言，正文默认使用中文。

保留英文仅限：

- Rust / C++ 关键字、类型、trait、API、symbol、代码；
- ownership、borrow checker、`Send` / `Sync`、RAII、ADT 等保留英文更准确的固定术语；
- 项目、库、工具、协议名称。

不要把可以自然表达的内容写成大段中英混杂。

推荐：

> 数据表示从“依赖底层缓冲区的指针视图”转为“由数据模型直接拥有的值”。

避免：

> Primary transformation 是 pointer-backed representation 到 owned semantic model。

## 2. 信：准确可信

- 事实、推断、counterfactual 不混写。
- 没有 bug/issue/test 证据时，不把“减少状态维度”写成“消除一类 bug”。
- 不把 feature removal 自动写成价值。
- 不把 modern C++ 能力抹掉，但也不让 hypothetical modern C++ 取代真实 legacy baseline。
- 不夸大 `Result`、`Send`/`Sync`、safe Rust、OOM、性能复杂度、测试 parity。
- Trade-off 与兼容性变化必须进入正文，而不是脚注式淡化。

## 3. 达：工程含义先于术语

先说明“发生了什么工程变化”，再补技术名词。

推荐：

> 旧实现删除字符串时必须先判断它来自主缓冲区还是动态分配区。这实际上是在手工维护指针来源（pointer provenance）。

避免：

> 旧实现存在复杂的 pointer provenance management mechanism。

优先使用因果句式：

> 因为 A，所以旧实现必须维护 B；新设计取消了 A，因此 B 不再需要存在。

这比列举多个孤立优点更容易理解。

## 4. 雅：凝练、自然、有层次

避免口号：

- “Rust 更安全”
- “Rust 大幅提升可维护性”
- “Rust 从根本上解决了所有问题”

推荐具体表达：

> 这次重构真正消失的，不只是几处 `delete[]`，而是围绕“指针必须持续有效”建立的一整套生命周期维护机制。

不要连续堆叠近义 bullet。能用一段完整因果叙述说清，就不要拆成五条。

## 5. 结构服务于理解

模板是辅助，不是必须逐项填写的表单。

### 核心案例

通常 3–5 个小节足够：

1. 为什么重要 / 旧设计问题
2. Before / After 代码与设计
3. 根本变化与消失的复杂度
4. 价值与 Rust 的作用
5. 必要的 trade-off / evidence

可以合并，不要求固定标题。

### Supporting finding

若价值密度低，使用一小段或一个紧凑表格即可。不要生成完整 Case。

### 避免重复

同一结论不要在以下位置原样出现多次：

- Executive Summary
- 价值地图
- Detailed Case
- Rust-driven findings
- Conclusion

每次再次出现时，必须提升抽象层级或加入新信息。

## 6. Transformation Thesis 的写法

执行摘要先讲“重构故事”，再列结论。

推荐结构：

> 旧系统为了满足某个历史约束，选择了某种表示/所有权/并发模型。这个选择又要求维护若干辅助机制和人工不变量。Rust 重构没有逐项翻译这些机制，而是改变了根模型，因此这些辅助机制整体失去存在必要。随后再说明 Rust 的 ownership、类型系统或并发模型如何推动或约束新的设计。

不要把 Executive Summary 写成 Rust feature 列表。

## 7. 代码展示

- 每个重要案例尽量有 Before / After。
- 只保留支持论证的关键代码，通常每侧 10–40 行。
- 省略日志、样板、重复分支时要明确说明。
- 代码后必须解释“这段代码证明了什么”，不能只贴代码。

## 8. 用词强度

优先选择与证据强度匹配的词：

| 证据情况 | 推荐措辞 |
|---|---|
| 源码直接可见 | “可以确认”“源码显示”“实现中明确……” |
| 结构性推断 | “这意味着”“可以推断”“主要影响是……” |
| 缺少动态验证 | “可能”“需要 benchmark / test 验证” |
| 只减少复杂度 | “减少状态维度/证明义务/维护机制” |
| 有真实 bug 证据 | “消除了/避免了该已知 failure mode” |

## 9. 最终自检

在提交报告前检查：

- 是否正文以中文为主？
- 是否能删掉 15% 的文字而不损失信息？如果可以，继续压缩。
- 是否有两个 Case 实际属于同一根因？
- 是否有 Supporting finding 被写得像 Major Case？
- 是否有“变化 = 价值”的偷换？
- 是否有同一结论重复三次以上？
- 是否每个重要 Rust 价值都有真实旧代码对照？
- 是否读者先理解工程问题，再看到 Rust 术语？

## 10. v0.6 收敛规则

### 一根因，一主案

同一根设计变化的多个后果，默认合并进一个核心案例。只有当某个后果改变了独立的公共契约、跨子系统边界或高风险 failure mode 时，才考虑单独成案。

### 不为“完整”保留章节

默认报告只需要六个概念区：执行摘要、系统 Before/After、核心案例、支持性发现、权衡/证据边界、结论。若某节没有新增判断，就删除或合并。

### 数字必须可复现

任何 LOC、symbol count、test count、call-site count 都写明口径。无法说明口径时，宁可写“涉及多个辅助函数/路径”，也不要给伪精确数字。

### 结论强度统一

全文对同一事实使用一致强度。执行摘要不能说“无法忽略错误”，正文却说“更难忽略”；优先采用较保守、技术上准确的说法。

### 少写形容词，多写因果

避免“显著、大幅、彻底、天然”等空泛强化词。若确实成立，用证据说明“具体少了什么、谁不再需要证明什么”。
