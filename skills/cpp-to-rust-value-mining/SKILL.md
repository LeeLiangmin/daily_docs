# C/C++ → Rust 迁移价值挖掘

把一次已完成的迁移，转化成一份**经得起技术评审追问**的价值论证。

**主线是读代码。** 价值点从两边真实代码的逐对比对中产生；git 历史、缺陷记录、静态计数都是佐证，用来给已经发现的差异加权，不是用来发现差异的。搞反了会有两个后果：漏掉大量从未引发过事故、但结构上确实改善了的地方；以及被 commit message 的质量绑架（真实项目里大量 message 是"fix bug""修复问题"，挖不出东西）。

## 核心原则：证据，不是宣传

读者通常是内部技术团队——他们知道 Rust 的宣传语，不需要再听一遍"内存安全"。他们会问的是：

- 这些改进是 Rust 带来的，还是**重写一遍**本来就会带来的？
- 你说的问题，旧代码里**真的存在**吗，还是理论上可能存在？
- 代价呢？编译时间、生态、团队学习曲线，为什么只字不提？

所以产出必须满足三条：**每条价值点指向具体代码位置**、**每条标注归因等级**、**主动列出代价**。做不到这三条的条目宁可删掉——一条经不起追问的结论会让整份材料打折。

**没有代码就先要代码。** 用户只问"Rust 比 C++ 好在哪"而没给出两份实现时，不要凭语言特性作答——那是通用宣传，正是本技能要避免的东西。先要仓库路径；拿不到就明确说明"没有代码只能给通用说法，价值有限"，再问能否提供代表性模块。

绝对不要：编造性能数字、编造缺陷记录、把从未在旧代码里出现过的写法说成"历史问题"、把教科书例子当成项目里的真实代码。没有的数据就说没有。

## 归因三级标注

每条价值点都要落到下面某一级，并在材料中显式标出：

| 等级 | 含义 | 判定标准 | 举例 |
|---|---|---|---|
| **L1 语言强制** | 这类问题在新实现里**写不出来**，不是"我们更小心了" | 违反它编译不通过 | use-after-free、数据竞争、未处理的错误分支、非穷尽的状态匹配 |
| **L2 语言促成** | 旧语言里理论上也能做，但代价高到实践中没人做；Rust 让它变成默认或低成本 | 旧代码里有同类尝试但不完整/退化了 | RAII 覆盖所有路径、把不变量编码进类型、无畏重构、零成本抽象替代宏 |
| **L3 重写红利** | 与语言无关，是重新设计带来的 | 用 C++ 重写一遍也能得到 | 模块拆分、命名、删除死代码、补文档 |

L3 **不要隐藏也不要包装成 L1**，如实标注反而加分——它证明你分得清因果，读者会因此更相信你的 L1 和 L2。可以在 L3 后面补一句"Rust 的类型系统让我们敢做这么大的改动"，把它和 L2 挂钩。

## 读代码的手段：不要只有 grep

grep 和 glob 能回答"出现了多少次"，回答不了"谁调用了谁""改这里会波及哪些地方"。而**模块边界与架构这一维度，只能靠结构化信息支撑**。按可用性优先选用：

**代码图谱 / 知识图谱工具**

- **GitNexus**：`npx gitnexus analyze` 在仓库根目录建索引（产出 `.gitnexus/`，基于 tree-sitter + KuzuDB），支持 C、C++、Rust。通过 MCP 暴露 `context`（某符号的调用者、被调用者、所属执行流）、`impact`（改动的影响半径）、`query`、`cypher`（自定义图查询）。**新旧两个仓库各建一次索引**，是第 1 步建立结构地图最快的办法。
  注意：需要 Node >= 18；大仓库先用 `--skip-embeddings`；索引会随 commit 变旧，用 `gitnexus status` 检查。
- 若环境不具备：C/C++ 用 `cscope`/`ctags`/`clangd`，或 `clang -H` 导出头文件依赖图；Rust 用 `cargo modules structure`、`cargo tree`、`cargo geiger`。

**用图谱能回答、grep 回答不了的问题**

- 旧实现里某个核心结构体被多少处直接访问了内部字段？新实现是多少？（可见性控制的实际效果）
- 旧实现的模块依赖有没有环？新实现的 crate 依赖是不是 DAG？
- 同一功能的调用链深度和跨文件跳转次数，两边各是多少？
- 改动一个核心函数，影响半径分别多大？（"可维护性"最接近可量化的证据）

**使用纪律**：图谱输出是**线索**，任何进入材料的结论都要回到源码确认；工具版本、索引时间、查询语句写进附录，否则评审无法复现。

## 执行流程

### 第 0 步：建立事实基线

不要在没看代码之前动笔。先确认：

1. **两份代码库的路径**，以及功能范围是否一比一对应（范围变了要说清楚，否则任何对比都不公平）。
2. 项目领域、规模、模块划分。
3. 是否存在 FFI/unsafe 边界，还是纯 Rust。
4. 旧仓库 git 历史是否完整（有则作为佐证源，没有也不影响主线）。
5. 材料给谁看、多长、什么形式。

缺口用简短问题补齐，一次别问太多。

### 第 1 步：建立结构地图与功能对应关系表

**这是主线的起点，也是最容易被跳过、跳过后整个对比就散掉的一步。**

先分别通读两边的结构（模块/文件/公共接口清单，有图谱工具就直接出依赖图），然后建立**对应关系表**：

| 功能单元 | 旧实现位置 | 新实现位置 | 对应关系 | 优先级 |
|---|---|---|---|---|
| 连接生命周期管理 | `src/conn.c` | `src/conn.rs` | 一对一 | 高 |
| 协议解析 | `parser.c` + `parser_util.c` | `protocol/` 模块 | 二对一 | 高 |
| 日志 | `log.c` | 换用 `tracing` crate | 被第三方替代 | 低 |

**对应关系本身就是发现**：一对多、多对一、被第三方库替代、旧有新无、新有旧无——每一种都值得追问为什么，其中往往藏着架构层面的价值点。

**优先读哪些**（时间总是不够，要有取舍）：

1. **核心数据结构及其生命周期管理** —— 所有权、资源、并发问题的集中地
2. **跨模块的公共接口** —— 所有权语义、错误语义、可空性的表达方式差异最明显
3. **并发相关代码** —— Rust 优势最集中、也最容易讲清楚的地方
4. **输入解析与边界处理** —— 越界、长度计算、不可信输入
5. **错误路径与清理逻辑** —— 旧实现里最脏、新实现里最干净的对比区
6. 纯计算逻辑优先级最低，两边往往差不多

### 第 2 步：逐对深读

对优先级高的每一对，按 `references/reading-checklist.md` 的八个维度提问。核心的一条主轴是：

> **这段代码的正确性，旧实现靠什么保证？新实现靠什么保证？**

左边填出来是"程序员记得"、"注释写了"、"约定"、"代码审查"、"运行时检查"，右边填出来是"编译器"、"类型系统"，就是一个价值点。两边填出来是同一类东西，就不是。

每读完一对，产出一条**差异记录**（不要边读边写材料，先记录）：

```
功能单元：<名称>
旧：<文件:行号> —— 正确性靠 <什么> 保证
新：<文件:行号> —— 正确性靠 <什么> 保证
差异类型：<接口语义 / 不变量表达 / 资源管理 / 错误处理 / 并发 / 状态表达 / 模块边界 / 扩展点>
初判归因：L?
待验证：<需要 git 历史或计数佐证的点>
```

差异记录是这一步的唯一产出，允许粗糙、允许重复、允许后面被推翻。**先攒够量再收敛**，不要读一处写一处结论。

### 第 3 步：聚类成价值主张

把差异记录按"差异类型"聚类。**反复出现的同类差异比单点差异更有价值**——单点差异是轶事，成类的差异才是结构性改进。

聚类后每条主张走一遍检查：

1. 证据是什么？（具体文件+行号，至少 2-3 处同类实例）
2. 归因哪一级？判定依据？（用 `references/defect-taxonomy.md` 的四个反问）
3. 反方会怎么反驳？把最强的反驳想出来，要么正面回应，要么降级或删掉。
4. 代价是什么？（这条改进换来了什么损失）

**通不过第 3 条的删掉。** 8 条经得起追问，胜过 20 条被现场问倒。

### 第 4 步：用佐证给主张加权（可选但很值）

到这一步才动 git 历史和静态计数，目的是回答"这个差异真的重要吗"：

- **git 历史**：用 `scripts/mine_fix_commits.py` 粗筛，再人工复核。**用法是反向查证**——已经从代码里发现"旧实现的锁和数据分离"，去历史里找有没有因此出过事故；找到了，这条主张就从"结构上更好"升级为"这里出过 N 次事故"。
  commit message 质量差时命中率会很低，**这不影响主线**，如实说明佐证不足即可。也可以改用 `git log -L` 追踪具体函数的修改史，比全库关键词扫描更准。
- **静态计数**：用 `scripts/code_metrics.py` 给主张配数字（`goto cleanup` 有几处、约定型注释有几条、丢弃返回值的调用有多少）。
- **图谱指标**：扇入数、依赖环、影响半径的两边对比。

三类佐证都是**线索**，引用前抽样复核，材料中注明口径。

### 第 5 步：挑选代码对照

代码对照是材料的视觉核心，**不是贴得越多越好**。选取标准：

- **同功能**：来自对应关系表里的同一对，否则对比不成立。
- **短**：单侧 30 行以内，超了截取核心并用 `// ...` 标注省略。
- **有结构性差异**：能一句话说清两边各靠什么保证正确。只是语法更简洁的，价值不大。
- **有代表性**：**不要**用旧实现里最烂的一段对比新实现里最好的一段。选取时说明为什么这段有代表性——被修改次数最多、扇入最高、或是核心路径。
- **真实**：可为可读性做最小化删减（去掉无关字段、缩短标识符），但不能虚构，须注明"已简化"。

统一格式呈现：

```
#### 对照 N：<一句话标题>

**旧实现**（路径:行号）
```c
// 代码
```

**新实现**（路径:行号）
```rust
// 代码
```

- **差异**：旧的靠 X 保证，新的靠 Y 保证
- **归因**：L1/L2/L3 —— 判定依据
- **佐证**：相关 commit / 出现次数 / 图谱指标（有则给，无则略）
- **代价**：无 / 具体是什么
```

默认 5-8 组；受众要"细看文档"就少而深（3-4 组），要"听讲三十分钟"就多而广（8-10 组每组一屏）。

### 第 6 步：证据缺口、性能与代价

**性能**：现场"那性能呢"几乎必问，沉默不是选项。没有 benchmark 数据时不要编也不要回避：

1. 明确声明本次迁移的目标是否包含性能。多数迁移是"等价性能下换取安全性和可维护性"——就这么说。
2. 若能低成本补：做**微基准**（挑 2-3 个热点函数），说清结论适用范围，不要拿微基准冒充整体结论。
3. 只能定性论证时，明确标注这是**语言特性推论而非本项目实测**，同时诚实提及可能变差的地方（边界检查、分配器行为差异、`Arc`/`clone` 使用不当）。

**行为等价性**：做过差分测试（旧实现当 oracle）、回归测试迁移、灰度对比，都写进去，这本身就是工程质量证据。没做过就如实说明当前验证手段和覆盖范围。

**代价与局限**：单独成节，至少覆盖编译时间、团队学习曲线与人员储备、生态成熟度（具体到实际依赖的库）、FFI/unsafe 边界的残留风险（**主动指出这里恰恰是新实现最该重点审查的地方**）、迁移的人力与机会成本、本次分析本身的局限。

## 受众适配

材料的深度和术语密度由受众决定，**先确认受众再动笔**：

- **内部技术评审**（默认）：完整走全流程。代码对照是主体，归因等级显式标注，代价一节必须完整，证据索引不能省。
- **管理者 / 非技术决策者**：**不要**贴代码对照。把 L1 结论翻译成风险与成本语言，配上定位耗时、影响面这类他们能感知的量。归因等级不外露，但心里要有。全文一页。
- **技术分享 / 博客**：保留 3-4 组最有冲击力的对照，案例讲透一个。统计数字要么给全口径要么不给。
- **PR / 提案**：重点放在代价与迁移成本，价值论证反而次要——这类读者的疑虑在风险侧。

同一批证据可支撑上面任何一种材料，但**不要用同一份文档应付不同受众**。

## 输出结构

默认按 `references/report-template.md` 组织。骨架：

```
## 结论摘要（3-5 条，每条带归因等级）
## 背景与对比基准（范围、规模、对应关系、公平性说明）
## 一、接口与不变量：运行时约定 → 编译期约束（代码对照，主体）
## 二、资源与错误处理
## 三、并发模型
## 四、模块边界与架构
## 五、工程化与可维护性
## 六、佐证：历史缺陷与静态指标
## 七、性能与等价性（含证据缺口说明）
## 八、代价与局限
## 附录：证据索引（代码位置、commit、计数口径、工具与查询、复现方式）
```

篇幅与受众匹配。**证据索引必须有**——能查证和不能查证的材料，可信度是两个量级。

## 脚本

两个脚本都服务于第 4 步的**佐证**，不是主线：

- `scripts/mine_fix_commits.py` —— 扫 git 历史，按缺陷类别归类 fix commit。
  `python scripts/mine_fix_commits.py --repo <旧仓库路径> [--since 2018-01-01] [--json out.json]`
- `scripts/code_metrics.py` —— 新旧代码库的客观计数对比。
  `python scripts/code_metrics.py --old <C/C++路径> --new <Rust路径> [--json out.json]`

输出都是**线索而非结论**，必须人工复核后才能写进材料。关键词与正则匹配有假阳性也一定会漏；引用计数时说明统计口径与复核比例。
