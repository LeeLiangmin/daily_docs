# C/C++ → Rust 迁移价值挖掘

把一次已完成的迁移，转化成一份**经得起技术评审追问**的价值论证。

## 目标

回答一个问题：**这次重构带来了什么竞争力？**

竞争力不是单一维度的。从六个维度系统地找，挑真正有东西的 3-4 个深挖（详见 `references/dimensions.md`）：

| 维度 | 核心问题 |
|---|---|
| 1 正确性与安全性 | 不变量由谁维持？ |
| 2 **变更成本与可维护性** | 改一处要付出什么代价？谁保证没改漏？ |
| 3 表达力与抽象能力 | 有没有旧语言根本写不出来的设计？ |
| 4 性能与资源 | 同样的活儿花了多少资源？ |
| 5 工程化与交付 | 从代码到上线，路径变了多少？ |
| 6 团队与风险 | 谁来维护、维护得动吗？ |

**不要只从维度 1 出发。** 它的论证最成熟、工具最锋利（不变量台账），因此最容易写过头——写完就交卷，材料会显得像 Rust 安全性宣传。**维度 2 对技术评审的分量往往超过维度 1**：评审席上的人每天真正头疼的是"这块代码没人敢动"。

某个维度确实没有实质变化，如实说"这次迁移在 X 维度上没有明显差异"——比硬凑可信得多。

### 维度 1 的主轴工具：不变量

维度 1 的核心问题展开就是：**这段代码的正确性，旧实现靠什么维持？新实现靠什么维持？**

C/C++ 里绝大多数不变量由人维持——写在注释里、靠命名暗示、靠 review 把关、或只存在于老员工脑子里，编译器一无所知。Rust 的语言特性几乎都能还原成同一件事：**把不变量从人的责任转移给编译器**。所以这一维最有力的表述不是"新实现更安全"，而是：**这条规则以前靠人记住，现在靠编译器；违反它的代码根本编译不过。**

方法见 `references/reading.md`。**但记住它只是六分之一。**

### 技术差异 ≠ 竞争力

每条留下的价值点都要能回答：**对谁、产生什么好处？**「锁与数据在类型上绑定」是技术表述；「这类并发故障不会再进生产环境，三年出过 2 次、每次定位 1-3 天」才是竞争力。翻译方法见 `dimensions.md` 末节。**没有翻译的技术差异，评审只会当成技术自娱。**

## 三条铁律

**1. 读代码是主线。** 价值点从两边真实代码的逐对比对中产生。git 历史、缺陷记录、静态计数都是佐证，用来给已发现的差异加权，不是用来发现差异的。搞反了会漏掉大量从未引发过事故、但结构上确实改善的地方，并且被 commit message 的质量绑架。

**2. 宁缺毋滥。** 目标不是证明"我们全面检查过"，而是让读者记住两三件事。逐条罗列会把真正精彩的发现淹没——读者翻到第 12 条时已经不看了，而你最好的那条可能排在第 15。**读得广，写得窄**：扫过几十处，进材料的只留少数几处。判断标准是「删掉它，材料会弱多少？」答案是"几乎没影响"就删。

**3. 证据、归因、代价，三者缺一不可。** 每条价值点指向具体代码位置；每条标注归因等级；主动列出代价。做不到的宁可删掉——一条经不起追问的结论会让整份材料打折。

**没有代码就先要代码。** 用户只问"Rust 比 C++ 好在哪"而没给出两份实现时，不要凭语言特性作答——那是通用宣传，正是本技能要避免的。先要仓库路径；拿不到就明确说明"没有代码只能给通用说法，价值有限"。

绝不编造：性能数字、缺陷记录、从未在旧代码里出现过的写法、拿教科书例子冒充项目真实代码。没有的数据就说没有。

## 四套标签（各管一件事，不要混）

全流程只用这四套标签，每条价值点最多同时带其中三个：

| 标签 | 回答什么 | 取值 | 用在哪 |
|---|---|---|---|
| **价值维度** | 这是哪一类价值？ | 1 正确性 / 2 变更成本 / 3 表达力 / 4 性能 / 5 工程化 / 6 团队 | 第 0 步圈定，第 3 步聚类 |
| **归因等级** | 这是谁的功劳？ | L1 语言强制 / L2 语言促成 / L3 重写红利 | 第 3 步，管**可信度** |
| **精彩度** | 值不值得单独讲？ | A 主角 / B 汇总 / C 丢弃 | 第 3 步，管**选材** |
| **不变量归宿** | 这条规则的下场？ | 消失 / 编码进类型 / 运行时检查 / 仍是约定 | 维度 1 专用，第 2 步 |

**三套评级彼此独立**：一条 L1 也可能只是 B 级（所有权防 use-after-free，人尽皆知）；一条 L3 也可能是 A 级（一次漂亮的模块重划）；维度 2 的条目常常是 L2 却是 A 级。判定细则见 `references/selection.md`。

另有一组**阅读切面**（八个，见 `reading.md`），那是看代码的角度，不是标签，不用记在价值点上。

## 执行流程

| 步骤 | 做什么 | 读哪个文件 |
|---|---|---|
| 0 | 建立事实基线、圈定要挖的维度 | 本文下方 + `references/dimensions.md` |
| 1 | 结构地图与功能对应关系表 | `references/mapping.md`（大项目改走 `at-scale.md`） |
| 2 | 逐对深读，产出差异记录 + 不变量台账 | `references/reading.md` |
| 3 | 按维度聚类、筛选、归因、翻译成竞争力 | `references/selection.md` |
| 4 | 用 git 历史与计数给主张加权（可选） | 本文下方 + `scripts/` |
| 5 | 挑对照、写材料 | `references/writing.md` |

**规模分流**：旧实现非空非注释行 **超过 5 万行**时，第 1 步不要按 `mapping.md` 通读结构列模块清单——那一步会直接失效。改走 `references/at-scale.md`：从主干数据流入手，用扇入排序定位核心，只追一条线而不给全部模块排序。

查阅型参考：`references/lookup.md` —— C/C++ 形态 ↔ Rust 机制 ↔ 归因 ↔ 精彩度 的统一对照表，第 2、3 步随时查。

**术语**：第 2 步的产出叫**差异记录**（散点、粗糙、可推翻）；第 3 步聚类筛选后叫**价值点**（成型、带标签、进材料）。两者不要混用。

### 第 0 步：建立事实基线

不要在没看代码之前动笔。先确认：

1. **两份代码库的路径**，功能范围是否一比一对应（范围变了必须说明，否则任何对比都不公平）
2. 项目领域、规模、模块划分
3. 是否存在 FFI/unsafe 边界，还是纯 Rust
4. 旧仓库 git 历史是否完整（有则作佐证源，没有不影响主线）
5. **材料给谁看**——决定深度与术语密度，见 `writing.md` 的受众适配
6. **圈定维度**：读 `dimensions.md`，判断这次迁移在哪 3-4 个维度上真的有东西。这决定第 1 步读什么代码、第 4 步取什么数据。**维度 4（性能）和维度 6（团队）常常需要代码之外的信息，趁这一步一并问清楚：有没有性能数据？团队规模与 Rust 熟练度？有没有合规方面的驱动？**

缺口用简短问题补齐，一次别问太多，只问会实质影响后续的。

### 第 4 步：佐证加权（可选但很值）

到这一步才动 git 历史和静态计数，目的是回答"这个差异真的重要吗"。**用法是反向查证**：已经从代码里发现"旧实现的锁和数据分离"，去历史里找有没有因此出过事故；找到了，这条主张就从"结构上更好"升级为"这里出过 N 次事故"。

- `scripts/rank_core_symbols.py --root <src> [--repo <仓库>]` —— **大项目定位核心**：数据结构/函数扇入排序，核心×热点交集
- `scripts/find_change_cost.py --repo <旧仓库>` —— **维度 2 专用**：补漏对、变更热点、变更耦合
- `scripts/mine_fix_commits.py --repo <旧仓库>` —— 按缺陷类别归类 fix commit（服务维度 1）
- `scripts/code_metrics.py --old <C/C++> --new <Rust>` —— 客观计数对比（含维度 5 构建系统）
- 图谱指标：扇入数、依赖环、影响半径的两边对比

commit message 质量差时命中率会很低，**这不影响主线**，如实说明佐证不足即可；也可改用 `git log -L` 追踪具体函数的修改史，比全库关键词扫描更准。

三类佐证都是**线索**，引用前抽样复核，材料中注明口径与复核比例。

## 读代码的手段：不要只有 grep

grep 能回答"出现了多少次"，回答不了"谁调用了谁""改这里会波及哪些地方"——而模块边界这一维度只能靠结构化信息支撑。

- **GitNexus**：`npx gitnexus analyze` 建索引（tree-sitter + KuzuDB，支持 C/C++/Rust），通过 MCP 提供 `context`（调用者/被调用者/所属执行流）、`impact`（影响半径）、`cypher`。**新旧仓库各建一次索引**，是第 1 步最快的办法。需 Node >= 18；大仓库先用 `--skip-embeddings`。
- 替代方案：C/C++ 用 `cscope`/`ctags`/`clangd`/`clang -H`；Rust 用 `cargo modules structure`、`cargo tree`、`cargo geiger`。

图谱能回答而 grep 不能的问题：核心结构体被多少处直接访问内部字段（可见性控制的实际效果）、模块依赖有没有环、调用链深度与跨文件跳转次数、改动核心函数的影响半径（"可维护性"最接近可量化的证据）。

**纪律**：图谱输出是线索，进材料的结论都要回源码确认；工具版本、索引时间、查询语句写进附录，否则评审无法复现。
