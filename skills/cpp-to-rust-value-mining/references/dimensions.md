# 价值维度矩阵

**上层框架。** 挖掘从这里开始：先确定这次重构在哪些维度上真的产生了价值，再决定深读什么、怎么论证。

不要只从一个维度出发。**不变量是最锋利的一把刀，但它只切"正确性"这一维**——性能、变更成本、表达力、工程化、团队与风险，都不是不变量问题，漏掉它们会让材料显得单薄，也会漏掉对评审分量最重的那几条。

## 六个维度速览

| 维度 | 核心问题 | 证据形式 | 常被低估？ |
|---|---|---|---|
| 1 正确性与安全性 | 不变量由谁维持？ | 代码对照、不变量台账、缺陷史 | 否，最常被过度使用 |
| 2 变更成本与可维护性 | 改一处要付出什么代价？ | 影响半径、编译器覆盖率、真实改动案例 | **是，对评审分量最重** |
| 3 表达力与抽象能力 | 有没有旧语言写不出来的设计？ | 代码对照、被消灭的重复/宏 | 是 |
| 4 性能与资源 | 同样的活儿花了多少资源？ | 实测数据、零拷贝路径、内存布局 | 否，但最容易翻车 |
| 5 工程化与交付 | 从代码到上线，路径变了多少？ | 步骤数、耗时、接入成本 | 是 |
| 6 团队与风险 | 谁来维护、维护得动吗？ | 上手周期、review 负担、合规趋势 | 是 |

**不必六个都写。** 挑真正有东西的 3-4 个，每个维度下再按精彩度筛（见 `selection.md`）。某个维度没有实质变化，如实说"这次迁移在 X 维度上没有明显差异"——比硬凑可信得多。

---

## 维度 1：正确性与安全性

**核心问题**：这段代码的正确性，旧实现靠什么维持？新实现靠什么维持？

这就是不变量问题，方法见 `reading.md` 的主轴部分和不变量台账。**这一维的论证最成熟、最难反驳**，但也最容易写过头——大部分人写完这一维就交卷了，材料因此显得像"Rust 安全性宣传"。

**归因注意**：死锁、逻辑竞态、业务逻辑错误不属于 Rust 的功劳。

**翻译成竞争力**：线上事故率、故障定位耗时、安全审计通过成本、CVE 暴露面。

---

## 维度 2：变更成本与可维护性

**核心问题**：改一处，要付出什么代价？谁能保证没改漏？

**这是被最严重低估的一维**，而它对技术评审的分量往往超过安全性——评审席上的人每天真正头疼的是"这块代码没人敢动"。

怎么挖：

- **补漏率（首选证据，可脚本化）**：跑 `scripts/find_change_cost.py --repo <旧仓库>`。它找的是这个模式——一个"新增 X"的 commit 之后不久，跟着一个"漏改了 X 相关的地方"的 commit。**这个比例就是复发率**，比任何描述性文字都有力：「三年新增 3 种帧类型，3 次全都跟着补漏 commit，其中一次是静默丢包」。复核每一对的 diff 后，去新实现看同样的扩展现在靠什么保证改全（枚举穷尽？trait 必填方法？还是仍然靠人）——这决定归因等级。
- **变更耦合**：同一脚本输出"总是一起被修改的文件对"。改 A 必须记得改 B、却没有任何机制保证，是维度 2 的典型痛点。看这层耦合在新实现里是否被类型或模块边界消化掉了。
- **变更热点**：改动最频繁的文件，既是深读优先级，也是"这块反复出问题"的量化依据。
- **影响半径**：同一个核心函数，两边的调用者数量与分布（用图谱工具的 `impact`）。
- **不敢动的代码**：旧实现里有没有"注释特别多、改动特别少"的区域？问团队"哪块没人敢碰"。新实现对应位置的处境。
- **重构信心**：新实现做过大改动吗？靠什么保证没改坏（类型系统 + 测试 vs 人工审查）。

**易犯错误**：写成"代码更清晰了"这种无法验收的话。必须落到具体改动的代价对比上。

**翻译成竞争力**：需求交付周期、改动引入回归的概率、技术债增速。

---

## 维度 3：表达力与抽象能力

**核心问题**：新实现里有没有旧语言**根本写不出来**、或代价高到没人会写的设计？

这一维和维度 1 的区别很关键：维度 1 是"写得更安全"，这一维是"写得出来"。

怎么挖：

- 旧实现里为绕开语言限制付出的代价：宏展开生成多份类型代码、`void *` + 函数指针表、复制粘贴的重复实现、手写虚表、`container_of`。新实现用泛型/trait 消除了多少？**统计被消灭的重复实现数量或宏行数。**
- 新实现里出现了旧实现完全没有的抽象：新 trait、typestate、newtype、迭代器组合、`impl Trait`。追问它解决了什么问题。
- 组合能力：旧实现要新增一种处理器/编解码器/后端，要改几个地方？新实现呢？

**归因注意**：旧实现若是 C++ 且已用模板与虚函数，这一维会大幅缩水，别硬写。

**翻译成竞争力**：新增功能的边际成本、支持新协议/新平台的速度。

---

## 维度 4：性能与资源

**核心问题**：同样的活儿，花了多少 CPU、内存、二进制体积、启动时间？

**最容易翻车的一维。** 评审对不严谨的 benchmark 最挑剔（同一台机器？同一负载？优化等级对齐了吗？），而 Rust 在这类迁移里往往持平或略胜，内存有时还更高。

怎么处理：

- 有实测数据：给方法、环境、负载、置信区间。**同时报不利的维度**，藏起来一旦被发现，整份材料都不可信了。
- 没有实测：明确声明本次目标是"等价性能下换取安全性与可维护性"，不要用定性论证冒充数据。若能低成本补，做微基准并说清适用范围。
- **可静态论证的部分**：新实现是否消除了某条路径上的拷贝/分配（`&str` 替代 `strdup`、切片替代复制、`bytes::Bytes` 零拷贝）——这类可以指着代码说，不需要 benchmark。这是这一维最稳妥的证据形式。
- 诚实提及可能变差的：边界检查、分配器差异、`Arc`/`clone` 用得随意。

**翻译成竞争力**：单机承载量、机器成本、P99 延迟、冷启动时间。

## 维度 5：工程化与交付

**核心问题**：从写完代码到上线，路径变了多少？

怎么挖（**必须落到具体数字和步骤**，不要写"更简单了"）：

- **依赖管理**：升级一个依赖要改几个地方？出过版本不一致事故吗？vendored 源码有多少行？
- **构建与交叉编译**：CMake/autotools 的平台分支有多少处？新实现交叉编译几条命令？构建耗时对比。
- **测试**：写一个新测试要改几个文件？doc test、property test、fuzz 的接入成本（`cargo-fuzz` vs 手搭 libFuzzer）。测试覆盖率变化。
- **静态检查**：旧实现开了哪些 warning、多少被 suppress？sanitizer 接入成本 vs clippy 默认能查出什么。
- **交付物**：二进制体积、运行时依赖、容器镜像大小。

**归因注意**：这一维大量属于 L3（换个构建系统也能改善）或 L2（cargo 是 Rust 生态自带的）。**如实标注，不要包装成语言优势。**

**翻译成竞争力**：发版频率、CI 时间与成本、支持新平台的周期。

---

## 维度 6：团队与风险

**核心问题**：谁来维护？维护得动吗？外部环境怎么看？

怎么挖：

- **上手路径**：新人接手旧实现要读多少前置知识（内存管理约定、锁的使用规范、宏体系）？新实现呢？有没有真实的新人上手数据。
- **review 负担**：旧实现的 code review 要人工检查哪些点（有没有漏 free、有没有漏加锁、返回值检查了吗）？这些里有多少现在由编译器负责？**这是一条很实在但常被漏掉的价值**。
- **人员储备与招聘**：这是双刃剑——Rust 对部分工程师有吸引力，但熟练者更难招。**两面都写**。
- **外部风险**：内存安全相关的行业与监管趋势、客户/合规方的要求、供应链审计。这一条对管理者受众尤其有效。

**易犯错误**：写成主观感受（"团队反馈更好写了"）。尽量落到可观察的事实：review 意见的类别分布变化、上手所需时间、招聘周期。

**翻译成竞争力**：人力成本、交付稳定性、合规与投标资格。

---

## 最后一步：翻译成竞争力

**技术差异不等于竞争力。** 每条留下的价值点，都要能回答：**对谁、产生什么好处？**

| 技术表述 | 翻译后 |
|---|---|
| 锁与数据在类型上绑定 | 这类并发故障不会再进生产环境（三年出过 2 次，每次定位 1-3 天） |
| 编译器覆盖所有调用点 | 加一个协议字段，从"改 8 处 + 漏 1 处"变成"改完就编译过" |
| 消除了一条路径上的拷贝 | 单连接内存占用下降，单机承载量提升 |
| cargo 管理依赖 | 升级依赖从半天变成一条命令，安全补丁跟进更快 |

两类受众要的翻译不同：

- **对产品**：更稳、更快、更省、上得更快
- **对团队**：改得动、不怕改、招得到人、review 更轻

写材料时，A 级价值点的每一条都要带一句这样的翻译；B 级汇总表可以只在表头统一说明。**没有翻译的技术差异，评审只会当成技术自娱。**
