# 聚类、筛选、归因

> 流程第 3 步

第 2 步攒下的是散点记录。这一步把它们变成少数几条经得起追问的主张。**顺序是先筛选、再论证**——对不该留的条目做归因论证是浪费。

## 一、按价值维度聚类

**先按价值维度分组，再在组内按差异类型聚类。** 分组后立刻做一次体检：

- 记录是不是几乎全落在维度 1？这是最常见的失衡。回第 2 步，带着维度 2、3、4 的问题再扫一遍——通常有素材，只是当时没往那个方向想。
- 哪些维度是空的？空得有道理（这次确实没动性能）就在材料里如实说明；空得没道理（根本没看构建和测试）就补。
- 最终进材料的维度控制在 3-4 个。**六个维度都写会摊薄，也很难六个都有真东西。**

组内聚类时：**反复出现的同类差异比单点差异更有价值**——单点差异是轶事，成类的差异才是结构性改进。不变量台账里同一"归宿"下的条目往往能合并成一条主张。

## 二、筛选：精彩度分级

**不要大水漫灌。** 材料的目标不是证明"我们全面检查过"，而是让读者记住两三件事。

### 什么算"值得对比"

按重要性排列，前两条最关键：

1. **一个决策消除了一整类问题**（结构性杠杆）。不是修好一个点，而是换了组织方式之后，某类问题**在新实现里没有容身之处**。这类发现最有价值，因为它体现的是设计判断，不是语言特性。
2. **非显然，有洞察**。读者看完会想"原来可以这样"。反面例子：「Rust 有 `Option` 所以不会空指针解引用」——任何人都能背出来，写进材料等于浪费读者注意力和你的可信度。

   **落到不变量上有个可操作的分水岭**：
   - **语言内建的不变量**（所有权、借用、`Send`/`Sync`、`Result`）每个 Rust 项目都一样 → 只配进 B 级汇总表
   - **团队自己定义的不变量**（typestate 表达操作顺序、newtype 区分语义、私有字段 + 校验构造器保证"一经构造即合法"、sealed trait 封闭抽象）体现的是你们对业务的理解，旧实现里想做也做不到 → **A 级素材的主产地**

   检验方法：**把它讲给另一个团队的 Rust 工程师，他学到的是"Rust 的特性"还是"你们的设计"？** 后者才是 A 级。
3. **旧实现里是真的痛**。反复出问题、人人绕着走、新人必踩、历次事故重灾区。痛点越具体，对比越有力。
4. **难以被简单模仿**。用 C++ 重写一遍也做不到，或代价高到没人会做。这一条同时也是归因判定的输入。
5. **有嚼头**。一句话说得清结论，但值得展开讲三分钟。一句话就讲完的塞进汇总表即可。

### 分级

- **A 级（主角，1-3 条足够）**：满足第 1、2 条。通常是架构或抽象设计层面的决策——重新划分模块边界、把某个团队自定义的不变量搬进类型系统（或让它彻底消失）、换掉一整套扩展机制。**有两三条 A 级就已经很强了。**
- **B 级（配角）**：改进确实成立，但属于按部就班的正确做法（RAII 覆盖清理路径、`Result` 替代返回码）。**不单独开节，成组汇总成表格**，用来支撑 A 级说明"这不是孤例"。
- **C 级（不进材料）**：教科书条目、语法层面的简洁、无关痛痒的差异。写进去只会稀释密度。

判断不了 A 还是 B 时问：**这条讲给一个熟悉 Rust 的人听，他会不会觉得有收获？**

**A 级多于三条时，把多的降为 B 级**——注意力被摊薄后，每一条的印象都会变浅。

## 三、归因：这是谁的功劳

技术评审最容易问倒人的一句话是：**"这些改进是 Rust 带来的，还是重写一遍本来就会带来的？"**

| 等级 | 含义 | 判定标准 | 举例 |
|---|---|---|---|
| **L1 语言强制** | 这类问题在新实现里**写不出来** | 违反它编译不通过 | use-after-free、数据竞争、未处理的错误分支、非穷尽状态匹配 |
| **L2 语言促成** | 旧语言理论上也能做，但代价高到实践中没人做 | 旧代码里有同类尝试但不完整/退化了 | RAII 覆盖所有路径、把不变量编码进类型、无畏重构、零成本抽象替代宏 |
| **L3 重写红利** | 与语言无关 | 用 C++ 重写一遍也能得到 | 模块拆分、命名、删除死代码、补文档 |

**L3 不要隐藏，也不要包装成 L1。** 如实标注反而加分——它证明你分得清因果，读者会因此更相信你的 L1 和 L2。可以在 L3 后补一句"Rust 的类型系统让我们敢做这么大的改动"，把它和 L2 挂钩。

### 判定 L1 前的四个反问

1. **新实现真的是这么写的吗？** 去代码里确认，不要凭语言特性推断。
2. **这里有 `unsafe`、`unwrap`、`transmute`、裸指针吗？** 有就降级或加限定条件。
3. **用现代 C++（智能指针、RAII、`std::optional`、`-Werror`）能不能同样做到？** 能，就是 L2 不是 L1。**这个反问最容易暴露虚高的结论。**
4. **旧代码里这类问题真的出现过吗？** 没出现过就不能写成"消除了历史问题"，只能写成"结构上排除了这类风险"——两者说服力不同，措辞要准确。

### 不属于 Rust 功劳的类别

挖到这些不要写进"Rust 消除了什么"：

- 业务逻辑错误、算法写错、边界条件想错
- **死锁、逻辑竞态、活锁**（Rust 不防，写了会被当场纠正）
- 配置错误、协议理解错误、对第三方行为的错误假设
- 性能问题（除非有实测数据支撑）
- 需求变更导致的返工

**如实排除比多列几条更能建立可信度。** 材料里可以显式给出排除说明：「本次统计中 X% 的历史缺陷属于逻辑与业务类，Rust 对这部分没有帮助。」——这句话会让读者相信剩下的那部分。

## 四、论证：留下的每条走一遍

1. **证据是什么？** 具体文件 + 行号，A 级至少 2-3 处同类实例
2. **归因哪一级？** 用上面四个反问
3. **反方会怎么反驳？** 把最强的反驳想出来，要么正面回应，要么降级或删掉
4. **代价是什么？** 这条改进换来了什么损失（更啰嗦？编译更慢？抽象更难懂？）
5. **翻译成竞争力**：对谁、产生什么好处？见下节

**通不过第 3 条的删掉。3 条讲透，胜过 20 条被现场问倒。**

**A 级要多问一层**：当时为什么这么设计？还考虑过什么替代方案？为什么没选？——这些才是让读者觉得"有收获"的部分，也是把一条改进讲成一个设计故事的关键。**缺了它，A 级会退化成 B 级。**

## 五、翻译成竞争力

**技术差异不等于竞争力。** 每条 A 级价值点都要带一句翻译，回答"对谁、产生什么好处"：

| 技术表述 | 翻译后 |
|---|---|
| 锁与数据在类型上绑定 | 这类并发故障不会再进生产环境（三年出过 2 次，每次定位 1-3 天） |
| 编译器覆盖所有调用点 | 加一个协议字段，从"改 8 处 + 漏 1 处"变成"改完就编译过" |
| 消除了一条路径上的拷贝 | 单连接内存占用下降，单机承载量提升 |
| cargo 管理依赖 | 升级依赖从半天变成一条命令，安全补丁跟进更快 |

两类受众要的翻译不同：**对产品**（更稳、更快、更省、上得更快）／**对团队**（改得动、不怕改、招得到人、review 更轻）。第 0 步确认的受众决定用哪一类。

翻译不出来的条目要警惕——**说不清对谁有好处，通常意味着这条其实是 C 级**。

## 完成标志

- 进材料的价值维度 3-4 个，且不是清一色维度 1
- A 级 1-3 条，每条有完整的设计故事、至少一组代码对照候选、一句竞争力翻译
- B 级归入 2-4 组汇总表
- 不变量台账四种归宿都有条目（全是"编码进类型"说明没认真找第四种）
- 每条都能回答"删掉它材料会弱多少"
