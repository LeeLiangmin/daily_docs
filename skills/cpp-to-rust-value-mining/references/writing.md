# 挑对照与写材料

> 流程第 5 步

## 挑代码对照

代码对照是材料的视觉核心，**不是贴得越多越好**。默认 3-5 组，**A 级主张每条配一组**，B 级共用汇总表不单独配图。贴到 8 组以上先自查：是不是把 B 级也当主角了。

选取标准：

- **同功能**：来自对应关系表里的同一对，否则对比不成立
- **短**：单侧 30 行以内，超了截取核心并用 `// ...` 标注省略。太长读者会跳过
- **有结构性差异**：能一句话说清两边各靠什么维持正确。只是语法更简洁的价值不大
- **有代表性**：不要用旧实现里最烂的一段对比新实现里最好的一段。选取时说明为什么这段有代表性——被修改次数最多、扇入最高、或在核心路径上
- **真实**：可为可读性做最小化删减（去掉无关字段、缩短标识符），但不能虚构，须注明"已简化"

统一格式：

```
#### 对照 N：<一句话标题>

**旧实现**（路径:行号）
```c
// 代码
```

**新实现**（路径:行号）
```rust
// 代码
```

- **差异**：旧的靠 X 维持，新的靠 Y 维持
- **归因**：L1/L2/L3 —— 判定依据
- **代表性**：为什么选这段
- **佐证**：相关 commit / 出现次数 / 图谱指标（有则给，无则略）
- **代价**：无 / 具体是什么
```

## 受众适配

**先确认受众再动笔。** 同一批证据可支撑下面任何一种，但不要用同一份文档应付不同受众。

- **内部技术评审**（默认）：完整走全流程。**维度 2（变更成本）往往比维度 1（安全性）更能打动这类读者**——他们每天头疼的是"这块代码没人敢动"。代码对照是主体，归因等级显式标注，代价一节必须完整，证据索引不能省。
- **管理者 / 非技术决策者**：**不要贴代码对照**。把结论翻译成风险与成本语言——"三年里有 N 次线上问题属于这一类，新实现从结构上排除了它们"，配上定位耗时、影响面这类他们能感知的量。归因等级不外露，但心里要有，因为"这是重写红利还是 Rust 红利"迟早会被问到。全文一页。
- **技术分享 / 博客**：保留 3-4 组最有冲击力的对照，案例讲透一个。**统计数字要么给全口径要么不给**——公开材料里的模糊统计最容易被挑刺。
- **PR / 提案（说服团队采用）**：重点放在代价与迁移成本，价值论证反而次要——这类读者的疑虑在风险侧。

## 三个必答问题

写材料前先确认这三个有答案，它们在评审现场几乎必然被问到，沉默不是选项。具体填法见下面的模板。

**"那性能呢？"** 没有 benchmark 数据时不要编也不要回避：声明本次目标是否包含性能（多数迁移是"等价性能下换取安全性与可维护性"，就这么说）；能低成本补就做微基准并说清适用范围；只能定性论证时明确标注这是语言特性推论而非本项目实测，同时诚实提及可能变差的地方。

**"你怎么证明行为一致？"** 差分测试（旧实现当 oracle）、回归测试迁移、灰度对比、线上运行时长——做过就写进去，这本身就是工程质量证据；没做过就如实说明当前验证手段和覆盖范围。

**"代价呢？"** 必须单独成节，尤其要主动点出 FFI/unsafe 边界是新实现最该重点审查的地方——主动披露比被问出来强得多。
