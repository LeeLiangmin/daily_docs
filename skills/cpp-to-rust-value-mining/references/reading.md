# 逐对深读

> 流程第 2 步

对第 1 步排出的高优先级功能单元，逐对精读。**这一步只产出记录，不产出结论**——筛选和论证是第 3 步的事。

本文主体是**价值维度 1（正确性与安全性）**的读法，因为它最依赖逐行精读。其余维度的证据形式不同，见文末「其他维度的读法」；**读代码时六个维度的眼睛要同时睁着**，不要读完一遍只带回正确性方面的记录。

## 不变量：维度 1 的主力工具

**不变量 = 程序在某个点上必须成立、但语言不一定帮你保证的事实。**

「访问这个字段前必须持有那把锁」「这个指针在回调期间保持有效」「必须先 `init()` 再 `use()`」「这个 `int` 是索引不是 ID」「长度字段和缓冲区容量始终一致」——都是不变量。C/C++ 里它们由**人**维持，编译器一无所知，违反的代价只在运行时显现。

深读时反复问的就是这一件事：**这条不变量，旧实现靠什么维持？新实现靠什么维持？**

### 不变量的四种归宿

对找到的每一条，追查它在新实现里的下场。**四种都要记**：

| 归宿 | 含义 | 价值 |
|---|---|---|
| **编码进类型** | 违反它编译不过 | 高 |
| **不变量消失了** | 结构变了之后它不再需要存在 | **最高** |
| **变成运行时检查** | `assert!`、构造校验、返回 `Err` | 中，如实说明"仍可能运行时失败" |
| **仍是注释约定** | 换了语言但约定没变 | 无——这是缺口，写进"代价与局限" |

**第二种最容易被低估，也最值得挖。** 「访问 `g_conn_list` 前必须持有 `g_conn_lock`」这条规则：

- 新实现是 `static LOCK: Mutex<()>` + `static LIST: Vec<Conn>` → 规则还在，只是编译器帮着查（第一种）
- 新实现是 `static CONNS: Mutex<Vec<Conn>>` → **规则消失了**。不存在"忘记加锁"这个动作，因为拿不到锁就拿不到数据（第二种）

**消灭一条规则比强制执行它更高级。** 这类发现是 A 级素材的首选来源，因为它体现的是设计判断而不是语言特性的直接应用。找法：看旧实现里那些**被重复叮嘱很多遍的约定**，新实现里对应的地方有没有变得"根本没法说错"。

第四种不要藏。新实现里仍靠注释维持的不变量，如实列出——一是"代价与局限"需要真实内容，二是这些正是团队下一步该改的地方，评审现场拿得出来比被问出来强。

### 在旧代码里找不变量（按效率排序）

1. **grep 约定型注释**：`必须`、`不要`、`仅`、`只能`、`需先`、`调用方`、`注意`、`确保`、`前提`、`must`、`should`、`caller`、`before calling`、`do not`、`ensure`、`assumes`、`requires`。唯一能机械执行的，先做。
2. **看断言**：`assert`、`BUG_ON`、`abort` 每一处都是显式写下的不变量，比注释可靠——写断言的人当时是认真的。
3. **看必须配对的函数名**：`init`/`destroy`、`lock`/`unlock`、`begin`/`end`、`acquire`/`release`，隐含"必须配对且顺序正确"。
4. **看字段之间的协同关系**：`buf` 和 `len` 必须一致、`state` 和 `fd` 必须匹配、两个数组必须等长。这类往往没有任何注释，只能靠读逻辑发现，但价值很高。
5. **直接问团队**：「这块代码有什么坑是新人一定会踩的？」回答几乎都是不变量，而且是最痛的那些。效率最高，别嫌麻烦。
6. **看反复出现的历史缺陷**：某个 bug 反复出现，背后通常有条难以维持的不变量。（这是 git 历史在主线中的正当用法——**验证**已发现的不变量有多难维持，不是用来发现它们。）

## 不变量台账

**本步骤最重要的产出物**，单独维护，最后进材料附录：

| # | 不变量（旧实现原话） | 旧位置 | 谁维持 | 新位置 | 归宿 | 承载机制 | 精彩度 | 备注 |
|---|---|---|---|---|---|---|---|---|
| 1 | 访问 g_conn_list 前必须持有 g_conn_lock | conn.h:18 | 注释+人 | conn.rs:56 | 消失 | `Mutex<Vec<Conn>>` | A | 同一约定在 4 处被重复叮嘱 |
| 2 | 返回的 conn 由调用方负责 conn_free | conn.h:24 | 文档 | conn.rs:31 | 消失 | 所有权 + `Drop` | B | 语言内建，非团队设计 |
| 3 | 必须先握手再发数据 | 无注释 | 老员工的脑子 | — | 仍是约定 | — | — | 新实现仍可在 New 状态调 send |

**台账的价值在于可穷举**：不变量的数量有限，找全了就是找全了。相比之下"架构改进"这类主张永远说不清有没有找全。**一张填满的台账是材料里最难反驳的东西。**

「备注」栏记同一条约定被重复叮嘱的次数——它直接反映这条不变量有多难维持，是精彩度的强信号，也是写材料时把"难度"落到实处的唯一手段。

## 八个阅读切面（取景器，不是打分表）

「切面」指看同一段代码的八个角度，和前面的**价值维度**是两回事——价值维度回答"找什么价值"，阅读切面回答"怎么看代码"。

切面 2（不变量）是维度 1 的主力，优先做、产出最多；其余七个多是它在不同场景下的展开。**某个切面两边没有实质差异就跳过**，硬凑的条目只会稀释密度。C 形态 ↔ Rust 机制的对应关系查 `lookup.md`。

**切面 1：接口与所有权语义**
所有权约定写在哪里（文档/注释/命名约定/完全没写）？谁负责释放返回值、谁接管参数？调用方看得出来吗？新实现的签名（`T`/`&T`/`&mut T`/`Arc<T>`/`Cow<T>`）是否把这些显式化了？有没有"调用后原对象失效"这类语义，新实现是不是靠移动语义直接排除？

**切面 2：不变量的表达方式** ★维度 1 的主力
见上文。这一项做透，其余七个往往只是补充。

**切面 3：资源与生命周期**
旧实现的清理路径有几条（数 `goto cleanup`、重复的 `free`、嵌套错误分支）？新增一个早退分支时需要记得做什么？新实现里资源由谁拥有，`Drop` 覆盖所有路径了吗？有没有 `Rc`/`Arc` 循环引用的可能（有的话"不会泄漏"要加限定）？

**切面 4：错误处理与控制流**
错误怎么表达（返回码/errno/out 参数/异常）？调用方能忽略吗？传播中信息丢失了吗、根因可追溯吗？新实现的错误类型设计如何？
**反向检查**：新实现里 `unwrap()`/`expect()`/`panic!` 有多少？很多说明编译期保证被换成了运行时崩溃，相关主张要降级。**必须自查，主动披露比被发现好得多。**

**切面 5：并发模型**
锁和它保护的数据怎么绑定（同一结构体内/分开的全局变量+注释）？有没有"这个字段只在 X 线程访问"这类约定，编译器知道吗？新实现是 `Mutex<T>` 把数据关进锁里，还是仍然锁与数据分离？跨线程传递靠什么保证安全？
**注意**：死锁和逻辑竞态 Rust 都不防，不要算进价值点。

**切面 6：状态与类型表达**
状态怎么表示（`#define` 整数常量/enum/布尔标志组合）？状态转移在哪里校验，`switch` 有没有 `default`，新增状态时怎么保证不漏改？新实现的 `match` 是穷尽的吗？有没有"同一底层类型表示不同语义"（都是 `int`，一个是 ID 一个是索引），新实现用 newtype 区分了吗？

**切面 7：模块边界与可见性**
核心结构体的字段是公开的吗、有多少处直接访问了内部字段（用图谱数，grep 数不准）？头文件有没有循环包含、有没有"什么都往里塞"的公共头？新实现的 `pub`/`pub(crate)`/私有划分如何，crate 依赖是不是 DAG？改动一个核心函数，两边影响半径分别多大？

**切面 8：扩展点与抽象**
旧实现怎么做多态（函数指针表 + `void *ctx`/宏展开/虚函数/模板）？`void *ctx` 的真实类型靠什么保证？有没有为绕开 C 缺乏泛型而写的重复代码或宏，新实现用泛型/trait 消除了吗？
**归因提醒**：旧实现若是 C++ 且已用模板和虚函数，这一项多半是 L3 或不成立，别硬写。

## 数据流四问（核心数据结构专用）

对主干路径上的核心数据结构，除了八个切面，额外问这四个——**它们的答案差异几乎必然是 A 级素材**：

1. **谁构造它**：一处还是多处？构造完成时不变量就成立了吗，还是要调用方再补几步？
2. **谁修改它**：有多少个地方能改？靠什么防止并发修改和非法状态？
3. **谁消费它**：读的地方对它有什么隐含假设？
4. **谁负责生命周期**：何时释放？释放后还有谁可能持有指针？

C 里这四问的答案通常是"很多地方都能改，靠约定"；Rust 里是一条所有权链。**一条数据流的对比能同时打穿维度 1（不变量）、维度 3（抽象）、维度 4（零拷贝）**，比孤立地对比八个函数有力得多。详见 `at-scale.md`。

## 什么时候该停下来细看

扫读时大部分地方一眼带过。下面这些信号出现时停下深挖——**精彩的发现几乎都藏在这些地方**：

- **新旧结构完全对不上**。旧实现一个大文件、新实现拆成性质不同的几块；或旧实现分散在多处的逻辑、新实现收拢成一个类型。**结构对不上说明设计思路变了**，而设计思路的变化正是 A 级素材的来源。逐行都能对上的地方反而通常是 B 级。
- **旧代码里有"绕开语言限制"的痕迹**。宏展开生成多份类型代码、`void *` + 函数指针表、`container_of`、手写虚表——为绕开 C 缺乏泛型/多态付出的代价。这类对比同时具备"痛"和"难以模仿"两个特征。
- **旧代码里有一段人人都不敢碰的地方**。注释特别多、改动特别少，或反过来改动特别频繁。问团队"哪块代码最让人头疼"，答案往往直接指向 A 级素材。
- **某个约定在旧实现里被重复了很多遍**。同一句"调用前必须加锁"出现在八个地方——说明这个不变量很重要且很难维持。新实现若把它变成了类型，就是典型的"一个决策消除一整类问题"。
- **新实现里出现了旧实现完全没有的抽象**。一个新 trait、一个 typestate、一个把两个概念分开的 newtype。追问它解决了什么问题，往往能问出一个完整的设计故事。

反过来，这些看一眼就走：两边逻辑一一对应只是语法不同、纯计算函数、简单 getter/setter、明显是机械翻译的代码。

## 差异记录模板

每读完一对产出一条。**允许粗糙、允许重复、允许后面被推翻**——先攒量，第 3 步再收敛。不要边读边写材料。

```
功能单元：<名称>
旧：<文件:行号> —— 正确性靠 <什么> 维持
新：<文件:行号> —— 正确性靠 <什么> 维持
阅读切面：<1 接口 / 2 不变量 / 3 资源 / 4 错误 / 5 并发 / 6 状态 / 7 模块边界 / 8 扩展点>
价值维度：<1 正确性 / 2 变更成本 / 3 表达力 / 4 性能 / 5 工程化 / 6 团队>
初判归因：L?
精彩度初判：A / B / C
待验证：<需要 git 历史或计数佐证的点>
反向发现：<新实现在这里更差或没改进的地方，如实记>
```

**精彩度初判凭第一直觉打，不要犹豫。** 读到一处让你停下来想"这个设计有意思"的，标 A。这个直觉通常是对的，而且很容易在后续整理中被磨平——当场记下来。A 级候选后面补一句：它解决的是什么问题、当时可能还有什么别的选择。

**「反向发现」不要空着走过场。** 新实现里没改进甚至更差的地方（unsafe 集中区、`unwrap` 密集处、被迫的 `clone`、比旧实现更绕的抽象）——找到它们有两个作用：材料的"代价与局限"需要真东西；这些本身就是团队接下来该改的地方，评审现场拿得出来会显得你真读过代码。

## 其他维度的读法

维度 1 靠逐行精读，其余维度的证据分散在别处，读代码时顺带留意（详见 `dimensions.md`）：

- **维度 2 变更成本**：读到一处时问「**如果给这个结构加一个字段，两边分别要改几处、谁保证不漏？**」。这是最容易在精读时顺手取得、又最有分量的证据。看到旧实现里有"补漏"型的历史修改（加了状态却漏改某个 switch），当场记下来——这是维度 2 的一等素材。
- **维度 3 表达力**：留意旧实现里为绕开语言限制付出的代价（宏生成多份类型代码、`void *`、复制粘贴的重复实现）。**统计被消灭的重复实现数量或宏行数**，比描述性文字有力。
- **维度 4 性能**：留意数据流路径上的拷贝与分配（`strdup`、memcpy 到中间缓冲、每次请求新建对象）。新实现是否消除了它们——**这类可以指着代码说，不需要 benchmark**，是这一维最稳妥的证据。
- **维度 5 工程化**：不在代码里，在构建脚本、CI 配置、测试目录结构里。单独看一遍这些文件。
- **维度 6 团队**：读代码时留意"要理解这段需要多少前置知识"，以及旧实现里哪些点必须靠人工 review 把关（漏 free、漏加锁、返回值未检查）——这些现在由编译器负责了，是 review 负担下降的直接证据。

差异记录里的「价值维度」一栏据此填写，第 3 步聚类时会用到。

## 常见陷阱

- **只读新实现**：Rust 代码读着舒服，容易多花时间在上面。但论证的重量在旧实现——**你得说清楚旧实现里的风险具体在哪一行**，光说新实现好没有说服力。
- **拿最烂对最好**：旧实现里总有一段年久失修的代码，用它对比新实现的精华，一旦被识破整份材料就废了。选取时问自己：这段有代表性吗？被修改次数多吗？在核心路径上吗？
- **把不熟悉当缺陷**：C 的惯用法（`container_of`、位域、宏）不等于坏代码。判断标准始终是"正确性靠什么维持"，不是"我看着别扭"。
- **忽略旧实现的防御措施**：旧实现可能已有静态分析、sanitizer、严格的 review 流程，这些会削弱某些主张（"我们有 ASAN 在 CI 里跑"）。**提前找出来并在材料里回应**，比现场被问出来好。
- **边读边下结论**：读第一对就写出"架构大幅改善"，后面的阅读会不自觉找证据支持它。
- **把清单当覆盖率跑**：八个切面每个憋两条凑成十六条，看起来全面，实际把最好的两条埋掉了。
- **只带回正确性方面的记录**：不变量的方法最成熟，读着读着就只剩它了。**每读完一个功能单元，回头看一眼六个价值维度**，问问这一处有没有维度 2、3、4 的素材——通常有，只是当时没往那个方向想。
