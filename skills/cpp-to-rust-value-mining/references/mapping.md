# 结构地图与功能对应关系

> 流程第 1 步
>
> **旧实现超过 5 万行时不要用本文**，通读结构、列模块清单这一步在大项目上会直接失效。改走 `at-scale.md`：从主干数据流入手，只追一条线。

**这是主线的起点，也是最容易被跳过、跳过后整个对比就散掉的一步。**

先分别通读两边的结构（模块/文件/公共接口清单，有图谱工具就直接出依赖图），然后建立对应关系表。没有它，代码对比会变成东一榔头西一棒槌，而且根本说不清"这一对为什么可比"。

## 对应关系表模板

| 功能单元 | 旧实现位置 | 新实现位置 | 对应关系 | 优先级 | 备注 |
|---|---|---|---|---|---|
| 连接生命周期管理 | `src/conn.c` | `src/conn.rs` | 一对一 | 高 | |
| 协议解析 | `parser.c` + `parser_util.c` | `protocol/` 模块 | 二对一 | 高 | |
| 日志 | `log.c` | 换用 `tracing` crate | 被第三方替代 | 低 | |

## 对应关系本身就是发现

每种关系都要追问，其中往往藏着架构层面的价值点：

- **一对多**（一个大文件被拆开）：拆分依据是什么？按职责还是按类型？通常是 L3，但**拆分能成立可能依赖类型系统**（改完之后编译器帮你查所有调用点），那就是 L2。
- **多对一**（多份重复实现被合并）：旧实现为什么会有重复？**常见原因是 C 里做泛型的代价太高，于是复制粘贴**——如果是这个原因，这条是 L2 而非 L3。
- **被第三方替代**（自研日志/序列化换成 crate）：追问旧实现为什么要自研。常见原因是 C/C++ 生态里引入依赖的成本高（构建、版本、ABI）。这是工程化维度的真实价值，别漏掉。
- **旧有新无**（功能被砍）：**必须写进材料的"对比基准"一节**，否则规模和性能对比不公平。
- **新有旧无**（新增能力）：多属重写红利（L3）；若新增的是测试、fuzz、benchmark 这类，归到工程化维度。

## 优先级排序

时间总是不够，必须取舍。**优先级要结合第 0 步圈定的维度**——若这次重点是维度 2（变更成本），就优先读被改动最频繁、扇入最高的模块；若重点是维度 3（表达力），就优先读旧实现里宏和 `void *` 最密集的地方；若重点是维度 4（性能），优先读数据流路径上有拷贝和分配的地方。

没有明确侧重时，按这个默认顺序：

1. **核心数据结构及其生命周期管理** —— 所有权、资源、并发问题的集中地
2. **跨模块的公共接口** —— 所有权语义、错误语义、可空性的表达方式差异最明显
3. **并发相关代码** —— Rust 优势最集中、也最容易讲清楚的地方
4. **输入解析与边界处理** —— 越界、长度计算、不可信输入
5. **错误路径与清理逻辑** —— 旧实现里最脏、新实现里最干净的对比区
6. **纯计算逻辑优先级最低** —— 两边往往差不多

## 用图谱工具加速这一步

有 GitNexus 或等价工具时，新旧仓库各建一次索引，先取这几项：

- 模块/crate 依赖图 → 直接看出有没有环、有没有"什么都往里塞"的公共头文件
- 各核心符号的扇入数 → 扇入最高的就是耦合最重的地方，优先读
- 文件/符号规模分布 → 找出旧实现里的"上帝文件"

这些数据在第 3 步会再用一次（作为架构与变更成本主张的佐证），第 1 步先用来**决定读什么**。

**顺手取一份变更热度数据**：`git log --numstat` 或图谱的变更频次，找出旧实现里改动最频繁的文件。这份数据在维度 2 里是主证据（"这块反复改、还常改漏"），第 1 步取一次两处用。

## 完成标志

对应关系表填完，且高优先级的功能单元不超过 5-8 个。多于这个数说明还没排序，回去砍——**第 2 步深读的成本很高，读什么必须先想清楚**。
