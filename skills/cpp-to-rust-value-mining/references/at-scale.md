# 大规模代码库：怎么找到核心

> 当代码量大到不可能通读时，`mapping.md` 的"通读结构、列模块清单"这一步会直接失效。本文替换它。

## 什么时候切到这套方法

| 规模 | 做法 |
|---|---|
| < 5 万行 | 按 `mapping.md` 正常走，能通读结构 |
| 5 万 – 50 万行 | **主干数据流法**（本文），模块清单不可靠 |
| > 50 万行 | 先分域，选 1-2 个域深挖，其余不碰；材料里明确写出覆盖范围 |

规模判断用非空非注释行（`code_metrics.py` 会给）。介于两者之间时选更保守的那档——**读不完却假装读完了，比读得少但说清楚范围更糟**。

## 核心思路：不给全部模块排序，只追一条主干

大项目可能有 200 个模块，给它们排序本身就是不可能任务。但**主干路径只有一两条**：一个请求从进入到响应、一份数据从读入到落盘、一次任务从提交到完成。

追这条路径经过的代码，就自动得到了核心集合——不需要事先知道哪些模块重要。这是本文和 `mapping.md` 的根本区别：**从"给一切排序"换成"追一条线"**。

## 第一步：定位入口

在旧实现里找这些，任选其一作为起点：

- `main()`、服务启动函数、事件循环
- 协议/请求的入口函数（`*_parse`、`*_handle`、`on_*`、`*_dispatch`）
- 回调/插件的注册点（注册表、函数指针表的填充处）
- 对外暴露的库 API（头文件里被最多外部引用的那几个）

新实现同样找一遍。**两边的入口形态差异本身就是第一条发现**——比如旧实现是全局注册表 + `init()`，新实现是构造一个值传下去，这类差异往往牵出一整组不变量。

## 第二步：确定主干数据流的载体

在 C 项目里，**系统的核心通常不是某个函数，而是那几个到处传递的 struct**——它们是流经系统的"血液"。

用 `scripts/rank_core_symbols.py --root <src>` 按扇入排序，看第一张表（数据结构扇入）。前 3-5 名就是主干数据流的载体。有 GitNexus 等图谱工具时以图谱结果为准，本脚本是退路。

拿到载体之后，对每一个追四个问题：

1. **谁构造它**（一处还是多处？构造时不变量成立吗？）
2. **谁修改它**（有多少个地方能改？靠什么防止并发修改和非法状态？）
3. **谁消费它**（读的地方对它有什么假设？）
4. **谁负责它的生命周期**（何时释放？释放后还有谁可能持有指针？）

**这四个问题的答案，在 C 和 Rust 里的差异，几乎必然是 A 级素材。** 因为 C 的答案通常是"很多地方都能改，靠约定"，而 Rust 的答案是所有权链——一条数据流对比能同时打穿维度 1（不变量）、维度 3（抽象）、维度 4（零拷贝），比孤立地对比八个函数有力得多。

## 第三步：画出两边的数据流骨架

把主干路径压缩成一条链，两边各画一条，逐段对照：

```
旧实现：  recv(fd, buf)  →  proto_parse(buf, len, &frame)  →  frame.payload 指向 buf 内部
          →  dispatch(&frame)  →  handler(ctx, ...)  →  free(buf)
          ⚠ payload 的有效期依赖 buf，靠注释约定；异步 handler 里读到脏数据（2022-03 事故）

新实现：  read() → Bytes  →  Frame::parse(buf) → payload: Bytes（共享所有权、零拷贝切片）
          →  registry.dispatch(&frame)  →  Codec::decode(&[u8])
          ⚠ 生命周期由 Bytes 的引用计数保证，异步持有不会悬垂
```

对照时逐段问：**这一段的数据，所有权在谁手上？谁能改？什么时候释放？** 骨架画完，维度 1、3、4 的素材通常已经浮出来了。

## 第四步：交集筛选，决定深读清单

三份排序取交集，得到深读优先级：

| 信号 | 工具 | 说明 |
|---|---|---|
| 高扇入 | `rank_core_symbols.py` / 图谱 | 核心 |
| 改动频繁 | `find_change_cost.py`（变更热点） | 难维护 |
| 有补漏史 | `find_change_cost.py`（补漏对） | 扩展点分散 |

**"高扇入 × 改动频繁"的交集是 A 级素材的高发区**——既是核心又一直在改，说明这里的复杂度从来没被结构化解决。`rank_core_symbols.py --repo <仓库>` 直接输出这个交集。

深读清单控制在 **5-8 个功能单元**，和小项目一样。规模变大不该让深读清单变长，只该让筛选更严格。

## 第五步：抽样与诚实声明

大项目一定读不完，**关键不是读全，而是说清楚读了什么**。

分三层：

- **全读**：主干数据流路径 + 排名前列的核心数据结构（通常占总量 5% 以内）
- **抽样**：交集清单里的功能单元，按上面的优先级
- **不读**：其余部分，明确列出

材料的"背景与对比基准"一节必须写明抽样口径：

> 本次分析覆盖 X 模块的主干请求路径（约 N 行，占旧实现 P%），以及扇入排名前 5 的数据结构。未覆盖：管理面、监控、离线工具链。结论的适用范围限于已覆盖部分。

**这句话不会削弱材料，反而会加强它**——评审最反感的是"看起来全面但经不起追问"。主动圈定范围，剩下的结论才站得住。

## 大规模场景下的额外注意

- **不变量台账不可能穷举**。小项目的台账可以声称"找全了"，大项目不能。改为声明"主干路径上的不变量已穷举"，并给出 grep 约定型注释的**总命中数 vs 已处理数**，让读者看到比例。
- **分域时按数据流分，不按目录分**。目录结构往往是历史产物，数据流才反映真实边界。
- **警惕"读了最容易读的部分"**。工具类、util、纯计算函数最好读，但最没价值。检查一下深读清单里有几个是真正的核心载体。
- **两边规模差异要解释**。大项目重写常伴随范围调整，若新实现少了 30% 的代码，先查清是设计改进还是功能被砍——搞错了整份材料的可信度都会崩。
