## 如何使用这张表

1. 拿到一个历史 fix commit，先看它**修的是什么**（不是 commit message 怎么写的，是 diff 实际改了什么）。
2. 在下表里找到对应类别。
3. 按"Rust 侧处境"一栏判断等级：**L1** = 同样的写法编译不过；**L2** = 能写出来但默认写法不会踩；**L3** = 和语言无关。
4. **关键动作**：去新实现里找到对应的那段代码，确认它确实是这么写的。不要假设"Rust 就应该是这样"——如果新实现在这里用了 `unsafe`、`unwrap`、或者把检查放到了运行时，那这条就不是 L1。

## 内存安全类

| 缺陷类别 | 旧代码典型形态 | Rust 侧处境 | 等级 | 注意 |
|---|---|---|---|---|
| use-after-free | 释放后仍持有指针；对象析构后回调仍触发 | 借用检查器在编译期拒绝；所有权明确 | L1 | 若新实现用了裸指针或 `unsafe` 绕过，降级并单独说明 |
| double free | 多处 free 同一指针；异常路径重复清理 | 所有权唯一，`Drop` 只执行一次 | L1 | |
| 内存泄漏 | 早退分支漏 free；错误路径漏清理 | 离开作用域自动释放，所有路径一致 | L1（对常规所有权）/ L2（`Rc` 循环仍可能泄漏） | 循环引用泄漏在 Rust 里依然存在，别说死 |
| 缓冲区溢出 / 越界读写 | `memcpy` 长度算错；`arr[i]` 未校验 i | 切片索引默认边界检查；迭代器无需索引 | L1（安全代码内） | 代价是运行时检查开销，可提一句 |
| 空指针解引用 | 忘记检查 `NULL` 返回 | `Option<T>` 强制处理 `None` 分支 | L1 | 若新代码大量 `unwrap()`，等于把编译期检查换成 panic，如实说 |
| 野指针 / 悬垂引用 | 返回栈上对象地址；容器扩容后旧迭代器失效 | 生命周期标注 + 借用规则 | L1 | 迭代器失效这一条对比效果尤其好 |
| 未初始化内存读取 | 结构体部分字段未初始化 | 变量必须初始化后才能使用 | L1 | |
| 整数溢出导致的内存错误 | 长度计算溢出后分配过小缓冲 | debug 下溢出 panic；`checked_*`/`saturating_*` 显式表达意图 | L2 | release 默认回绕，说清楚 |

## 并发类

| 缺陷类别 | 旧代码典型形态 | Rust 侧处境 | 等级 | 注意 |
|---|---|---|---|---|
| 数据竞争 | 共享变量无锁访问；"这个字段只在 X 线程改"的注释约定 | `Send`/`Sync` + 借用规则在编译期排除 | L1 | Rust 最强的一条，值得重点写 |
| 忘记加锁 / 加错锁 | 锁与数据分离，靠约定绑定 | `Mutex<T>` 把数据关在锁里，不拿锁拿不到数据 | L1 | 结构性差异非常直观，适合做代码对照 |
| 忘记解锁 | 早退分支漏 unlock | `MutexGuard` 的 `Drop` 保证释放 | L1 | |
| 死锁 | 加锁顺序不一致 | **Rust 不能防止死锁** | L3 / 不算 | 不要把死锁算成 Rust 的功劳，写了会被当场纠正。`mine_fix_commits.py` 已把它单列为 `concurrency_deadlock` 类别并排除在"可防"统计外 |
| 竞态条件（逻辑层） | check-then-act | Rust 不防这个 | L3 / 不算 | 同上 |
| 回调跨线程使用非线程安全对象 | 靠人工审查 | `Send` 约束编译期拦截 | L1 | |

## 错误处理与控制流类

| 缺陷类别 | 旧代码典型形态 | Rust 侧处境 | 等级 | 注意 |
|---|---|---|---|---|
| 未检查返回值 | 调用返回 -1 但调用方忽略 | `Result` 标记 `#[must_use]`，忽略触发警告；`?` 让传播成为最省事的写法 | L1（默认配置下为警告，若开 `deny(warnings)` 则为硬错误） | 统计旧代码里"未检查返回值"的出现次数，这个数字很有冲击力 |
| 错误信息丢失 | 层层返回 -1，根因不可追 | `Result<T, E>` 携带类型化错误，可 `source()` 链式追溯 | L2 | |
| 清理路径不一致 | `goto cleanup` 分支遗漏 | `Drop` + `?` 使得清理与早退天然一致 | L1 | `goto cleanup` 的计数很适合做对比 |
| 状态机漏分支 | `switch` 缺 `default` 或漏 case | `match` 穷尽性检查 | L1 | 新增枚举变体时编译报错，这点值得单独强调 |
| 异常安全（C++） | 构造/赋值中途抛异常导致状态不一致 | 无异常，错误是值 | L2 | |

## 类型与接口类

| 缺陷类别 | 旧代码典型形态 | Rust 侧处境 | 等级 | 注意 |
|---|---|---|---|---|
| 类型混淆 | `void*` 强转错类型；单位/含义相同底层类型混用 | 泛型 + trait；newtype 区分语义 | L1（`void*`）/ L2（newtype 是设计选择） | newtype 属于设计选择，除非新实现真的用了，否则不能算 |
| 隐式转换出错 | 有符号/无符号、窄化转换 | 无隐式数值转换，必须显式 | L1 | |
| API 误用 | 必须先 init 再 use、必须成对调用 | typestate 模式让错误顺序编译不过 | L2 | 只有新实现真的这么设计了才算 |
| 可变性失控 | 到处传裸指针，谁都能改 | `&` / `&mut` 显式区分，同时只能有一个可变借用 | L1 | |
| 头文件 / 声明不一致 | 声明与定义签名不匹配、宏重定义 | 模块系统，无头文件 | L2 | |

## 资源与生命周期类

| 缺陷类别 | 旧代码典型形态 | Rust 侧处境 | 等级 |
|---|---|---|---|
| 文件描述符 / socket 泄漏 | 错误路径漏 close | `Drop` 自动关闭 | L1 |
| 锁、事务、临时文件未释放 | 同上 | 同上（RAII 覆盖全路径） | L1 |
| 资源释放顺序错误 | 手动控制析构顺序 | 所有权关系表达依赖，drop 顺序确定 | L2 |

## 不属于 Rust 功劳的类别

挖到这些类别的历史 bug，**不要**写进"Rust 消除了什么"，可以写进 L3 或干脆不写：

- 业务逻辑错误、算法写错、边界条件想错
- 死锁、逻辑竞态、活锁
- 配置错误、协议理解错误、对第三方行为的错误假设
- 性能问题（除非新实现有实测数据支撑）
- 需求变更导致的返工

如实排除这些，比多列几条更能建立可信度。可以在材料里显式给出这个排除说明：「本次统计中，X% 的历史缺陷属于逻辑与业务类，Rust 对这部分没有帮助。」——这句话会让读者相信剩下的那部分统计。

## 归因判定的四个反问

对每一条打算标 L1 的结论，先自问：

1. **新实现真的是这么写的吗？** 去代码里确认，不要凭语言特性推断。
2. **这里有 `unsafe`、`unwrap`、`transmute`、裸指针吗？** 有就降级或加限定条件。
3. **用现代 C++（智能指针、RAII、`std::optional`、`-Werror`）能不能同样做到？** 能，就是 L2 而不是 L1。这个反问最容易暴露虚高的结论。
4. **旧代码里这类问题真的发生过吗？** 没发生过就不能写成"消除了历史问题"，只能写成"结构上排除了这类风险"——两者的说服力不同，措辞要准确。
