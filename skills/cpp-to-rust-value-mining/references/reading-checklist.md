## 对应关系表模板

在深读之前先填这张表。没有它，后面的对比会变成东一榔头西一棒槌。

| 功能单元 | 旧实现位置 | 新实现位置 | 对应关系 | 优先级 | 备注 |
|---|---|---|---|---|---|
| | | | 一对一 / 一对多 / 多对一 / 被第三方替代 / 旧有新无 / 新有旧无 | 高/中/低 | |

**对应关系本身就是发现，逐类追问**：

- **一对多**：旧实现一个文件被拆成多个模块 → 拆分依据是什么？是按职责拆的还是按类型拆的？这通常是 L3，但拆分能成立可能依赖类型系统（L2）。
- **多对一**：多份重复实现被合并 → 旧实现为什么会有重复？（常见原因：C 里做泛型的代价太高，于是复制粘贴）如果是这个原因，就是 L2 而非 L3。
- **被第三方替代**：自研的日志/序列化/网络层换成了 crate → 追问旧实现为什么要自研。常见原因是 C/C++ 生态里引入依赖的成本高（构建、版本、ABI）。这条属于工程化维度的真实价值，别漏掉。
- **旧有新无**：功能被砍了 → **必须在材料的"对比基准"一节说明**，否则规模和性能对比不公平。
- **新有旧无**：新增能力 → 这是重写红利（L3），但如果新增的是测试、fuzz、benchmark 这类，可以归到工程化维度。

**优先级排序原则**：核心数据结构与其生命周期管理 > 跨模块公共接口 > 并发相关 > 输入解析与边界处理 > 错误路径与清理 > 纯计算逻辑。

## 八个提问维度

对每一对高优先级的功能单元，逐项过一遍。**贯穿所有维度的主轴只有一句**：

> 这段代码的正确性，旧实现靠什么保证？新实现靠什么保证？

左边是"程序员记得 / 注释写了 / 约定 / 代码审查 / 运行时检查"，右边是"编译器 / 类型系统"，就是价值点。两边同类，就不是。

### 1. 接口与所有权语义

- 旧接口的所有权约定写在哪里？（文档、注释、命名约定 `xxx_take`/`xxx_borrow`、还是完全没写）
- 谁负责释放返回值？谁接管参数的所有权？调用方能不能看出来？
- 新实现的签名（`T` / `&T` / `&mut T` / `Arc<T>` / `Cow<T>`）是否把这些语义显式化了？
- 有没有"调用后原对象失效"这类语义？旧实现怎么防止误用（防不住），新实现是不是靠移动语义直接排除？

### 2. 不变量的表达方式

**这一项产出最多，优先做。** 在旧代码里 grep 这类注释：`必须`、`不要`、`仅`、`只能`、`需先`、`调用方`、`must`、`should`、`caller`、`do not`、`before calling`。

- 每一条这样的注释，都是一个"靠人记住"的不变量。
- 逐条去新实现里找：它变成类型了吗（typestate、newtype、枚举、私有字段 + 构造函数校验）？还是仍然是注释？还是变成了运行时断言？
- **三种结果都有价值**：变成类型 = L1/L2 的价值点；仍是注释 = 诚实记录，说明改进不彻底；变成运行时检查 = 部分改进，说清楚。

### 3. 资源与生命周期

- 旧实现的清理路径有几条？（数 `goto cleanup`、重复的 `free`、嵌套的错误分支）
- 有没有"早退分支漏清理"的结构性风险？新增一个早退分支时，需要记得做什么？
- 新实现里这些资源由谁拥有？`Drop` 覆盖了所有路径吗？
- 有没有 `Rc`/`Arc` 循环引用的可能？（有的话，"不会泄漏"这个说法要加限定）

### 4. 错误处理与控制流

- 旧实现的错误怎么表达？（返回码、errno、out 参数、异常）调用方能忽略吗？
- 错误信息在传播过程中丢失了吗？根因可追溯吗？
- 新实现的错误类型设计如何？（`Result` + 自定义错误枚举 + `source()` 链）
- **反向检查**：新实现里 `unwrap()`/`expect()`/`panic!` 有多少？如果很多，说明编译期保证被换成了运行时崩溃，相关主张要降级。这一项必须自查，主动披露比被人发现好得多。

### 5. 并发模型

- 旧实现里锁和它保护的数据是怎么绑定的？（同一结构体内 / 分开的全局变量 + 注释）
- 有没有"这个字段只在 X 线程访问"这类约定？编译器知道吗？
- 新实现是 `Mutex<T>` 把数据关在锁里，还是仍然锁与数据分离？
- 跨线程传递的对象靠什么保证安全？（`Send`/`Sync` vs 人工审查）
- **注意**：死锁和逻辑竞态 Rust 都不防，不要算进价值点。

### 6. 状态与类型表达

- 旧实现的状态怎么表示？（`#define` 整数常量 / enum / 布尔标志组合）
- 状态转移在哪里校验？`switch` 有没有 `default`？新增状态时怎么保证不漏改？
- 新实现用枚举了吗？`match` 是穷尽的吗？状态转移是不是被集中表达？
- 有没有"用同一个底层类型表示不同语义"的情况（都是 `int`，一个是 ID 一个是索引）？新实现用 newtype 区分了吗？

### 7. 模块边界与可见性

- 旧实现里核心结构体的字段是公开的吗？有多少处直接访问了内部字段？（用图谱工具数，grep 数不准）
- 头文件之间有没有循环包含？有没有"什么都往里塞"的公共头文件？
- 新实现的 `pub`/`pub(crate)`/私有的划分如何？crate 依赖是不是 DAG？
- 改动一个核心函数，两边的影响半径分别多大？

### 8. 扩展点与抽象

- 旧实现怎么做多态？（函数指针表 + `void *ctx` / 宏展开 / C++ 虚函数 / 模板）
- `void *ctx` 的真实类型靠什么保证？转错了会怎样？
- 有没有为了绕开 C 缺乏泛型而写的重复代码或宏？新实现用泛型/trait 消除了吗？
- **归因提醒**：旧实现如果是 C++ 且已用模板和虚函数，这一项多半是 L3 或不成立，别硬写。

## 差异记录模板

每读完一对产出一条。**允许粗糙、允许重复、允许后面被推翻**——先攒量，第 3 步再收敛。不要边读边写材料。

```
功能单元：<名称>
旧：<文件:行号> —— 正确性靠 <什么> 保证
新：<文件:行号> —— 正确性靠 <什么> 保证
差异类型：<接口语义 / 不变量表达 / 资源管理 / 错误处理 / 并发 / 状态表达 / 模块边界 / 扩展点>
初判归因：L?
待验证：<需要 git 历史或计数佐证的点>
反向发现：<新实现在这里更差或没改进的地方，如实记>
```

**"反向发现"一栏不要空着走过场。** 新实现里没改进甚至更差的地方（unsafe 集中区、`unwrap` 密集处、被迫的 `clone`、比旧实现更绕的抽象）——找到它们有两个作用：一是材料里的"代价与局限"一节需要真东西，二是这些本身就是团队接下来该改的地方，评审现场拿得出来会显得你真读过代码。

## 读代码时的常见陷阱

- **只读新实现**：Rust 代码读起来舒服，容易多花时间在上面。但价值论证的重量在旧实现——**你得说清楚旧实现里的风险具体在哪一行**，光说新实现好没有说服力。
- **拿最烂对最好**：旧实现里总有一段年久失修的代码。用它对比新实现的精华，一旦被识破整份材料就废了。选取时问自己：这段有代表性吗？被修改次数多吗？在核心路径上吗？
- **把不熟悉当缺陷**：C 里的惯用法（`container_of`、位域、宏）不等于坏代码。判断标准始终是"正确性靠什么保证"，不是"我看着别扭"。
- **忽略旧实现的防御措施**：旧实现可能已经有静态分析、sanitizer、严格的 code review 流程。这些会削弱某些主张（"我们有 ASAN 在 CI 里跑"）。**提前找出来并在材料里回应**，比现场被问出来好。
- **边读边下结论**：读第一对就写出"架构大幅改善"，后面的阅读会不自觉找证据支持它。先攒差异记录，攒够了再聚类。
