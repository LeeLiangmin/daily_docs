# 高价值 before/after 对照模式清单

用于：在两份代码库里定位值得做对照的地方，避免只挑到"语法更简洁"这种低价值差异。

本文件配合 `reading-checklist.md` 使用：清单告诉你**怎么读**，本文件告诉你**读到什么形状的东西要停下来记一笔**。

**下面的代码片段只是模式示意，不是可以直接贴进材料的素材。** 必须去实际代码里找到对应的真实位置，用真实代码做对照。示意代码的作用是告诉你"该找什么形状的东西"。

## 判断一组对照有没有价值

一组对照值得放进材料，当且仅当你能用**一句话**填完这个模板：

> 旧实现在这里靠 **____** 保证正确性，新实现靠 **____** 保证正确性。

如果两边的空填出来是同一类东西（都靠"程序员记得"），这组对照价值不大。如果左边是"注释/约定/人工审查/运行时检查"，右边是"编译器/类型系统"，那就是高价值对照。

## 模式 1：手动清理路径 → RAII 全覆盖

**找什么**：`goto cleanup`、`goto err`、多层嵌套的 `if (ret != 0) { free(...); return ...; }`、每个早退分支都要重复的清理代码。

```c
int process(const char *path) {
    FILE *f = NULL; char *buf = NULL; int ret = -1;
    f = fopen(path, "r");
    if (!f) goto cleanup;
    buf = malloc(SIZE);
    if (!buf) goto cleanup;
    if (read_all(f, buf) < 0) goto cleanup;   // 新增一个早退分支就要记得走 cleanup
    ret = 0;
cleanup:
    if (buf) free(buf);
    if (f) fclose(f);
    return ret;
}
```

```rust
fn process(path: &Path) -> Result<(), Error> {
    let mut f = File::open(path)?;
    let mut buf = Vec::with_capacity(SIZE);
    f.read_to_end(&mut buf)?;   // 任何早退，f 和 buf 都会被释放
    Ok(())
}
```

**差异**：旧实现靠"每个早退分支都记得跳到 cleanup"，新实现靠 `Drop` 在所有路径上自动执行。
**证据加成**：统计旧代码里 `goto cleanup` 的出现次数、以及历史上有多少个 fix commit 是在补漏掉的清理。

## 模式 2：返回码 → Result

**找什么**：返回 `int`/`-1`/`errno` 的函数，以及**调用后没有检查返回值**的位置。

```c
int rc = do_something();
// 调用方可以完全忽略 rc，编译器不会有任何意见
```

```rust
let value = do_something()?;   // 忽略 Result 会触发 must_use 警告
```

**差异**：旧实现靠"调用方记得检查"，新实现里忽略错误需要显式写出来（`let _ =`），而正确传播反而是最省事的写法（`?`）。
**证据加成**：统计旧代码里未检查返回值的调用点数量。这个数字往往出人意料地大，是很有冲击力的一条。
**注意**：如果新实现里 `unwrap()` 满地都是，这条要打折甚至反过来——顺便统计一下新代码的 `unwrap`/`expect` 密度，这既是诚实，也是给自己找到的改进点。

## 模式 3：锁与数据分离 → 数据关进锁里

**找什么**：注释里写着"访问 X 前必须持有 Y 锁"、全局锁 + 全局变量、`pthread_mutex_lock` 与被保护数据在不同结构里。

```c
pthread_mutex_t cache_lock;
struct cache *g_cache;   // 注释：访问 g_cache 前必须持有 cache_lock
                         // 但编译器不知道这件事，谁都能直接读 g_cache
```

```rust
static CACHE: Mutex<Cache> = Mutex::new(Cache::new());
let mut cache = CACHE.lock().unwrap();  // 不拿锁就拿不到 Cache
```

**差异**：旧实现靠注释和代码审查维持锁与数据的绑定，新实现里这个绑定是类型层面的——拿不到锁就拿不到数据。
**为什么高价值**：这组对照几乎不需要解释，读者一眼就懂，且很难反驳。优先选。

## 模式 4：可空指针 → Option

**找什么**：返回可能为 NULL 的函数，以及调用方**没有检查**的地方。

**差异**：旧实现里"可能为空"是文档信息，新实现里是类型信息，不处理 `None` 编译不过。
**注意**：确认新实现真的在用 `Option` 而不是到处 `unwrap()`。

## 模式 5：void* / 宏泛型 → 泛型与 trait

**找什么**：`void *ctx` + 函数指针表、用宏展开生成多份类型代码（`DEFINE_LIST(int)` 这类）、`container_of` 技巧。

```c
struct handler { void (*cb)(void *ctx, int ev); void *ctx; };
// ctx 的真实类型只存在于程序员脑子里，转错了编译器不会说什么
```

```rust
trait Handler { fn on_event(&mut self, ev: Event); }
```

**差异**：旧实现的类型正确性靠"调用方和注册方约定好"，新实现由类型检查保证；旧实现的宏展开无法被 IDE 和调试器理解，新实现的泛型可以。
**归因提醒**：C++ 模板同样能做到类型安全，若旧实现是 C++ 且已用模板，这条降为 L3 或不写。

## 模式 6：注释约定的不变量 → 类型编码

**找什么**：形如 `/* 必须先调用 init() */`、`/* 只能在 IO 线程调用 */`、`/* 调用后本对象失效 */` 的注释。**这类注释是金矿**——每一条都是一个"靠人记住"的不变量，看看新实现有没有把它变成类型。

```rust
// typestate：未连接的连接对象根本没有 send 方法
let conn: Connection<Disconnected> = Connection::new();
let conn: Connection<Connected> = conn.connect()?;
conn.send(data)?;
```

**做法**：在旧代码里 grep 这类注释（`必须`/`不要`/`仅`/`只能`/`需先`/`调用方`/`must`/`should`/`caller`/`before calling`），逐条去新实现里找对应处理方式。**三种结果都要记**：变成类型 = 价值点；仍是注释 = 改进不彻底，如实记；变成运行时断言 = 部分改进。找到几条就是几条真实的设计改进，而且是你们自己的、不是教科书的。

这是产出最密集的一条，**优先做**。

## 模式 7：整数状态码 / switch → 枚举穷尽匹配

**找什么**：`#define STATE_XXX 3` 系列、缺 `default` 的 `switch`、状态用 `int` 表示。

**差异**：新增一个状态时，旧实现要靠人找全所有 `switch`，新实现所有未处理该分支的 `match` 会直接编译报错。
**说法建议**：这条讲"未来的维护成本"最有效——不是"现在少了个 bug"，而是"以后加状态时不会漏"。

## 模式 8：缓冲区与长度分离 → 切片

**找什么**：`func(char *buf, size_t len)` 形式的接口，尤其是历史上出现过长度算错的地方。

**差异**：旧实现里指针和长度是两个可能对不上的参数，新实现的 `&[u8]` 把两者绑定，且索引默认带边界检查。
**代价**：边界检查有运行时开销，主动提一句，说明在热点路径上的处理方式（迭代器、`get_unchecked` 的使用与审查）。

## 模式 9：所有权靠文档 → 所有权靠签名

**找什么**：注释写着"调用方负责释放返回值"、"本函数接管 p 的所有权"的接口。

**差异**：旧实现的所有权语义写在文档里，新实现写在签名里（`T` vs `&T` vs `&mut T` vs `Arc<T>`），且编译器强制执行。
**为什么高价值**：这是接口设计层面的改进，比单点 bug 更能体现"架构质量"，适合放在架构那一节。

## 模式 10：工程化层面的对照

这些不是代码片段对照，而是配置与流程对照，同样有价值，且容易被忽略：

- **依赖管理**：vendored 的第三方源码目录 + 手写 Makefile 片段 vs `Cargo.toml` + lockfile。落到具体问题上：旧实现里升级某个依赖要改几个地方？有没有过版本不一致的事故？
- **构建**：CMake/autotools 的平台分支数量 vs `cargo build`。交叉编译的实际步骤对比。
- **测试**：测试怎么组织、写一个新测试需要改几个文件、有没有 doc test 和 property test、fuzz 接入成本（`cargo-fuzz` vs 手搭 libFuzzer）。
- **静态检查**：旧实现开了哪些 warning、有多少被 suppress 掉、有没有跑 sanitizer/静态分析工具及其接入成本 vs clippy 默认能查出什么。
- **API 文档**：doc comment + 文档测试保证示例代码不过期，vs 手写文档与代码脱节。

工程化这一节的说服力来自**具体数字和具体步骤**，不要写"构建更简单了"，要写"跨平台构建从 N 步变成 1 步""CMake 里的平台分支从 N 处降到 0"。

## 用代码图谱定位对照素材

grep 找得到模式，找不到"最值得对比的那一处"。有 GitNexus 或等价工具时，用下面的方式定位素材：

- **找热点**：`git log -L` 或图谱的变更频次，找出被反复修补的函数。**被修最多次的那个函数，几乎一定是最好的对照素材**——它有完整的事故史，故事讲得出来。
- **找扇入最高的结构体/函数**：调用者最多的那个，是旧实现里耦合最重的地方。对比新实现同一功能的调用者数量和访问方式（是不是还能直接摸内部字段），这组对照直接支撑"模块边界"的主张。
- **找影响半径**：对同一个核心函数分别做 impact 分析，两边的数字差异是"可维护性"最接近可量化的证据。
- **找环**：旧实现的模块依赖若存在环，把环画出来 vs 新实现的 crate DAG，这是架构一节最直观的一张图。

图谱给的是**候选位置**，具体贴哪几行仍要人工判断，判断标准还是本文开头那个填空模板。

## 低价值对照：不要选这些

- 纯语法糖对比（`for` 循环 vs 迭代器链，除非能说明它消除了索引越界的可能）
- 行数变少（除非能说明少的是哪一类代码，比如"少的全是错误处理样板"）
- "Rust 更现代""写起来更爽"这类主观感受
- 用旧实现里最烂的一段对比新实现里最好的一段——这种对比一旦被识破，整份材料就废了。**选取时要说明为什么这段有代表性。**
