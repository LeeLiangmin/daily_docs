# C/C++ → Rust 重构项目流程管理手册

> 版本：v1.0　|　用途：团队内部可复用的 SOP 模板　|　适用范围：模块级 / 全量级 C/C++ 代码库向 Rust 迁移

## 使用说明

本文档是一份**流程模板**，不是针对单一项目的实施细则。使用方式：

1. 项目启动时，复制本文档到项目仓库 `docs/migration/` 目录下
2. 按每个阶段的检查清单逐项打勾，未完成项需说明原因
3. 每个"签单"章节需要责任人签字（可用 PR review / 邮件确认代替纸质签字，但必须留痕）
4. 项目结束后，将实际执行情况与本模板的差异反馈回来，用于迭代本手册

整体流程分为 **六个阶段**：

```
阶段0 准入评估 → 阶段1 基线建立 → 阶段2 环境准备
   → 阶段3 执行与过程管理 → 阶段4 交付验收 → 阶段5 上线与复盘
```

## 阶段 0：准入评估（立项签单）

### 0.1 目的
决定"要不要重构、用什么策略重构"，避免重构决策拍脑袋。

### 0.2 评估检查清单

| 检查项 | 说明 | 结论 |
|---|---|---|
| 模块边界是否清晰 | 是否有明确的接口层可以隔离改造 | □是 □否 |
| 第三方依赖 Rust 生态覆盖度 | 关键 C/C++ 库是否有成熟 Rust crate 或可 FFI 封装 | □高 □中 □低 |
| 内存管理复杂度 | 裸指针、手动生命周期管理、复杂所有权关系的密度 | □低 □中 □高 |
| 并发/多线程复杂度 | 锁、原子操作、线程模型复杂度 | □低 □中 □高 |
| 实时性/性能敏感度 | 是否存在硬实时约束，Rust 改造后能否满足 | □是 □否 |
| 现有测试覆盖率 | 决定基线建立成本 | ___% |
| 团队 Rust 熟练度 | 是否需要培训期 | □熟练 □需培训 □需外部支持 |
| 历史缺陷密度 | 该模块过去 N 个月的 bug 数/严重度，判断重构收益 | ___ |

### 0.3 策略选择（三选一，需写明理由）

- [ ] **全量重写**：适合模块小、边界清晰、依赖少的场景
- [ ] **模块级增量替换（Strangler Fig）**：适合大型系统，逐步收缩 C/C++ 边界
- [ ] **长期 FFI 混合共存**：适合核心库暂无 Rust 替代、只对新代码用 Rust 的场景

## 阶段 1：基线建立

> 这是全流程中最容易被低估、但决定重构成败的一环。没有可靠基线，重构等于盲飞。

### 1.1 功能基线

- [ ] 梳理对外接口清单（函数签名、协议、命令行参数等），形成**接口契约冻结文档**
- [ ] 构建黑盒行为快照：固定输入 → 记录输出、日志、副作用，形成可自动比对的回归测试集
- [ ] 覆盖边界情况与异常路径（不只是 happy path）
- [ ] 已知缺陷清单归档（重构不是顺带修 bug，除非明确纳入范围）

### 1.2 性能基线

| 指标 | 测量方法 | 基线值 | 可接受劣化范围 |
|---|---|---|---|
| 吞吐 | | | |
| P99 延迟 | | | |
| 内存峰值 | | | |
| CPU 占用 | | | |
| 启动时间 | | | |

### 1.3 质量基线

- [ ] 静态扫描结果存档（圈复杂度、重复率等）
- [ ] 现有单测/集成测试覆盖率记录
- [ ] Sanitizer（ASan/UBSan/TSan）扫描结果存档，作为 Rust 版本"内存安全提升"的对比依据

### 1.4 基线交付物

- `baseline/functional-snapshot/`：功能快照与回归用例
- `baseline/perf-report.md`：性能基线报告
- `baseline/quality-report.md`：质量基线报告
- `baseline/interface-contract.md`：接口契约冻结文档

## 阶段 2：环境准备

### 2.1 工具链

- [ ] Rust 版本 / edition 锁定，写入 `rust-toolchain.toml`
- [ ] 混合构建体系搭建（CMake + Cargo，或 corrosion / cxx 等工具）
- [ ] FFI 工具链确定（bindgen 生成绑定 / cbindgen 导出头文件）
- [ ] 依赖库选型清单，附带 License 合规审查结果

### 2.2 CI/CD

- [ ] 双语言构建流水线（C/C++ 与 Rust 部分均可独立构建、联合构建）
- [ ] clippy + rustfmt 强制检查
- [ ] cargo-audit / cargo-deny 依赖安全扫描
- [ ] 与阶段1基线的自动化比对（性能回归、行为回归）接入 CI
- [ ] Miri / sanitizer 对照测试（针对 unsafe 代码块）

### 2.3 开发环境

- [ ] 容器化开发环境（Dockerfile / devcontainer），避免"我这能跑"
- [ ] 团队 Rust 培训材料 / onboarding 文档（如策略选择中标注需培训）

## 阶段 3：执行与过程管理

### 3.1 模块切分与验收标准

每个模块进入重构前，需明确：

- 模块边界与依赖关系
- 验收标准：**功能对等** + **性能不劣于基线容忍范围** + **unsafe 代码占比上限**
- 负责人与预计工期

### 3.2 问题处理流程（分级）

| 问题类型 | 处理方式 |
|---|---|
| 行为不一致（与基线快照不符） | 回归基线定位差异，优先怀疑重构引入而非"顺手改需求" |
| 性能倒退 | Profiling 对比，超出容忍阈值则打回，不允许"先上线再说" |
| Rust 生态缺失某能力 | 短期用 FFI 包一层过渡，**必须记录为技术债并设定偿还时限**，不允许无限拖延 |
| unsafe 代码难以避免 | 集中封装、加注释说明不变式（invariant），必要时补充 Miri/fuzz 测试 |
| 严重架构分歧 | 升级到技术负责人仲裁，不在模块内部无限讨论 |

### 3.3 回滚机制

- [ ] Feature flag 或双实现并存开关，保证任意阶段可退回 C/C++ 实现
- [ ] 回滚触发条件提前书面定义（如：P99延迟劣化超过X% / 崩溃率上升）

### 3.4 进度看板（建议字段）

- 模块完成率
- 代码转换比例（LOC）
- unsafe 代码占比趋势
- 测试覆盖率变化
- 遗留技术债数量与状态

### 3.5 里程碑评审

固定节奏（如每两周）对照 0.4 的优先级和 1.x 基线做评审，防止范围蔓延（scope creep）。

## 阶段 4：交付验收

### 4.1 交付物清单

- [ ] **源码**：重构后代码 + 构建脚本（含混合构建配置）
- [ ] **功能对等性测试报告**：对照阶段1功能基线的比对结果
- [ ] **性能对比报告**：对照阶段1性能基线，说明达标/劣化项及原因
- [ ] **安全审计报告**：unsafe 代码审计结果、fuzzing 报告、sanitizer 对照结果
- [ ] **架构与迁移文档**：新旧架构对比、模块依赖图、FFI 边界说明
- [ ] **运维/部署变更说明**：部署方式、配置项、监控指标是否变化
- [ ] **回滚预案**：明确的回滚步骤与触发条件
- [ ] **技术债清单**：遗留的 FFI 过渡层、待优化 unsafe 块等，附偿还计划
- [ ] **团队知识转移材料**：培训记录、关键设计决策记录（ADR）

### 4.2 建议交付目录结构

```
project-root/
├── docs/
│   └── migration/
│       ├── 00-admission-review.md        # 阶段0签单
│       ├── baseline/                     # 阶段1基线
│       │   ├── functional-snapshot/
│       │   ├── perf-report.md
│       │   ├── quality-report.md
│       │   └── interface-contract.md
│       ├── architecture.md               # 新旧架构对比
│       ├── migration-log.md              # 过程记录（问题/决策/技术债）
│       ├── security-audit-report.md
│       ├── perf-comparison-report.md
│       ├── rollback-plan.md
│       ├── tech-debt-tracker.md
│       └── acceptance-signoff.md         # 阶段4签单
├── src-rust/                             # Rust 实现
├── src-legacy/                           # 保留的 C/C++ 部分（如混合共存）
├── ffi-bindings/                         # FFI 绑定层
└── ci/                                   # CI 配置与基线比对脚本
```

### 4.3 交付签核

| 角色 | 确认事项 | 签字/日期 |
|---|---|---|
| QA | 功能对等性、回归测试通过 | |
| 架构负责人 | 架构合理性、技术债可控 | |
| 安全负责人 | unsafe 审计、依赖安全扫描通过 | |
| 业务负责人 | 交付范围与预期一致 | |

**任一项未通过，不得进入阶段5上线。**

## 阶段 5：上线与复盘

- [ ] 灰度发布计划，明确观察周期与回退触发条件
- [ ] 上线后核心指标对比基线（内存安全事故数、崩溃率、性能）
- [ ] 复盘会议：预期收益 vs 实际数据，记录经验教训
- [ ] 将本次执行中与本手册的差异点反馈更新到手册模板（版本迭代）
