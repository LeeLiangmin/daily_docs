# C/C++ → Rust 单项目迁移总流程

## 1. 文档目的

本文档用于指导一个具体 C/C++ 项目迁移到 Rust 的完整过程。

目标不是描述某种通用的 Rust 编程方法，而是明确：

- 项目开始前要确认什么；
- 原项目需要了解什么；
- 迁移前要准备什么；
- 迁移过程中怎么控制进度；
- 什么条件算迁移完成；
- 最终交付什么；
- 项目结束后怎么复盘。

整个流程按**单个项目**执行。

---

## 2. 基本原则

### 一次只迁移一个项目

一个迁移流程只对应一个具体 C/C++ 项目。

当前项目完成并交付后，再开始下一个项目。

### 一个项目使用一个确定的模型

项目开始前确定模型。

迁移过程中不设计多模型切换或模型兜底。

模型无法处理的问题：

1. 迁移工程师处理；
2. 如果涉及原代码行为或业务语义，由业务方或原项目负责人确认。

### 项目流程和迁移 skill 分开

项目流程负责：

- 范围；
- 输入；
- 进度；
- 问题；
- 结果；
- 交付；
- 复盘。

具体代码如何迁移，由现有迁移 skill 负责。

---

## 3. 总体流程

```text
1. 迁移前确认
        ↓
2. 原项目现状
        ↓
3. Rust 迁移方案
        ↓
4. 按迁移 skill 执行并控制进度
        ↓
5. 结果验证、交付、复盘
```

对应核心文档：

```text
01 迁移需求确认单
02 原项目现状报告
03 Rust 迁移方案
04 Skill执行与进度记录
05 迁移结果、交付与复盘
```

---

# 4. 第一阶段：迁移前确认

## 目的

先把项目谈清楚，避免迁到一半才发现双方理解不一致。

核心回答：

- 为什么迁？
- 迁什么？
- 迁完要达到什么目标？
- 最终要交什么？
- 业务方能提供什么？
- 当前有没有条件开始？

## 主要确认内容

- 迁移背景；
- 迁移范围；
- 不迁的内容；
- 迁移目标；
- 交付要求；
- 业务方人员投入；
- 编译环境；
- 测试环境；
- 工作环境；
- 模型条件；
- 目标平台和架构；
- 第三方依赖限制；
- 需要保持兼容的内容；
- 当前已知风险。

## 产出

`01_迁移需求确认单.md`

---

# 5. 第二阶段：原项目现状

## 目的

搞清楚迁移前 C/C++ 项目的真实状态。

不是做技术审计，只记录后面真正会用到的数据。

核心回答：

- 原项目能不能稳定构建？
- 现在有哪些测试？
- Rust 完成后需要和哪些数据比较？
- 有哪些重要第三方依赖？
- 哪些接口或行为不能改变？
- 原项目已经存在哪些问题？
- 哪些地方可能成为迁移难点？

## 主要内容

- 构建情况；
- 测试情况；
- 性能和资源数据；
- 二进制大小；
- 第三方依赖；
- 兼容要求；
- 当前已知问题；
- 迁移时需要特别注意的地方。

## 原则

如果某项数据：

- 不影响迁移方案；
- 不影响迁移过程；
- 不用于最终验收；

则没有必要为了填表而收集。

## 产出

`02_原项目现状报告.md`

---

# 6. 第三阶段：Rust 迁移方案

## 目的

从“当前是什么状态”走到“业务方要求的目标状态”。

这里只确定项目层面的迁移方案，不重复定义 skill 内部怎么迁代码。

核心回答：

- 迁哪些内容？
- 哪些内容不迁？
- 各部分大体怎么处理？
- 第三方依赖怎么处理？
- 哪些接口和行为必须保持？
- 哪些地方保留 C/C++？
- 最大风险是什么？
- 哪些问题需要先验证？
- skill 开始执行前需要准备什么？

## 产出

`03_Rust迁移方案.md`

---

# 7. 第四阶段：按 skill 执行迁移并控制进度

## Skill 顺序

当前项目按照以下顺序执行：

```text
legacy-spec
    ↓
legacy-ffi
    ↓
legacy-test-gen
    ↓
legacy-translate
    ↓
legacy-lite-tdd
```

每个 skill 有自己的内部阶段。

项目流程不重新定义这些阶段。

## 项目层怎么控制进度

项目只记录：

- 当前正在执行哪个 skill；
- 当前处于该 skill 的哪个阶段；
- 当前阶段完成了什么；
- 当前还缺什么；
- 有没有阻塞；
- 是否可以进入下一个 skill。

## 进度判断

不以“迁移了多少行代码”作为主要进度。

也不要求强行计算一个“完成 63%”。

主要看：

```text
legacy-spec       已完成
legacy-ffi        已完成
legacy-test-gen   进行中：<当前阶段>
legacy-translate  未开始
legacy-lite-tdd   未开始
```

## 产出

`04_Skill执行与进度记录.md`

---

# 8. 第五阶段：结果验证、交付和复盘

## 目的

回答三个问题：

1. 迁移结果是否达到项目开始时约定的目标？
2. 是否具备正式交付条件？
3. 这个项目有哪些经验可以用于下一个项目？

## 结果验证

使用《原项目现状报告》中已经记录的数据进行对比。

例如：

| 对比项 | 原 C/C++ | Rust | 原定要求 | 是否达到 |
|---|---:|---:|---:|---|
| 功能测试 | | | | |
| 单元测试 | | | | |
| 集成测试 | | | | |
| 性能 | | | | |
| 内存 | | | | |
| 二进制大小 | | | | |

只保留这个项目真正关心的指标。

## 交付

主要包括：

### 代码和产物

- Rust 源代码；
- 保留的 C/C++ 代码；
- 构建脚本；
- 测试代码和脚本；
- 最终产物。

### 说明材料

- 迁移需求确认单；
- 原项目现状报告；
- Rust 迁移方案；
- Skill 执行及进度记录；
- 设计和实现说明；
- 测试结果；
- 性能结果；
- 第三方依赖说明；
- 已知问题；
- FAQ；
- 发布和运维说明。

## 复盘

重点回答：

- 哪些地方比较顺；
- 哪些地方最容易卡住；
- 哪些地方返工最多；
- 哪些问题本可以更早发现；
- 哪个 skill 最容易出问题；
- 哪些输入准备不足；
- 模型在哪些地方效果好；
- 哪些地方必须人工介入；
- 下一个项目流程需要改什么。

## 产出

`05_迁移结果_交付与复盘.md`

---

# 9. 整个项目的核心逻辑

```text
为什么迁
    ↓
迁什么
    ↓
原项目现在是什么样
    ↓
这次准备怎么迁
    ↓
按照 skill 一步一步执行
    ↓
持续知道当前迁到哪里
    ↓
迁移后的 Rust 是什么状态
    ↓
是否达到最初目标
    ↓
是否可以交付
    ↓
这个项目留下什么经验
```

整个流程的原则很简单：

> 每一步都要能让一个没有参与前面讨论的人知道：现在该干什么、已经有什么结果、还缺什么、能不能继续。
